# 第一部分：存储位置功能评估

## 1.1 功能现状（证据）

「管理 → 存储 → 存储位置」（Job000103，契约 §18）对外语义是"命名物理存储根"：创建后不可改名，媒体可归属到某位置，未归属的留在"默认存储根"。

**代码证据：**

| 层 | 位置 | 事实 |
| --- | --- | --- |
| 迁移 | `migrations/00034_storage_locations.sql:6-21` | 建 `storage_locations` 表；`media` 加 `location_id UUID REFERENCES storage_locations(id) ON DELETE SET NULL` + 索引 |
| 后端 | `internal/storage/locations.go` | 4 个端点：Create（名称 slug 校验+重名 409）/ List（带 media_count 引用计数）/ Patch（仅改描述，name 不可改 400）/ Delete（COUNT>0 拒删 409） |
| 路由 | `cmd/api/main.go:265-268` | `GET/POST/PATCH/DELETE /storage/locations`（requirePrivileged） |
| 前端 | `src/frontend/src/views/admin/StorageLocationPanel.vue` | 纯 CRUD 面板：新建/改描述/删除/引用计数徽标。**无任何"把媒体/目录绑定到位置"的交互** |
| 与挂载关系 | `migrations/00032_storage_mounts.sql:5-22` | `storage_mounts` 表**无 location_id 列**——两个功能数据层完全不相连 |

**消费方排查（核心证据）——全仓 `location_id` grep 命中仅 3 处，全部在 locations.go 自身：**

- `locations.go:86` ListLocations 的 `SELECT COUNT(*) FROM media m WHERE m.location_id = l.id`（引用计数展示）
- `locations.go:154` DeleteLocation 的 COUNT 删除守卫
- `internal/mediascope/source_guard_test.go:569-575` 上述两查询的守卫登记（非面向用户豁免）

**三条 INSERT INTO media 路径逐一核对，均不含 location_id：**

- 扫描入库 `internal/index/index.go:94-114`
- 上传入库 `internal/media/upload.go:519-532`
- 复制入库 `internal/media/batch_store.go:134-144`

**读取/解析侧也全部不消费**：原文件解析 `upload.go:130-149 ResolvePath` 只按 `UploadDir → MediaRoot` 回退拼路径；缩略图 `thumb.go:39-62` 走 `THUMB_DIR`；下载同 ResolvePath；全仓无按位置的配额统计（quota 仅命中算力节点 GPU 配额）。

**线上实测（2026-09-25，测试服 pano_album 库）：**

| 检查 | 结果 |
| --- | --- |
| `SELECT count(*) FROM storage_locations` | **0** |
| `SELECT count(*) FROM media WHERE location_id IS NOT NULL` | **0**（死列线上实证） |
| `SELECT count(*) FROM storage_mounts` | 0 |

## 1.2 使用场景分析

设计初衷（Job000103 台账）是给"多物理存储根"预留命名层：将来媒体可以标记"存在 archive-a 盘还是默认盘"。但**从立项到现在没有任何数据流接线**：上传不选位置、扫描不标位置、读取不查位置。它现在唯一能干的事是"创建一个名字，看着它显示 0 个引用"。

## 1.3 是否被其他功能替代

不是"被替代"，而是**从未启用**：

- 物理多盘场景的真实承载者是**网络挂载**（rclone/NFS 落进媒体库 `_imports/`）与 bind mount——它们直接成为媒体库目录树的一部分，不需要 location 这层抽象；
- 存储统计由管理端概览（`/admin/stats` 全站计数+字节数）覆盖；
- "媒体存在哪"在文件/文件夹视图里直接可见。

## 1.4 维护成本与用户困惑

| 成本类型 | 具体表现 |
| --- | --- |
| 代码维护 | locations.go + locations_test.go + 4 路由 + 前端面板 + api 封装 ≈ 500 行；每次大改（守卫登记、契约、手册、nginx 前缀核对）都要带着它 |
| 守卫登记 | source_guard 专门登记了它的两条 COUNT 豁免（`:569-575`），删除文件时必须成对清理，否则守卫红 |
| 用户困惑 | 面板的「命名物理存储根」「引用计数」文案暗示它能管理媒体存放位置，实际什么都绑不上——管理员的合理操作（"把我的媒体归到 archive-a"）没有任何入口，是典型的"看起来有用、用起来落空" |
| 文档负担 | 契约 §18 整节 + 手册存储页签描述需要随它同步演进 |

## 1.5 结论

**建议移除。** 该功能无实际价值、无替代冲突、移除零功能损伤，且能降低长期维护面。

**上线前预检 SQL（任何环境先跑）**：

SELECT (SELECT count(*) FROM storage_locations) AS locations,

# 第三部分：挂载逻辑改造设计

## 3.1 现状梳理（问题定性）

当前挂载落点链路（证据见 `cmd/storagectl/mount.go:182-184` + `main.go:215`）：

```
创建挂载（填 name/type/conn/凭据）
  → storagectl 对账：rclone/nfs 只读挂到容器内 /mnt/storage/<id8>
  → 增量复制到 /data/media/_imports/<id8>/        ← 落点硬编码，用户不可控
  → ScanAsPrefixed(prefix="_imports/<id8>") 入库归属属主
  → media.folder_path = "_imports/<id8>/…"
```

问题：

1. **落点是技术名** `_imports/<id8>`——用户在文件夹树里看到的是 `_imports/a1b2c3d4`，不可读、无法表达语义（"这是爸妈 NAS 的照片"）；
2. **空挂载目录不可见**——文件夹树 = `media.folder_path` 聚合 ∪ `folder_dirs` 注册表（`internal/folders/folders.go:76-145`）；挂载刚建好、还没同步文件时，`_imports/<id8>` 两个来源都不沾，**用户在文件夹里完全看不到它**；
3. **用户无法选择归类**——想把 NAS 照片并进 `photos/trip` 之类的既有语义目录？没有入口。

注意：条件②「能被相册扫描到」在现状下是**事实成立**的（落点在 MEDIA_ROOT 之内，`/admin/scan` 递归不排除 `_imports`）——改造的真正着力点是**条件①可见性**与**语义化**。

## 3.2 改造目标与两条件的可判定定义

> 网络位置必须**明确挂载到用户指定的虚拟语义目录**（`landing_dir`，相对媒体根的路径）。
> 该目录必须同时满足：
> **条件①（文件夹可见）**：`GET /folders/tree` 返回的目录树中存在 `landing_dir` 节点——无论是否已有媒体（空目录经 `folder_dirs` 注册表可见）。
> **条件②（扫描可及）**：`POST /admin/scan {"dir": landing_dir}` 返回 202 且任务能扫到该目录下文件（等价于 Job000117 目录树选择器能逐级浏览到它——两者同一 `resolveScanDir` 边界）。

## 3.3 改造后挂载流程

```
① 创建挂载（新增「导入到」字段 landing_dir）
   ├─ 前端：输入框 + 「浏览…」（复用 Job000117 DirectoryTreeDialog 选既有目录）
   │        默认值建议 imports/<名称slug>，可改
   ├─ 后端校验：相对路径（拒绝绝对）、逐段 slug（[a-z0-9-_]，1-32 字符）、
   │          拒绝 .. 穿越（复用 index.resolveScanDir 的越界判定口径）、
   │          拒绝保留前缀 _imports/* 与 @eaDir*、解析后必须仍在 MEDIA_ROOT 内
   └─ 入库 storage_mounts.landing_dir
② api 创建时同步准备落点（条件①+②的就绪）
   ├─ MkdirAll(MEDIA_ROOT/landing_dir)（api 容器挂 mediadata 卷，直接可建）
   └─ 注册 folder_dirs(path=landing_dir, owner_id=mount.owner_id)
     → 空目录此刻已出现在「文件夹」树（中间段自动成节点，BuildTree 纯函数派生）
③ storagectl 对账（改动点最小化）
   ├─ syncLocalDir: UPLOAD_DIR/_imports/<id8>  →  UPLOAD_DIR/<landing_dir>
   └─ 索引前缀:   "_imports/"+mountKey(id)      →  landing_dir（ScanAsPrefixed 签名不变）
④ 增量同步 → 文件落在语义目录 → folder_path 聚合自然可见 → /admin/scan 可扫
⑤ 删除挂载：保持现有语义——只删注册行，FUSE 卸载+rmdir 由对账孤儿清理执行；
   已导入文件与 media 行**保留**（归属用户）；folder_dirs 注册行随挂载删除清理，
   目录物理保留（里面是用户媒体，不许删）
```

**变更 landing_dir（PATCH）**：v1 建议**不允许修改**（同 location 的 name 不可改理由：导入路径稳定）。要改 = 删了重建。→ 需用户裁决（见 §5 开放问题）。

## 3.5 兼容与迁移

- 存量挂载（测试服 0 行；通用部署可能有）→ 00036 回填 `_imports/<id8>`，行为与改造前**逐字节一致**；
- 存量 `_imports/` 目录物理保留（历史导入文件不动）；新建挂载禁止再用 `_imports` 前缀，老挂载继续可用——平滑过渡；
- 哈希去重链不变：无论落点路径是什么，重复导入仍按 sha256 幂等。

## 3.6 边界与安全

| 风险 | 对策 |
| --- | --- |
| 路径穿越（landing_dir=../../etc） | normalizeLandingDir 复用 resolveScanDir 越界判定 + 逐段校验，400 INVALID_INPUT |
| 覆盖系统目录名 | 保留前缀黑名单：`_imports`（历史机制）、`@eaDir`（群晖 sidecar） |
| 选到已含大量媒体的目录 | 允许（哈希去重保证幂等），但对话框给确认提示"该目录已有 N 个媒体，导入将并入其中" |
| folder_dirs 注册与目录物理删除的竞态 | 注册行只在挂载删除时清理；用户手动删物理目录不影响（folders 树对注册行标注 Registered，已有语义） |
| 多挂载选同一目录 | v1 允许（不同远程源可汇入同一目录，哈希去重兜底）；列表页展示归属 |

# 第四部分：验证方法（两点要求的可执行判定）

## 4.1 条件①「文件夹可见」验证

**API 级（挂载创建后、任何文件同步之前立即断言——这是本改造的核心增量）：**

```
GET /folders/tree（owner 身份）
断言：返回树中存在 path == landing_dir 的节点（含空目录场景）
```

实现提示：folders 树节点目前从前端组件拼出，e2e 探针可按节点名逐级查 DOM（FolderTree），或直接用 DB 断言 `SELECT count(*) FROM folder_dirs WHERE path=$1`（快但绕开 API）；推荐 CDP DOM 断言（真实用户视角）。

**UI 级：** 文件夹页左侧树展开可见 `landing_dir` 节点名（截图留证）。

## 4.2 条件②「扫描可及」验证

**API 级（两级断言）：**

```
1. GET /admin/fs/tree?dir=<landing_dir 的父目录> → items 含 landing_dir 末段
   （Job000117 选择器能浏览到 = 扫描面板能选到）
2. POST /admin/scan {"dir": landing_dir} → 202 → 轮询 GET /admin/jobs/:id 至 done
   → 断言 job done 且（若有文件）total>0；media.folder_path LIKE 'landing_dir/%'
```

**e2e 全链路（测试服实际部署后执行）：**

| 步骤 | 动作 | 预期 |
| --- | --- | --- |
| 1 | 创建挂载，landing_dir=`imports/e2e-nas` | 201；响应含 landing_dir |
| 2 | 立即查 GET /folders/tree | **imports/e2e-nas 节点已可见（空目录）← 核心断言** |
| 3 | 等 storagectl 对账（≤10s） | 挂载 online；文件落地 imports/e2e-nas/ |
| 4 | 文件夹页 UI | 树节点可见且媒体可浏览 |
| 5 | POST /admin/scan {"dir":"imports/e2e-nas"} | 202 → done；hash 去重（storagectl 已导过 → total=0 或全 duplicate，无重复行） |
| 6 | 目录树选择器浏览 | 能逐级浏览到 imports/e2e-nas |
| 7 | 删除挂载 | 204 → 对账卸载 → folder_dirs 行清理 → imports/e2e-nas 从树消失（物理目录与媒体保留） |
| 8 | 存量兼容 | 造一条 landing_dir 回填为 `_imports/<id8>` 的挂载 → 对账后路径形态与改造前一致 |

## 4.3 回归面

- 既有挂载 e2e（Job000076 系）重跑：落点回填逻辑不得改变存量行为
- folders 管理端点（POST /folders、grants）与挂载注册无冲突（folder_dirs 主键 path，重复注册用 ON CONFLICT DO NOTHING）
- storagectl 单元/集成：syncLocalDir 改 landing_dir 后的对账循环
