## 0. 结论先行（给决策用）

1. **功能成立，且技术地基已具备三处**：
   - 「同源视频」判定有现成依据 —— `media.hash` 是 **sha256 内容哈希**（`migrations/00024_media_phash.sql:42` 的 COMMENT 明确「sha256 内容哈希（64 hex）。感知哈希见 media.phash —— 两者语义不同，勿混用」）。同源复用因此可判定为「源文件字节完全相同」，不需要新建指纹体系。
   - 多用户隔离有**唯一真源** —— `internal/mediascope`。回忆标签只挂可见性裁决，不另造一套权限。
   - 异步任务有现成队列 —— 自研 `internal/queue`（键 `q:<name>:waiting|processing|delayed|failed`），AI 打点走队列而非同步请求。

2. **「AI 自动打点」需要重新定义**，三条候选路径中有一条不可行、一条需扩展、一条推荐：
   - 复用内置人脸识别模块 —— **不可行**（理由见 §8.2，人脸管线是清扫式单帧、输出不含事件语义、无视频时序能力）。
   - 复用现有 Agent 语义接口 LLM 上游 —— **需扩展**。现 `internal/agentllm.ProxyChat` 是**纯文本透传**（body 原样转发，4MB 上限），全仓无 vision/多模态代码。
   - **推荐：分层降级 L0–L3**（见 §8.3）。二期建议只做 L0–L2：零 token 成本的本地启发式候选点（音频能量/场景切换/GPS 变化）+ LLM 文本编排生成标题描述。多模态抽帧理解（L3）列入远期可选，默认关闭。

3. **需求原文有 11 处建议修正**（含 2 处必须修正的交互隐患），详见 §3 各项内的「修正建议」标记与 §9 汇总。**审核结果：11 条全部采纳。**

## 1. 功能定位与命名

### 1.1 一句话定义

在任意视频（普通视频 / 全景视频）上标注「**回忆点**」（单一时间点）与「**回忆片段**」（时间区间），既能手工创建、也能由 AI 提议候选；标签可被跳转定位、被搜索、被分享，并能在**同源视频**（源文件字节完全相同）之间显式复用。

### 1.2 与相邻概念的边界（重要，避免落地时混淆）

| 概念 | 是什么 | 与本功能的关系 |
| --- | --- | --- |
| `tags` / `media_tags`（现有） | 给**整张媒体**打的关键词标签（user/ai 两类，含逐图态 confirmed/confidence/origin） | **不同层**。回忆标签带时间轴坐标与视角，是「媒体内部」的标注；`tags` 是「媒体级」的标注。二者数据结构不共用（见 §4.1） |
| `memories` 表（00008 预留） | 空壳表：id/title/criteria JSONB/video_asset_path/owner_id/created_at，注释「回忆影片（可选模块）」 | **不复用**。其字段语义是「生成一段回忆影片」的合成任务，与「在时间轴上打点」不匹配；且 Go 侧零读写引用（grep 全仓无命中）。建议保留不动，本功能新建表（见 §4.1 决策 3） |
| `album_comments`（现有） | 相册级评论（两级回复） | 无关联。回忆描述不是评论，不提供他人回复 |
| 播放列表 / 收藏 | 集合与偏好 | 无关联 |

### 1.3 目标用户与场景

- **主场景**：家庭相册主人回看长视频（旅行 vlog、孩子成长记录、活动录像），在「值得重看」的位置插旗，日后一键跳到那一段。
- **次场景**：把「高光片段」分享给家人（分享链接里带标签，观看者可直接跳到那段，不用拖进度条）。
- **复用场景**：妻子与丈夫各上传了同一段婚礼视频，妻子的标注可以一键「搬」到丈夫的副本上，无需重打。

## 3. 功能逐项展开（含修正建议）

> 标记约定：**【保留】** 原需求可直接落地；**【澄清】** 需补充定义；**【修正建议】** 建议改变原需求写法，理由随附。

### F1 总开关与 AI 子开关

**原需求**：设置/管理中新增「视频热点回忆」总开关，关闭后全站隐藏相关入口；其下可单独开启「AI 智能回忆点/片段自动标签」，含生效时间段与触发方式（手动/定时/新视频自动），模型可复用现有设置中的 Agent 语义接口·LLM 上游，也可单独配置专用大模型 API，或评估复用内置人脸识别 AI 模块。

| 需求点 | 处置 | 说明 |
| --- | --- | --- |
| 总开关，关闭后全站隐藏入口 | 【保留】 | 「隐藏相关入口」的清单要枚举死（见下），否则会漏。关闭后：详情页「回忆」块不渲染、列表按钮不渲染、添加弹窗不可达、设置页 AI 子项置灰、搜索不返回回忆条目、分享创建对话框不出现「回忆标签」勾选、已有分享链接中的回忆标签**仍可见**（历史链接不能被开关追溯破坏，见 §7 边界 B-09） |
| 生效时间段 | 【澄清】 | 明确含义：**不是**「只对某个拍摄时间段内的视频生效」，而是**允许 AI 任务运行的每日时间窗**（如 02:00–06:00，避开日间资源争抢）。默认 `02:00–06:00`，可关闭时段限制改为「立即执行」。 |
| 触发方式：手动 / 定时 / 新视频自动 | 【修正建议】 | **默认只开「手动」**。「定时」= 每日在生效时段扫描未分析视频入队（配额内）；「新视频自动」需加**双重限流**：单次入库最多 N 个（默认 5）+ 队列串行，否则批量导入 100 个视频会形成任务风暴，把队列与 GPU/CPU 占满（与 v1.9.x 的转码资源教训同源）。此外三种触发共用同一个「单日 AI 任务配额」（见 F9）。 |
| 模型来源：复用 Agent LLM / 单独配置 / 复用人脸模块 | 【修正建议】 | 见 §8。UI 上给**两选一**：`复用 Agent 语义接口·LLM 上游`（默认）/ `单独配置专用 API`（展开一组独立表单，存 DB 一张新单行表或复用 `agent_llm_config` 结构的第二条记录）。**移除「复用人脸模块」选项** —— 该路径技术上不成立（§8.2），写进 UI 会误导使用者。 |

**UI 落点**：`views/SettingsView.vue` 新增一个卡片区（`views/settings/VideoMomentCard.vue`），壳样式对齐 `.card`（`bg: var(--color-surface); border: 1px solid var(--color-border); border-radius: var(--radius-lg); padding: 20px`）。开关沿用全站惯例：原生 `<input type="checkbox">` + `accent-color: var(--color-primary)`（范式参考 `views/admin/TranscodeTab.vue`；全仓无独立 Switch 组件）。**权限门**：AI 子项涉及 LLM 密钥，应比照 `AgentLlmCard` 的 403 整卡不渲染门禁（`admin:system`）。

**持久化【修正建议】**：总开关属于「系统级」而非「用户级」，应走**服务端配置**（新表 `app_settings` 单行或复用现有配置接口），不要写前端 `ui-prefs`——否则每个用户的开关状态不同，分享页判定会出现「A 关了 B 没关」的矛盾。UI 偏好（如「删除时不再二次确认」）才走 `ui-prefs`。

### F2 标记模型（回忆点 / 回忆片段）

**原需求**：任意视频（全景/非全景）均可手工添加两类标签；多用户同源视频数据完全隔离。

**【澄清】「多用户同源视频数据完全隔离」的精确含义**（这是本功能最容易做错的一条）：

系统里存在「源文件完全相同、但是两条独立 media 记录」的情形（不同账号各自上传了同一文件；`media.hash` 相同）。隔离要求应表述为：

> **系统不得因 `media.hash` 相同而跨账号共享任何回忆数据。** 同源复用只能是**显式的、一次性的复制动作**（属主主动发起 → 拷贝一份成为自己的数据 → 之后各自独立演进），默认状态下 A 的标签绝不出现在 B 的视频上。

这正好也是 F8「应用到我自己的视频」的实现约束（复制而非引用，见 §8.4 的复用语义）。

**隔离粒度三层**（与现有可见性模型同构）：

| 层 | 规则 |
| --- | --- |
| 个人空间（`media.space='personal'`） | 仅 `media.owner_id` 本人可见可编辑；他人（含同源副本的他人）不可见 |
| 共享空间（`media.space='shared'`） | 空间成员可见；**编辑权仅限标签创建者本人与空间管理者**（待裁决，见 §12 开放问题 Q-3） |
| 分享页（无登录） | 仅能看到分享配置里勾选的那部分（只读，仅可跳转） |

**「两类标签」的语义定义**：

| 类型 | 值 | 时间字段 | 播放行为 | 典型用途 |
| --- | --- | --- | --- | --- |
| 回忆点 | `point` | 仅 `start_ms` | 跳到该点（不循环） | 「就是这里」——某句话、某个表情、某个瞬间 |
| 回忆片段 | `clip` | `start_ms` + `end_ms` | 跳到起点并**循环播放该区间** | 「这一段」——一小段表演、一段对话 |

**【修正建议】片段最短长度**：原需求未定义。建议强制 `end_ms - start_ms >= 500ms`（防误触产生零长片段），上不封顶（= 整片）。

**【修正建议】数量上限**：原需求说「无限增删改」。建议单视频 **≤50 个**（手工 + AI 合计），理由：① 详情页与列表弹窗的可用性（50 行已是滚动极限）；② 防止 AI 生成或脚本刷量造成数据膨胀；③ 分享勾选的可操作性。达到上限时给出明确提示而非静默失败。

**视频类型判定【修正建议】**：原需求写「任意视频」。落地时注意 `media_type` 枚举是 `('photo','video','360')`（`migrations/00004_ddl_part.sql:4`），**360 是独立类型**；前端 `usePlayerMedia.js` 的 mode 判定顺序是 `is_360 → photo → video`（`mode` 取值 `''|'photo'|'pano'|'video'`）。因此「回忆」块的渲染条件必须是 **`mode === 'video' || mode === 'pano'`**，不能写成 `detail.type === 'video'`（会漏掉全部全景视频）。

### F3 添加 / 编辑浮层

**原需求**：可鼠标拖动的独立浮层；字段含标题、描述、类型、时间点/起止时间（联动当前播放进度与手动输入，手动输入后暂停并跳转）；全景额外含视角与 FOV（可联动当前播放状态）；视频详情页内可无限增删改。

#### 3.3.1 字段与校验规则（完整表）

| 字段 | 控件 | 约束 | 校验时机 | 服务端错误码 |
| --- | --- | --- | --- | --- |
| 类型 `kind` | 分段单选（回忆点/回忆片段） | 必填，`point`/`clip` | 提交 | 400 `INVALID_KIND` |
| 标题 `title` | 单行输入 | 必填；去首尾空白后非空；**显示宽度 ≤20**（汉字计 1、其余字符计 0.5，即 20 汉字 = 40 拉丁字符） | 前端实时计数 + 服务端复核 | 422 `TITLE_TOO_LONG` / `TITLE_REQUIRED` |
| 描述 `description` | 多行文本（**见下方修正**） | 选填；显示宽度 ≤200；保留换行；**不做 HTML 渲染** | 同上 | 422 `DESC_TOO_LONG` |
| 时间点 `start_ms` | 取当前进度按钮 + 手动输入 | 必填；`>= 0`；`<= 视频时长`（`media.duration` 是**秒数**，比较时换算） | 提交 | 422 `TIME_OUT_OF_RANGE` |

#### 3.3.2 指令性修正建议

**【修正建议 1 ——「富文本」应降级为纯文本】**（理由 4 条，按权重排序）
1. **XSS 面**：描述会出现在**匿名可访问的公开分享页**。富文本必须配服务端白名单 sanitize（`b/i/br/a` + `a[href]` 协议白名单），这是一整块额外攻击面；而纯文本零风险。
2. **上限不匹配**：200 字的空间里，富文本的排版价值近乎为零（写不了带结构的文档）。
3. **一致性与成本**：全站其它文本域（媒体备注 `PATCH /media/:id` 的 notes、相册描述）都是纯文本。引入富文本编辑器会新增一个前端依赖（体积 + 维护 + `p0_guard` 硬编码色扫描面）。
4. **移动端**：富文本工具的移动端输入体验普遍差于原生 textarea。

**建议实现**：多行纯文本（保留换行，`white-space: pre-wrap` 渲染），前端实时显示「已用 N/200」。若后续确实需要强调，可再评估「极简 Markdown 子集（换行 + 加粗）」——但**二期不做**。

**【修正建议 2 ——「20 中文字符或 20 外文单词」应统一为显示宽度】** 原需求是双口径（汉字按字符、外文按单词），会产生「20 个英文单词 ≈ 100+ 字符 = 5 倍于 20 汉字」的落差，前端计数与用户理解都会混乱。建议统一为**显示宽度 ≤20**（汉字 1 / 其他 0.5），紧凑且与视觉宽度一致；描述同理 ×10 = 200。

**【修正建议 3 —— 手动输入后的「暂停并跳转」要定义副作用边界】** 原需求说「手动输入后暂停并跳转」。要定义：
- 输入**合法**且视频**处于播放中** → 暂停 + seek（这是用户想要的效果）。
- 输入合法但视频**本来就暂停** → 只 seek，**不要自动播放**（否则用户每敲一次就播一下）。
- 输入**非法**（超时长）→ 不 seek，输入框下方红字提示合法范围（如「该视频时长 03:24，请输入 0:00–3:24」）。
- 输入**不完整**（用户刚敲了 1 个字符）→ 不触发任何动作，等 blur 或回车。
- **片段模式下输入 start 早于 end** → 输入 start 时若 `start >= end`，自动把 end 推到 `start + 500ms`（或清空 end 提示重填，二选一，建议前者）。

**【修正建议 4 —— 全景视角的「联动」需要新增播放器通信桥，这是工作量点】** 现状核实：
- `360Player.vue` **没有 `defineExpose`**，父组件 `PlayerView.vue` 只靠 props 单向驱动；视角变量是 `usePanoEngine` 内部的 **`lon` / `lat`**（不是 yaw/pitch），默认 0。
- 因此「取当前视角」需要一个**新的双向通道**：`360Player` 暴露 `getView()` → `{lon, lat, fov}`，并接受一个「恢复视角」的命令入口（props 或 expose 方法）。恢复时必须 `clamp`（`lon` 归一化到 [-180,180]、`fov` 夹到 [45,100]），否则历史数据里的越界值会导致视角异常。
- **同源复用与分享跳转也依赖这个通道**（F8 需要「跳到 00:32 且视角朝北偏东 30°」）。
- 这个桥同时要覆盖**原始文件回退模式**（`panoOriginalUrl` 分支，Job000126）——回退模式下引擎仍活着，视角读写应同样可用，但**循环片段的 seek 精度会降级**（见 §7 B-04）。

**【修正建议 5 —— 可拖动弹窗的移动端策略】** 原需求只提「鼠标拖动」。桌面端用指针事件范式（参考 `components/viewer/ViewerEditTools.vue:156-197` 的 `pointerdown` + window 级 `pointermove/pointerup`，用 `transform: translate()` 移动而非改 `left/top`，避免 layout thrash）。移动端建议**不做自由拖动**，改为**底部抽屉**（全宽、从下升起、内容可滚），理由：手指拖动与大表单的滚动冲突，体验反而差。同时加：双击标题栏复位、拖出视口时 clamp 回可视区、`Esc` 关闭、打开时焦点移入第一个字段（可访问性）。

**【澄清】「无限增删改」** → 见 F2 修正建议（≤50/视频）。

### F4 详情页功能块与三态交互

**原需求**：功能块含跳转/编辑/删除三种状态切换 + 添加、列表按钮；默认跳转态，以带类型小图标的标签呈现，固定 3 行，垂直滚动；片段标签为循环开关（首次点击从头循环，第二次取消）；悬停显示描述与时间信息浮层；删除态需二次确认（可在设置中统一关闭）。

**落点**：`components/player/MediaInfoPanel.vue` 的 `info-body`（:14）内，建议插在 `MediaTagEditor`（:41）之后、评分段之前，条件渲染 `mode === 'video' || mode === 'pano'`（见 F2 修正）。

#### 3.4.1 【修正建议 1 ——「固定 3 行」应改为「高度封顶 + 计数」】

原写法的三个问题：
1. **「行」依赖宽度**：1440px 一行可容 8 个胶囊，390px 只能容 2 个 —— 固定 3 行在移动端等于 6 个标签、桌面端等于 24 个，语义漂移。
2. **与「垂直滚动」矛盾**：若固定 3 行且内容超出走垂直滚动，那第 4 行永远看不到（要么 3 行是"上限"要么是"窗口"，不能兼得）；原需求实际想要的是「**窗口**」，即最多显示 3 行高度，超出滚动。
3. 侧栏本身在滚动容器里，块内再套垂直滚动会出现**滚动陷落**（滚轮在块内滚完才传出去，移动端尤其糟）。

**建议改为三选一（原型里给方案 A）**：

| 方案 | 行为 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A（推荐）** | 默认显示**最多 2 行**高度（`max-height: 2 行`，超出隐藏），底部一行「+N 更多 / 查看全部」按钮 → 打开列表浮层（F5） | 无块内滚动、不抢滚动条、有明确出口；与「列表弹窗」职责自然分工 | 快看全貌需一次点击 |
| B | **单行水平横滚**（chips 横向 overflow-x，隐藏滚动条，两端渐隐遮罩） | 视觉最轻、深色播放器上观感好、移动端天然适用 | 桌面鼠标横滚不如竖滚直觉 |
| C | 保留「高度封顶 + 垂直滚动」，但仅在**列表浮层**内允许滚动 | 满足原需求原意 | 详情块仍是滚动陷落 |

#### 3.4.2 【修正建议 2 ——「循环开关」与「跳转」语义冲突，必须拆开】

原需求：「片段标签为循环开关（首次点击从头循环，第二次取消）」。问题：
- **第二次点击的意图歧义**：用户看了一遍，想再看一遍，会再点一次 —— 此刻他会得到「取消循环」，与预期相反。这是**高频误操作**，不是一个边角情况。
- **状态残留不明确**：循环中切到另一个视频再回来，还在循环吗？切换到别的标签呢？（隐含需要「同一时刻至多一个循环片段」的互斥规则，原需求未定义。）
- **全景 HLS 的循环精度**：HLS 分片 seek 有 1–2 秒量级的偏差，循环点会「漂移」，用户会感知为"循环得不干净"（见 §7 B-04）。

**建议改为三个独立语义**：

| 操作 | 行为 |
| --- | --- |
| 单击标签（任何态下） | **跳转定位**：`point` 跳到 `start_ms` 暂停；`clip` 跳到 `start_ms` 并**播放到 `end_ms` 自动暂停一次**（"看一遍"，不循环） |
| 片段标签上的**独立循环按钮**（hover/选中时出现的 ⟳ 图标，或标签尾部的固定小图标） | 开启/关闭该片段的循环；开启时标签有明确选中态（主色底 + 播放中动效），**全局互斥**（开新的自动关旧的） |
| 再次单击已选中的片段标签 | 重复"看一遍"（不取消、不意外） |

这样「取消」有了专用出口，误操作面消失。

#### 3.4.3 其他交互细节（【澄清】）

- **悬停浮层内容**：标题 + 类型 + 时间（点：`00:32`；片段：`00:32 – 00:47，共 15 秒`）+ 全景视频附「视角 132° / FOV 78」+ 描述（最多 3 行，超出省略）。**移动端无 hover**，改为长按 400ms 弹出同一浮层（或直接进编辑弹窗，二选一，建议长按弹浮层）。
- **删除态二次确认的开关位置【修正建议】**：原需求写「可在设置中统一关闭」。建议**反向**：确认弹窗内提供「以后不再询问」勾选（勾了才持久化到 `ui-prefs`）。理由：设置页的全局开关是"一次性永久解除保护"，用户点错一次就永久失去保护且想不起来去哪儿恢复；弹窗内的勾选是"当时当刻"的决策，符合直觉。并且**该开关只作用于回忆标签删除**，视频删除、账号操作等危险操作不受影响。
- **`ui-prefs` 写入【强制】**：`PUT /user/ui-prefs` 是**整行替换语义**（`views/spaces/useSpacesPage.js:29` 注释：「缺键会清回其他模块默认」）→ 写入前**必须先 `GET` 全量副本再合并写回**，否则会清掉其它模块的偏好。（这是项目已知坑，落地时必须遵守。）
- **空态**：无标签时显示一行引导文案 + 「添加回忆」按钮；总开关关闭时整块不渲染（不是显示空态）。
- **加载态**：回忆块**懒加载**（独立端点，不阻塞 media 详情首屏，见 §10 性能）。

### F5 列表浮层

【保留】+ 三处补充：

### F6 搜索

**原需求**：相册顶栏统一搜索支持标题与描述的模糊匹配，结果条目前置回忆点/回忆片段图标，点击后跳转视频并定位到对应时间点。

**【澄清】与现有搜索的合并方式**：现状 `GET /search` 的匹配对象是 `media.filename` / `media.place` / `media.folder_path` + 标签名，方式是 `ILIKE '%..%' OR similarity() >= 0.15`。回忆标签的加入有两条路：

| 方案 | 做法 | 影响 |
| --- | --- | --- |
| A（推荐） | 现有 `/search` 增加第二个结果集：命中回忆标签的**条目**（而非媒体），并集返回 | 改动小；但结果列表里会同时出现「媒体」与「回忆条目」两种对象，前端要按类型渲染 |
| B | 回忆标签命中时，把所属**媒体**提到结果里并加角标 | 结果对象单一；但「点击定位到时间点」需要额外携带定位参数 |

**建议 A**：回忆条目带 `{moment_id, media_id, title, kind, start_ms, thumb_url}`，前端渲染时前置类型图标（点：◎ 圆形靶点；片段：▭ 带区间的圆角矩形），点击 → `router.push({name:'player', params:{id: media_id}, query:{ t: start_ms, ...}})`。

**【关键依赖 —— 路由定位参数现在不存在，必须新增】** `PlayerView.vue` 目前**不读任何 query 参数**，普通视频连 `currentTime` 都没有监听。定位跳转需要新增：
1. 路由 query 契约：`?t=<ms>`（点位）+ `?m=<moment_id>`（由 id 反查视角，避免 URL 携带 lon/lat/fov 造成参数污染与伪造）。
2. `PlayerView` 在媒体加载完成后读取并执行 seek（对 360 还要在引擎 ready 后恢复视角）。
3. **深链可用性**：接受该 URL 的用户可能未登录 / 无权限 → 走既有 404 语义（不是 403，按项目授权纪律）。

**排序【澄清】**：建议回忆条目**不参与**媒体的相关性排序，而是单独成组（「视频回忆」分组置顶或置底二级分组）。理由：命中即精确（用户搜的是标签文字），不需要相似度排序；混排会让媒体结果被淹没。

### F7 标签管理模块

**原需求**：支持「全部/AI 标签/手工标签/回忆标签」切换与按分类搜索。

**【澄清 + 修正】「回忆标签」不是 `tags` 表的一类**，它是独立实体（`video_moments`）。若 UI 上把它做成第四个平级 tab，用户会以为它和「AI 标签/手工标签」同一体系，随后在别处（分享勾选、搜索）产生概念错乱。

**建议**：tab 文案改为 **「全部 / 标签（AI） / 标签（手工） / 视频回忆」**，且「视频回忆」tab 内明确是**独立视图**：
- 视图形态建议：**按标签名聚合列表** —— 每个名字一行（如「女儿第一次走路 ×3」），展开显示出现该名字的视频与时间点，行内可跳转。
- 保留「按分类搜索」能力：回忆 tab 内的搜索框匹配 `title` / `description`。

现状参考：`views/TagsView.vue` 目前无 tab（现有是标签云 + 待确认角标，靠 `t.kind==='ai' && !t.confirmed` 加 `.ai` 类与「待」角标区分）—— 所以四个 tab 是**新增**，且要兼顾现有 `.ai` 视觉语言的一致性。

### F8 分享勾选与同源复用

**原需求**：视频分享可勾选分享部分回忆标签（观看人只读、仅可跳转）；相册分享可选择全部或部分；其他账号观看时，若其名下存在源文件完全相同的视频，可选择将分享的标签全部或部分应用到自己的视频。

#### 3.8.1 分享配置的数据模型

现状：`share_links`（`migrations/00008_ddl_part.sql:8`）字段为 id/token/kind/target_id/owner_id/title/expire_at/password_hash/allow_download/is_wechat/max_views/access_count/created_at —— **没有承载"选中了哪些回忆标签"的位置**。

**建议扩展（二选一，推荐 a）**：

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| **a（推荐）** | `share_links` 新增列 `moment_scope JSONB NOT NULL DEFAULT '{"mode":"none"}'`；结构 `{"mode":"none"\|"all"\|"selected","ids":[uuid,...]}` | 单列搞定、不动外键图、创建分享是低频操作无需 JOIN 反查；标签被删后 ids 里的死 id 在读取时静默过滤即可 |
| b | 新建 `share_link_moments(share_link_id, moment_id)` | 规范化、可反查"某标签被哪些分享包含"；但增加级联维护面（标签删除、分享删除、分享续期）且此反查无实际产品需求 |

**语义**：「分享出去的是引用，不是快照」—— 分享页展示的是**分享主的当前数据**。属主事后编辑标题/描述，观看者看到更新后的内容；属主删除标签，观看者少一个（符合直觉，且避免了"快照同步"的复杂度）。

**相册分享的复杂度【澄清 —— 原需求未覆盖】** 相册含 N 个视频、每个视频 M 个标签，逐个勾选是 N×M 的界面灾难。建议**三级简化**：
1. `不包含回忆标签`（默认）
2. `全部包含`
3. `自定义` → 展开「按视频选择」（每个视频一行，行级三态：不含 / 全部 / 部分），仅在选「部分」时下钻到标签级复选框。

**观看页行为**：只读。标签可点击跳转（当前时间点 + 全景视角）；**不显示**编辑/删除/循环按钮；hover/长按浮层显示描述与时间。开关关闭（F1）后，已有分享链接**仍展示**其勾选内容（历史契约不追溯破坏），但新建分享时不再出现该勾选项。

#### 3.8.2 同源复用

**入口**：分享观看页（**需登录态**才能发起；匿名访问只读，不显示复用入口）。

**判定**：`media.hash`（sha256）相等 —— 「源文件完全相同」= 字节级相同，正是 sha256 的语义。**必须服务端强制校验**（不能只靠前端比对），且要明确：
- 转码产物 / 重新导出的视频 hash 不同 → **不算同源**（这是有意的严格性：时间轴坐标系只有在字节相同时才必然对齐）。
- 同一账号内的同 hash 副本也适用（虽然少见，但逻辑上一致）。

**流程**：观看页顶部提示条（「你也有这个视频 · 复用标注」）→ 复用浮层（复用浮层的清单复用 F5 的列表组件，带复选框）→ 勾选（默认全选）→ 「应用到我的视频」→ 服务端写入（`origin` 保留原值 + 标记 `imported_from` 便于溯源）→ 跳转到自己的视频详情页。

**【澄清 —— 原需求未定义的三种情况】**：

| 情况 | 建议行为 |
| --- | --- |
| 目标视频已存在同名同时刻标签（重复导入） | 按 `(media_id, start_ms, title)` 去重，跳过并在结果里提示「已跳过 N 个重复项」 |
| 源标签时间点超出目标视频时长（理论上同 hash 则时长必然相同，但要防御） | 跳过该条 + 提示（不写入越界数据） |
| 目标视频已达 50 条上限 | 提前拦截，提示剩余可用槽位（如「仅可导入前 12 条，已达上限」） |

**「完全隔离」与「复用」的关系再强调**：复用是一次性复制。复制完成后两端**不再有任何联动** —— 源方后续编辑不影响已复制的数据。（这是 §3.2 隔离约束的具体体现，也是实现上最省的方案。）

### F9 AI 自动打点

见 §8 专章（选型对比 + 分层方案 + 成本控制）。此处只列产品行为：

- 产出的候选条目 `origin='ai'`、`ai_confirmed=false`，在详情块与列表浮层中**视觉区别于手工标签**（比照 `media_tags` 的「待」角标范式），并提供**逐条采纳/忽略**与**批量采纳**。
- 采纳后 → `ai_confirmed=true`（保留 `origin='ai'` 供 F7 的「AI 标签」分类）；忽略 → 删除该候选（或标记 `dismissed` 防重复生成，建议后者：否则下次扫描会重新生成同一个误报）。
- AI 任务状态对用户可见：设置页 AI 卡片显示「队列中 / 分析中 / 今日已用 N/M 配额 / 上次运行时间 / 失败原因」；详情页显示该视频的 AI 分析状态（未分析 / 分析中 / 已完成 / 失败可重试）。
- **AI 只提议，不直接写入用户可见的正式标签**（默认必须确认）。是否提供「自动采纳高置信度（如 ≥0.9）」的开关 → 待裁决（§12 Q-5，建议二期不做，先观察准确率）。

## 4. 数据模型

### 4.1 新表 `video_moments`（建议迁移编号 00048，实装时以实际链尾为准）

```sql
CREATE TYPE moment_kind AS ENUM ('point', 'clip');
CREATE TYPE moment_origin AS ENUM ('user', 'ai', 'heuristic', 'imported');

CREATE TABLE video_moments (
    id            UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    media_id      UUID NOT NULL REFERENCES media(id) ON DELETE CASCADE,
    owner_id      UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,  -- 创建者（隔离依据）
    kind          moment_kind   NOT NULL,
    start_ms      BIGINT        NOT NULL CHECK (start_ms >= 0),
    end_ms        BIGINT        CHECK (end_ms IS NULL OR end_ms > start_ms),
    title         TEXT          NOT NULL,
    description   TEXT          NOT NULL DEFAULT '',
    pano_lon      REAL,          -- 仅 is_360；[-180,180]
    pano_lat      REAL,          -- 仅 is_360；[-90,90]
    pano_fov      REAL,          -- 仅 is_360；[45,100]
    origin        moment_origin NOT NULL DEFAULT 'user',
    ai_confidence REAL,          -- 仅 origin='ai'
    ai_state      TEXT,          -- 仅 origin='ai'：pending(待确认) | accepted | dismissed
    imported_from UUID,          -- 同源复用时的源标签 id（仅溯源，无外键约束，源可能已删）
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 约束：kind 与 end_ms 的一致性
ALTER TABLE video_moments ADD CONSTRAINT vm_clip_needs_end
  CHECK ((kind = 'clip' AND end_ms IS NOT NULL) OR (kind = 'point' AND end_ms IS NULL));
-- 约束：非全景视频不得携带视角字段（全景判定见应用层，DB 侧只保证三字段同生同灭）
ALTER TABLE video_moments ADD CONSTRAINT vm_pano_fields_all_or_none
  CHECK ((pano_lon IS NULL AND pano_lat IS NULL AND pano_fov IS NULL)
      OR (pano_lon IS NOT NULL AND pano_lat IS NOT NULL AND pano_fov IS NOT NULL));

-- 索引
CREATE INDEX idx_vm_media    ON video_moments (media_id, start_ms);      -- 详情页/播放列表取数（主查询）
CREATE INDEX idx_vm_owner    ON video_moments (owner_id, created_at DESC); -- 标签管理页聚合
CREATE INDEX idx_vm_ai_待确认 ON video_moments (media_id) WHERE origin = 'ai' AND ai_state = 'pending';
-- 搜索：标题/描述的关键词检索。与现有媒体检索的 ILIKE 范式对齐，索引方案二选一：
--   (a) pg_trgm GIN：CREATE INDEX ... USING gin (title gin_trgm_ops)；需确认 pg_trgm 已启用（现有搜索用 similarity()，应已启用）
--   (b) 若后续接全文检索，再上 tsvector 生成列
```

**设计决策与理由**：

1. **不复用 `memories` 表**（决策 3）。理由：该表是「生成一段回忆影片」的合成任务载体（有 `criteria JSONB` 与 `video_asset_path`），与「时间轴打点」字段零重叠；且 Go 侧零引用，改动它等于给一个语义错误的表续命。保留其现状（未来若做"回忆影片合成"再用）。
2. **`owner_id` 冗余存放**（决策）。虽然可以从 `media` JOIN 出来，但：① 隔离查询（`WHERE owner_id = $me`）不需要 JOIN；② 标签的可见性应跟"谁创建"绑定而非"media 归谁"（共享空间场景下二者不同）；③ 与 `media_tags` 的归属风格一致（该表也是逐图态挂在关联表上）。
3. **时间用毫秒 BIGINT**（决策）。`media.duration` 是**秒**（INTEGER），精度不足（帧级定位需要毫秒；且片段最短 500ms 无法用秒表达）。写入校验时换算：`start_ms <= duration * 1000`。
4. **`ai_state` 与 `origin` 分离**（决策）。`origin` 记录"从哪来"（永久），`ai_state` 记录"当前处置"（可变）。这样 F7 的「AI 标签」分类可以展示"AI 提议且已采纳"的条目，而误报可以通过 `dismissed` 而不复现（同时保留记录用于评估 AI 准确率）。
5. **`imported_from` 无外键**（决策）。源标签可能被删除，不应阻塞。仅用于溯源与展示「复制自他人分享」。
6. **不加 `space` 列**（决策）。可见性由 `media` 的 `space` + `owner_id` 通过 `mediascope` 推导，避免双份状态不一致（这是项目可见性唯一真源的纪律）。

### 4.3 AI 任务与配额（若做 F9）

两个可选存储形态：
- **轻量（推荐）**：复用现有队列 + 在 `video_moments` 之外新增一张小表 `ai_moment_jobs`（media_id / state / attempts / error / started_at / finished_at）+ 一张单行配额表（或直接用 `app_settings` 存当日的计数与日期）。
- **重量**：复用 `index_jobs` / `transcode_jobs` 表结构。不建议 —— 那两个表的语义是媒体处理流水线，AI 打点是"增值分析"，混入会让流水线状态机变复杂。

**配额模型**：单日任务数配额（默认 20 个视频/日）+ 单视频候选点上限（默认 8 个）+ 全局并发 1（串行，避免与转码争资源）。配额在设置页可调，0 = 不限制（谨慎，需二次确认）。

**状态字段**：`blockState: 'browse' | 'edit' | 'del'`（组件内 ref，不持久化）。切换时**清空上态的选择**（如从 del 切到 edit，已勾选的删除项作废）。

**全局互斥的"当前选中标签"**：同时只允许一个标签处于选中（用于循环播放与高亮）；切换视频/退出详情页时清空。

### 5.2 添加/编辑弹窗状态机

```
closed ──点「添加回忆」/ 点某标签的 ✎──> open(create | edit)
  open 内：
    kind 切换 point <-> clip（保留已填内容，end 清空/回填）
    [取当前进度] → 读播放器 currentTime → 按 kind 填入 start 或 (start=当前, end=当前+10s)
    [取当前视角] →（仅 pano）读 lon/lat/fov → clamp 后填入
    时间输入合法且视频播放中 → 暂停 + seek
    提交 → 校验 → OK: 写入 + 关闭 + 刷新块 + 若 kind=clip 询问「立即播放这一段？」（可选增强）
              → NG: 字段级红字（不关弹窗，不清内容）
    Esc / 点遮罩 / 取消 → 若有未保存修改 → 二次确认「放弃修改？」
```

### 5.3 播放器联动契约（新增，三端一致）

| 能力 | 普通视频（`video`） | 全景视频（`pano`） |
| --- | --- | --- |
| 读当前进度 | **新增**：`timeupdate` 监听（现状**完全没有**，`plainVideoRef` 是 PlayerView 自持 DOM ref） | 已有：`usePanoStream` 的 `timeupdate` 写 `progressValue`(0–1000)/`timeText` |
| 命令 seek | **新增**：`video.currentTime = ms/1000` | 已有底层能力（HLS/原片），需暴露统一命令入口 |
| 读视角 | — | **新增**：`360Player` expose `getView() → {lon, lat, fov}` |
| 恢复视角 | — | **新增**：命令入口，恢复时 `lon` 归一化、`fov` clamp 到 [45,100] |
| 片段循环 | **新增**：`timeupdate` 判定越过 `end_ms` → seek 回 `start_ms` | **新增**：同上；精度受 HLS 分片限制（±1–2s，需在 UI 提示） |
| 精度说明 | 毫秒级 seek（原片） | 原片回退模式毫秒级；HLS 模式 ±1–2s |

**循环播放的实现要点**：判定用 `currentTime >= end_ms/1000 - epsilon`（epsilon 取 0.15s，避免 HLS 关键帧回退造成的死循环）；循环开启时**禁止拖动进度条到区间外**？——不必禁止（用户可能想跳走），但要定义：拖出去 = 自动关闭循环（更简单直观，建议采用）。

### 5.4 分享页交互（只读）

- 回忆标签以**与详情页同构的胶囊**呈现（视觉一致降低学习成本），但：无编辑/删除/循环按钮，单击 = 跳转。
- 视频未播放时点击 → 开始播放并从该点起播（分享页的默认行为要明确：**允许从标签起播**，这与自动播放策略的兼容性需实测——移动端浏览器可能阻止带声音的自动播放；降级为「先 seek 到该点，显示播放按钮」）。
- **同源复用提示条**：仅登录且检测到同 hash 时出现（检测接口见 §6.3）。

## 6. 隔离 / 权限 / 接口

### 6.1 隔离（唯一真源 mediascope）

所有读写路径必须走 `internal/mediascope`，**不新建权限体系**：
- 列表/详情：`ReadCond(start, userID, role, alias)` 参与查询（或先取 media 再用 `VisibleCond` 判定），无权限 → **404 非 403**（文案同形，按项目授权纪律）。
- 创建：目标 `media_id` 必须先通过读权限校验，再落 `owner_id = 当前用户`。
- 更新/删除：仅 `owner_id = 当前用户` 或（共享空间管理者，待裁决 Q-3）。
- **FailClosed**：作用域缺省必须拒绝，不允许"未传 space 即视为可见"。

### 6.2 服务端接口草案（路由命名对齐现有风格，无 `/api/v1` 前缀）

| 方法 | 路径 | 说明 | 权限 |
| --- | --- | --- | --- |
| GET | `/media/:id/moments` | 该视频的回忆标签列表（含未确认 AI 条目，带 `ai_state`） | media 读权限 |
| POST | `/media/:id/moments` | 新建 | media 读权限（归属落 current user） |
| PATCH | `/moments/:momentId` | 编辑（部分字段） | 创建者 |
| DELETE | `/moments/:momentId` | 删除 | 创建者 |
| POST | `/media/:id/moments/import` | 同源复用导入（body: `{source: {share_token} \| {media_id}, ids?: [...]}`） | 目标 media 编辑权 + 服务端 hash 校验 |
| POST | `/media/:id/moments/ai-scan` | 触发 AI 分析（手动触发） | media 编辑权 + 总开关开启 + 配额 |

### 6.3 搜索集成

- 命中集：`title ILIKE '%q%' OR description ILIKE '%q%'`（与现有 `similarity() >= 0.15` 的模糊范式是否叠加 → 建议**不叠加**，回忆标签文字短、ILIKE 已足够，且避免 trigram 索引外的额外开销；若实测召回不足再加）。

- 前端 `SearchResultsView` 新增「视频回忆」分组（或类型徽标），点击 → 路由 query 定位（见 F6）。

## 7. 边界与异常处理矩阵

| 编号 | 场景 | 期望行为 |
| --- | --- | --- |
| B-01 | 视频时长未知（`media.duration IS NULL`，尚未探测） | 禁止添加（前端禁用按钮 + 提示「视频元数据未就绪」，后端 422）；AI 任务不排队 |
| B-02 | 添加的时间点 > 视频时长 | 422 + 字段红字（给出合法范围） |
| B-03 | 片段 `end <= start` 或差 < 500ms | 422 + 前端阻止（输入时就地提示） |
| B-04 | 片段循环在 HLS 模式下的精度漂移 | UI 明示「循环边界受转码分片限制，约 ±1–2 秒」；原片回退模式无此限制 |
| B-05 | 视频正在转码 / HLS 未就绪 | 回忆标签**仍可管理**（数据与播放解耦）；跳转走原片（若可播）或提示「转码完成后可精确跳转」 |
| B-06 | 并发编辑同一条标签 | last-write-wins；`updated_at` 变化可用于前端刷新（本期不做乐观锁，明示为已知取舍） |
| B-07 | AI 上游不可用 / 超时 | 任务标 `failed` + 错误摘要可见 + 可重试；不影响手工功能与已有数据 |
| B-08 | AI 返回非法结构（越界时间、超长标题、非法 JSON） | 逐条丢弃 + 记审计告警；不写入半成品 |
| B-09 | 总开关关闭后，历史分享链接里的回忆标签 | **仍可见**（不追溯破坏历史契约）；仅新建分享不再提供勾选 |
| B-10 | 分享链接过期 / 密码错 / 超次数 | `/public/shares/:token/moments` 复用现有 `checkAccess` 语义（EXPIRED / MAX_VIEWS / PASSWORD_REQUIRED / WRONG_PASSWORD → 403） |
| B-11 | 标签被删除后，分享链接的 `moment_scope.ids` 含死 id | 读取时静默过滤（不 500） |
| B-12 | 视频被删除 | `ON DELETE CASCADE` 清空标签（含 AI 候选与 job 记录） |
| B-13 | 同源复用：目标已达 50 上限 | 提前拦截并给出剩余槽位；不部分写入（原子） |
| B-14 | 同源复用：重复条目 | 按 `(media_id, start_ms, title)` 去重跳过 + 结果摘要提示 |
| B-15 | 同源复用：hash 相同但时长不同（异常数据） | 逐条校验 `start_ms <= 目标时长*1000`，越界跳过 |
| B-16 | 用户未登录打开分享页 | 只读展示；**不显示**同源复用入口（需要身份） |
| B-17 | 深链 `?t=xx` 指向无权限媒体 | 404（与现有拖链接行为一致） |
| B-18 | 全景视角历史数据越界（人工改库/迁移脏数据） | 读取时 clamp（lon 归一化、fov 夹取），不报错 |
| B-19 | 单视频标签数达 50 | 409 `LIMIT_EXCEEDED` + 明确文案 |
| B-20 | AI 候选被忽略后又想采纳 | `dismissed` 条目在列表浮层「已忽略」分组内可恢复（不做硬删） |
| B-21 | `PUT /user/ui-prefs` 部分 payload | **禁止**：前端必须先 GET 全量再合并（否则清空其它模块偏好）—— 这是项目既有坑，写进实现约束 |
| B-22 | 移动端浏览器阻止自动播放 | 分享页从标签起播时若被拒，降级为「已定位，点击播放」 |

## 8. AI 方案选型对比（重点章节）

### 8.1 问题本质

「AI 自动打点」= **从视频内容中判断"哪里值得回忆"并生成标题/描述**。这需要两件能力：
- **感知**：理解画面/声音里发生了什么（或退一步：找出"变化/异常"的位置）。
- **表述**：把发现变成人格化的中文短标题（"囡囡第一次自己走路"）。

### 8.2 三条候选路径的可行性评估

| 路径 | 感知能力 | 表述能力 | 结论 |
| --- | --- | --- | --- |
| **① 复用 Agent 语义接口 · LLM 上游** | **无**（现状）。`internal/agentllm.ProxyChat` 是**纯文本透传**（body 原样转发、4MB 上限），全仓无 vision/多模态代码。若上游模型本身支持视觉（如 qwen-vl），必须**扩展**：多模态 messages（image_url/base64）+ 抽帧器（ffmpeg）+ 拼帧策略 + 结构化输出解析 | 有 | **需扩展后可用**（L3，见 §8.3） |
| **② 单独配置专用大模型 API** | 有（专用视频理解 API 原生支持长视频/音频） | 有 | **可行但成本与运维面增加**：多一套配置/密钥/计费/审计；适合作为"可选增强"而非默认 |
| **③ 复用内置人脸识别 AI 模块** | **不具备所需能力** | **无** | **不可行**。核实结论：① 人脸管线（YuNet+SFace）做的事是「检测人脸位置 + 提 128 维特征 + 聚类出人」，输出是"谁"，不是"发生了什么"；② 执行模型是**清扫式单帧**（`cmd/facesgen` 通过 `faces_scanned_at` 标记处理，`ListPending` 只取 LG 缩略图或原图**单帧**），**无视频时序分析能力**；③ 时间轴打点必须有时序能力（哪些时刻画面/声音发生了变化）。**它能提供的最多是"该视频第 X 秒画面里有人脸"这一弱信号**，不能作为自动打点的主方案 |

**关于 ③ 的补充说明（为什么写"评估复用"在 UI 上会误导）**：人脸模块的真正可复用点是它**已经在本机跑推理**（不需要外网、零 token 成本）。这个"零成本本地推理"的价值可以保留 —— 但要用在**本地启发式**（L1，见下），而不是人脸聚类本身。

### 8.3 推荐方案：分层降级 L0–L3

| 层 | 名称 | 技术手段 | 成本 | 产出质量 | 二期建议 |
| --- | --- | --- | --- | --- | --- |
| **L0** | 无 AI 基线 | 纯手工打点 | 0 | 取决于用户 | **必做**（功能主体，AI 是加速器不是前提） |
| **L1** | 本地启发式候选点 | ① **音频能量分析**（ffmpeg 提音频 → 音量包络 → 峰值/突变检测：笑声、欢呼、掌声、音乐起）② **场景切换检测**（ffmpeg scene 滤镜：画面切换密集处）③ **GPS 轨迹变化**（复用 v1.8.x 已有的视频 GPS 提取能力：移动/停留切换点）④ 时长分布（跳过片头片尾的静默段） | **0 token**（纯 CPU/ffmpeg） | 中——"候选位置"准，但无标题 | **做**。产出 `origin='heuristic'` 的**候选点**（不是成品标签），用户在列表浮层一键"采纳为回忆点" |
| **L2** | LLM 文本编排（**推荐主路径**） | 输入：L1 候选点的特征向量（时间点 + 音频峰值 + 场景变化密度 + GPS 变化 + 文件名 + 拍摄地点 + 日期）+ 该视频已有的 AI 人物标签；输出：结构化 JSON（每条：title / description）；**纯文本调用，复用现有 `/agent/llm/v1` 代理 + `agent_llm_config`** | 低——每视频一次调用，约 1–3k token | 好——标题/描述可用，是"回忆"最有价值的部分 | **做**。这是"AI 自动标签"的**主要交付形态** |
| **L3** | 多模态抽帧理解 | ffmpeg 按 L1 候选点/N 秒间隔抽关键帧 → 缩放至 448–720p JPEG → base64 → vision 模型 → "这段在做什么" → 结构化输出 | **高**——每帧约 1k token；1 分钟视频抽 6 帧 ≈ 6k token；100 个视频即 60 万 token | 最好 | **二期不做**，列为远期可选。若做：必须配**硬配额 + 单日上限 + 单视频上限**，且默认关闭 |

**为什么 L2 是推荐主路径**：
1. **不引入 vision 依赖** —— 不改 `agentllm` 的透传契约，复用已有配置/代理/审计，改动面最小。
2. **成本可控** —— 每视频一次调用，且输入是"特征摘要"而非图像，token 量小且恒定。
3. **质量足够** —— 用户在这个场景里要的是"帮我命名 + 帮我把候选排序"，而不是"帮我看见"。位置由 L1 给（数学问题），表述由 L2 给（语言问题）——**分工正好落在各自最擅长的域**。
4. **可解释** —— 每条候选可显示"为什么提议这里"（音频峰值/场景切换），用户对误报的容忍度会显著提高。

**L1 的具体算法草案**（实装前需在 115 上用真实样本校准阈值）：

```
输入：视频文件（或代理流）
步骤 1  音频：ffmpeg -i in.mp4 -vn -ac 1 -ar 8000 -f wav → 按 0.5s 窗计算 RMS 包络
步骤 2  峰值：对包络做 z-score 平滑，取局部极大且 z > 2.0 的点，做最小间隔合并（≥15s）
步骤 3  场景：ffmpeg -i in.mp4 -vf "select='gt(scene,0.35)',showinfo" → 收集切换时间戳
步骤 4  融合：候选 = 音频峰值 ∪ 场景切换密集簇 ∪ GPS 停留→移动的切换点
步骤 5  排序与裁剪：按 K 值（默认 8）取分数最高的候选；剔除片头 3% / 片尾 5% 内的点
输出：[{t_ms, score, reasons:["audio_peak","scene_cut"]}, ...]
```

**注意**：L1 的输入解码与转码 worker 争资源 —— 必须走队列、限并发 1、优先在生效时段跑（F1）。

### 8.4 成本与配额控制（无论做哪层都必须有）

| 控制项 | 默认值 | 说明 |
| --- | --- | --- |
| 单日 AI 任务视频数 | 20 | 达到后排队到次日（而非报错） |
| 单视频候选点上限 | 8 | 防"AI 把整片标满" |
| 全局并发 | 1 | 与转码/索引 worker 错峰，避免 CPU 打满（v1.9.x 教训） |
| 单次调用 token 上限 | 4k（输入+输出） | 超出截断（L2） |
| 生效时段 | 02:00–06:00 | F1 配置 |
| 失败重试 | 2 次 | 间隔递增；仍失败标 failed |

**token 成本量级（L2）**：100 个视频 × 2k token ≈ 20 万 token。按项目 1.62 倍率 ≈ 32 万当量 —— 可接受，但要计入二期 token 预算（见 §11）。
