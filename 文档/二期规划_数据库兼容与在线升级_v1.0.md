## 2. R-A：数据库兼容升级（老数据继承）

### 2.1 风险模型

老版本数据不能被继承，只有三种成因：

| 风险类型 | 机理 | 典型 SQL |
|---|---|---|
| **数据丢失** | 迁移直接删列/删表 | `DROP COLUMN`、`DROP TABLE`、`TRUNCATE` |
| **数据变形** | 列类型收窄、约束收紧导致旧值写不回去 | `ALTER COLUMN ... TYPE`（缩小）、`SET NOT NULL`（旧行为 NULL） |
| **版本撕裂** | 新 schema + 旧代码，或反之，跑在不兼容的中间态 | 迁移已应用但镜像回滚了 |

### 2.2 强制规则（每次发版必须满足）

| # | 规则 | 判定方式 |
|---|---|---|
| **A1** | 迁移**只增不删**：新增列必须 `nullable` 或带 `DEFAULT` | 静态分析 |
| **A2** | 禁止 `DROP COLUMN` / `DROP TABLE` / `TRUNCATE` / `RENAME COLUMN` | 静态分析（破坏性 → 直接 FAIL） |
| **A3** | 列类型只允许**扩大**（`varchar(50)`→`varchar(200)`✅；反向 ❌） | 静态分析 |
| **A4** | 破坏性变更必须**两段式**：本期「加新列 + 双写」，下个版本才「删旧列」 | 人工评审 + 检查工具提示 |
| **A5** | 每个迁移头部须声明 `-- +goose Up` 之外的元信息：**`-- min-app-version: x.y.z`**（可运行的最低应用版本） | 静态分析 |
| **A6** | 迁移前**自动备份**：`pg_dump` → `data/backups/pre-migration-<version>/` | 部署流程强制 |
| **A7** | 低版本 api 遇到高版本 schema 必须 **fail-closed 拒绝启动**，而非报错崩溃或半可用 | 代码约定 + 契约测试 |

### 2.3 A7 的具体做法（当前缺失，必须补）

新增 `schema_compat` 表记录已应用的最大 schema 版本与最低应用版本：

```sql
CREATE TABLE schema_compat (
  id             smallint PRIMARY KEY DEFAULT 1 CHECK (id = 1),
  schema_version bigint  NOT NULL,          -- 已应用的最大迁移序号
  min_app_version text    NOT NULL,          -- 这些迁移要求的应用最低版本
  applied_at     timestamptz NOT NULL DEFAULT now()
);
```

api 启动时：
- 读 `schema_version` 与自身 `version.Version` 比较
- 若 `min_app_version > 当前版本` → **拒绝启动并打印明确原因**（而不是让用户撞运行时错误）
- 这与现有 fail-closed 一致，只是把「迁移失败」扩展到「版本不兼容」

### 2.4 回滚策略（明确取舍）

**goose `down` 不作为常规回滚手段**——DDL 回滚极易丢数据。改为：

| 场景 | 处置 |
|---|---|
| 迁移失败（未完成） | goose 事务回滚 + 恢复 `pg_dump` 备份 |
| 迁移完成但应用有问题 | **回滚镜像**（schema 向前兼容是 A1/A3 的目的，旧代码能跑新 schema） |
| 必须回退 schema | 人工介入 + 备份恢复，**走runbook，不自动化** |

> 这条取舍正是 A1/A3 的价值：只要迁移是纯加法，**回滚应用就等于回滚一切**，不需要动数据库。

## 3. R-B：构建文件变更提醒

### 3.1 为什么必须有

本项目刚在 2026-10-09 遇到实例：为了让 api 镜像能构建，运维不得不修改 `docker/api/Dockerfile`
（合并 cache mount 分层 + 加 `go clean -modcache`）。**如果这是用户从 v1.9.3 升到 v1.9.4，
用户不手动改这个文件就会构建失败或行为异常**——而升级界面若不提示，用户根本不会知道。

### 3.2 规则

| # | 规则 |
|---|---|
| **B1** | 每次发版记录**构建文件指纹**：`docker-compose.yml`、`docker/*.Dockerfile`、`.env.example` 的 sha256 |
| **B2** | 升级时对比「当前版本 vs 目标版本」的构建文件指纹，**有差异必须在升级前显式提示** |
| **B3** | 提示**分级**：<br>🔴 **高危** —— `docker-compose.yml` / `Dockerfile` 变了（可能需手工改配置、端口、卷）<br>🟡 **注意** —— `.env.example` 新增了变量（可能需补配置）<br>🟢 **常规** —— 仅版本号变化 |
| **B4** | 提示内容必须含**逐文件摘要**：文件名 + 变更类型 + 关键行 diff（不贴全文，指向 Release Notes） |

## 4. 本期交付的工具（对应 R-A / R-B）

`scripts/release_compat_check.py` —— 并入发版链，与 `release_consistency_check.py` 同级。

### 4.1 用法

```bash
# 发版前：检查迁移兼容性 + 构建文件变化
python scripts/release_compat_check.py --version 1.9.5 --diff-from v1.9.4

# 只查迁移（快速）
python scripts/release_compat_check.py --migrations-only

# 只查构建文件变化
python scripts/release_compat_check.py --build-files-only --diff-from v1.9.4
```

### 4.2 输出（19+ 项断言，机器可读）

```

[PASS] 新增列均为 nullable 或带 DEFAULT
```

## 5. R-C：在线升级（Phase 2 功能规划）

### 5.1 功能目标

用户在 Web 管理界面点「检查更新」→ 看到可用版本与升级风险 → 确认后自动完成升级。
**全程可回滚，失败不砖机。**

### 5.2 版本源与文件布局

**版本信息源（按优先级探测）**：

1. `https://raw.githubusercontent.com/warlocks365/Panomint/main/update/latest.json`
2. GitHub Releases API（`repos/warlocks365/Panomint/releases/latest`）—— 私有库需 token
3. 降级：用户手动上传 `.zip` 升级包

**`update/` 目录约定（发布时随 tag 提交）**：

```
update/
  latest.json                 # 版本索引
  1.9.5/
    manifest.json             # 文件清单 + sha256 + 目标路径
    compose.yaml              # docker-compose 覆盖层
    migrations/               # 若需手工迁移（正常走 api 自迁移，此处仅留备份）
    NOTES.md                  # 升级步骤 + 已知风险 + 回滚指引
```

`latest.json` 结构：

```json
{
  "version": "1.9.5",
  "released_at": "2026-10-20T10:00:00Z",
  "min_db_schema": 47,
  "min_app_version": "1.9.0",
  "notes_url": ".../NOTES.md",
  "build_files_changed": [
    { "path": "docker/api/Dockerfile", "level": "high",
      "summary": "合并 Go cache mount 分层，修复 BuildKit 缓存损坏导致构建失败" }
  ],
  "manifest_sha256": "…"
}
```

> `build_files_changed` 是 **R-B 的数据化**：发版时由 `release_compat_check.py` 自动生成，
> 在线升级界面直接读取，无需现场 diff。**这让 R-B 在没有网络对比时依然可用。**

### 5.3 升级流程（fail-safe 七步）

| 步 | 动作 | 失败处置 |
|---|---|---|
| 1 | 拉 `latest.json`，比对本地版本 | 网络失败 → 提示并给出手动上传入口 |
| 2 | 展示：版本说明 + **构建文件变更提示（R-B）** + 数据库影响（本次新增迁移数 + 是否破坏兼容） | — |
| 3 | 用户确认。**若含破坏性变更，必须二次确认并要求勾选「我已备份」** | 用户取消 → 终止，无副作用 |
| 4 | 拉取文件，**逐个校验 sha256** | 校验失败 → 立即中止，已拉文件丢弃 |
| 5 | **自动备份数据库**（`pg_dump`） | 备份失败 → 中止升级 |
| 6 | 停旧容器 → 换镜像/ compose → 启新容器（api 启动自迁移，A6/A7 生效） | 启动失败 → **自动回滚**：旧镜像 + 恢复备份 |
| 7 | 健康检查 `/ready`（含 DB/valkey）→ 通过则完成 | 超时未就绪 → 自动回滚 |

### 5.4 安全要求

| 项 | 要求 |
|---|---|
| 传输 | 仅 HTTPS；**必须校验 sha256**；GPG 签名留二期 |
| 权限 | 入口需 `owner` / `admin`（复用项目既有 RBAC，不新造权限） |
| 审计 | 每次升级写审计日志：发起人、from→to、文件清单、结果（项目已有审计表） |
| 断点保护 | 升级中途断电 → 下次启动识别「半升级态」（schema 已变但镜像未换）并**明确提示**，不让用户以为正常 |
| 网络受限 | 内网无 GitHub 访问时降级为手动上传 zip，功能不残废 |

### 5.5 明确不做（Phase 2 边界）

- **不自动应用破坏性迁移** —— 永远要人确认（A2/A4 的意义所在）
- **不做跨大版本直升** —— 从 1.9.x 跳到 2.0 需走人工迁移流程
- **不自动回滚 schema** —— 只回滚应用，schema 向前兼容（§2.4）
- **不做 GPG 签名** —— 二期后再加

## 7. 待确认事项

| # | 事项 | 我的倾向 |
|---|---|---|
| 1 | A5 的 `min-app-version` 元信息，是**每个迁移文件都写**，还是按批次写在 `manifest`？ | 每个文件都写（迁移可能被 cherry-pick，批次信息会失真） |
