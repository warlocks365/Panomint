## 一、本版主功能：媒体元数据编辑

照片 / 视频 / 360 照片 / 360 视频的**详细信息面板**里，可以直接编辑拍摄时间、拍摄地、详细地址与 GPS —— 四类媒体共用同一入口，一次改动全覆盖。

### 两个入口

| 入口 | 路径 |
| --- | --- |
| **播放器信息面板** | 打开媒体 → 侧栏「编辑拍摄信息」 |
| **媒体卡右键 / 长按菜单** | 时间轴上右键卡片（移动端长按 600ms）→「编辑拍摄信息」 |

### 拍摄地怎么填

两条通道，都自动带坐标：

1. **地图搜索** — 输入「景山前街」等关键词，出候选列表；选中即自动填入拍摄地、详细地址、GPS
2. **地图选点** — 在地图上点选/拖动标记，取该点坐标（首次点开时才加载地图，平时零开销）

也支持纯手工填写（拍摄地、详细地址、坐标都能手输）。

### 关键约束：只改数据库，不动原媒体文件

写入只 UPDATE `media` 表 —— **不写 EXIF、不改 sidecar、不触碰 `path` 指向的 NAS 原片**。

e2e 实测证据：对一个 **1.1 GB 的视频**完成元数据保存后，`path` / `type` / `filesize` 三项完全未变。

## 二、数据模型变更（迁移 00047）

| 字段 | 变更前 | 变更后 |
| --- | --- | --- |
| `media.place` | 装的是逆地理的**完整地址**（如「北京市东城区景山前街 4 号」），`VARCHAR(128)` | 语义收敛为**短地名**（如「景山前街」），放宽到 `VARCHAR(256)` |
| `media.address` | 不存在 | **新增** `TEXT`，承载详细地址 |
| `media.gps` / `taken_at` | 已有 | **不动** |

### 历史数据搬迁

把 `place` 里的**详细地址**内容复制到 `address` 并清空 `place`；**已经正确的短地名原样保留**（如「故宫博物院」「西湖」「朝阳区」）。

判定规则：含「路/号/街/巷/弄/胡同/大道/里/村/镇」或总长 > 24 字才搬。

搬迁是**复制**不是移动 —— 判定有误时原值仍在 `address` 可找回，**无数据丢失**。

**实测**：在真实 PG 隔离 schema 上构造 7 行数据验证（3 短地名 + 3 详细地址 + 1 空）——短地名零误搬、详细地址全部正确搬迁、二次执行 `UPDATE 0`（幂等）、用户已填的 `address` 不被覆盖。线上迁移后 61 条 `place` 全部保留（测试库的 `place` 本就都是短地名）。

### ⚠️ 升级注意

- 迁移由 api 启动时自动执行（goose），失败即拒启动
- 若你现有的 `place` 是**手工填的短地名**，不会被动
- 若你现有的 `place` 是**长地址**，会被搬到 `address`，`place` 留空待重填

## 三、API 变更

### `PATCH /media/:id` 扩展（契约化）

请求白名单从 2 个字段扩到 **7 个**：新增 `taken_at` / `place` / `address` / `lat` / `lng`。

**三态语义**（调用方**只提交变化了的字段**）：

| 请求形态 | 语义 |
| --- | --- |
| 字段**缺席** | **不动** |
| `place`/`address` 为 `""` | **清空** |
| `taken_at` 为 `""` | **清空** |
| `lat`/`lng` 均为 `0` | 清空 `gps` |

> 全量提交会把未编辑但为空的字段清掉 —— 这是本端点最容易误用的一点。

**校验**：`taken_at` 只接受 RFC3339（带时区）；`lat`/`lng` **必须成对**（只给一个 → 400）；坐标越界 → 400。

### 坐标系声明头 `X-Coord-Source`（新）

库内 `media.gps` 是 WGS-84；而高德地图的搜索候选与选点返回 **GCJ-02**（偏 300~500 米）。

| 请求头 | 服务端行为 |
| --- | --- |
| `X-Coord-Source: gcj02` | 转成 WGS-84 后落库 |
| 缺省 | **假定已是 WGS-84**，原样落库 |

> 缺省不转换是刻意的：EXIF / GPS 设备给的坐标本来就是 WGS-84，再转一次是**不可逆的精度损失**。境外坐标不做转换（公式只对国内有效）。

### `GET /media/:id` 新增字段

响应增加 `address`（详细地址）。`gps` 仍为 WGS-84，与之前一致。

### 审计

新增动作 `media.metadata_edit`，**只记「改了哪些字段」，不记坐标明文**（坐标属半敏感位置数据，审计表无删除端点 = 永久留档）。

## 四、同时修复的问题

### 4.1 发版前代码审查（2 名独立审查员，各报 fail）

发版前派 2 名独立审查员做对抗性代码审查（后端 + 前端），**两份都报 fail**，
逐条验证后确认 6 个真缺陷并修复：

| # | 缺陷 | 后果 | 根因 |
| --- | --- | --- | --- |
| **1** | **短地名功能实际未上线** | `place` 与 `address` 存的是同一份完整地址 —— 直接违背「短地名取尾部地标」的裁决 | `ShortPlaceName` 写了 195 行 + 161 行测试，但**全仓零调用方**（写完没接线） |
| **2** | 软删媒体 PATCH 返回 200 但没写入 | 用户看到「已保存」，刷新就回退 | `SetMetadata` 不检查 `RowsAffected`；`ownerOf` 不过滤 `deleted_at` |
| **3** | 编辑器读 `gps.lon` 而后端发 `gps.lng` | 有 GPS 的媒体显示「没有数据」，且**可能静默清空已有 GPS** | 两处 JSON tag 键名不一致 |
| **4** | 迁移 00047 的 Down 不回填 place | 回滚会**永久丢失**详细地址 | 文件头注释写了回填语句，Down 段里却没有 |
| **5** | 菜单删除成功后卡片不消失 | 注释自称会消失，实际无消费者 | `item.__removed` 只写不读 |
| **6** | P0 R4 硬编码颜色门禁 FAIL | 4 个新组件有 31 处 `var(--token, #fallback)` | fallback 值仍算硬编码 |

**修复 1 的验证**（线上实测）：

```
place = 天安门                ← 短地名（取尾部地标）
addr  = 北京市东城区天安门      ← 详细地址
```

两者不再相同 —— 修复前它们是同一份值。

> 每个修复都配了**反向验证**：把修复代码删掉，测试必须 FAIL。
> 例如 `TestCandidatesExposeShortPlace`（真调用 `Candidates`，不是自己重映射）
> 在删掉 `ShortPlace` 赋值后立即失败 —— 证明它是真能挡住回归的测试。

### 4.2 其他已修问题

| 问题 | 根因 |
| --- | --- |
| 搜索候选缺少详细地址 | `Address` 字段在三处透传全漏（`MapCandidate` 构造、Nominatim 解析、`nominatimForwarder`） |
| 地图选点回填坐标异常 | 弹层 emit `{lat, lon}` 而接收方读 `pos.lng` → `NaN`（弹层内显示正常，肉眼无法察觉） |
| 搜索不出候选 | 同一输入框上 `v-model` 与 `@input` 并存，处理器读到旧值 |
| 越界提示被掩盖 | `lat=91/lng=0` 报「必须成对」而吞掉真正的「纬度越界」 |
| 短地名提取漏行政区 | 只剥了「北京市」，漏掉直辖市市辖区「东城区」 |
| 右键菜单完全不可用 | 「批量选择态不弹菜单」的判断有误 —— `selectable` 是**常态为真** |
| GCJ-02 坐标从未转换（偏 300~500 米） | 后端读 `coord_source`（下划线），前端发 `X-Coord-Source`（连字符），HTTP 头规范化后对不上 |
| 有 GPS 却不显示 GPS 行 | 前端读 `gps.lon`，后端 tag 是 `lng`；且该行被 `v-if` 门控 |

## 五、部署说明

### 群晖

1. Container Manager → **映像** → 重新下载 `warlocks/panomint-{app,worker,db,web}:1.9.4`
2. 项目 → **停止** → **构建/重新启动**
3. 验证：`/version` 返回 `1.9.4`；`pano-index-worker` 日志出现「worker 启动」

编排文件用本仓库 `release/docker/docker-compose.synology.yml`（tag 已是 1.9.4）。

### Docker Compose

```bash
docker compose pull
docker compose up -d
```

### 数据迁移

自动执行，无需手动操作。执行前建议备份：

```bash
docker exec pano-db pg_dump -U pano pano_album > pano_album_$(date +%Y%m%d).sql
```
