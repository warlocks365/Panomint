## 一、P0 发现（3 条，全部经 team-lead 复核属实）

### [P0-1] 相册评论端点完全无归属校验（越权残留）
- **位置**：`src/backend/internal/albums/handlers.go:273-311`（ListComments / AddComment）；`store.go:434`（查询带出作者邮箱）
- **描述**：`ListComments` 不查 `getAlbumMeta`/`canManage`，任何持 `media:read` 的账号可读**任意相册**的评论且响应带**作者邮箱**；`AddComment` 只验相册存在性，任何 `album:write` 可往**他人相册**写评论。
- **影响**：与 §二十六 已修的 `GET /albums/:id` 本体越权**同一家族的残留**——本体修了，两条 comments 子资源漏修。构成跨用户数据泄漏 + 越权写入。
- **建议**：`ListComments` 复用 `GET /albums/:id` 的归属判定（`canAccess`）；`AddComment` 加 `canManage(album, user)` 校验；`store.go:434` 的 SELECT 去掉 `users.email` 或按角色裁剪。**修复后必须派独立 worker 做对抗验证**（参照 §二十六 的 60/0/1 模式），并把"子资源路由必须过归属校验"写进守卫（类似 errtext_guard 的机械检查）。

### [P0-2] CLIP 编码器互斥锁未覆盖输入张量写入（并发结果张冠李戴）
- **位置**：`src/backend/internal/embed/clip_cgo.go:276-289`（EncodeText 写 mask 在锁外）、`:328-337`（EncodePixels `copy(dst, px)` 在锁外）；同型缺陷 `internal/faces/embed.go:108`（EmbedAligned）；共享单例证据 `cmd/api/main.go:436`
- **描述**：`e.visIn`/`e.maskIn`/`e.textIn` 是 Encoder 单例的**共享输入张量**，写入之后才 `mu.Lock()`。两个并发请求（如同时语义搜索 + 后台 embed 任务）时，A 写入输入后被 B 覆盖，A 的 `Run()` 读到 B 的输入 → 返回 B 的向量。
- **影响**：语义搜索结果在并发下**静默张冠李戴**，无任何报错。当前库 93 条几乎不触发，库一大必现。同包 `faces/detect.go:188`（先锁后写）是正确范本，证明属疏漏而非设计。
- **建议**：三处（EncodeText / EncodePixels / EmbedAligned）把 `mu.Lock()` 提到"写输入张量"**之前**，覆盖 写入+Run+读出 全段。修后补一个并发一致性测试（同一 Encoder 并发两路不同输入，断言各得其所）。

### [P0-3] faces.bbox 坐标空间随图源漂移，重扫时用户命名静默丢失
- **位置**：`src/backend/cmd/facesgen/main.go:287-364`（检出→入库全程无归一化）；`internal/faces/scan_source.go`（原图/LG 二选一）；`internal/faces/match.go`（BestFaceMatch 用 IoU≥0.5）
- **描述**：Job000032 把图源改为「原图优先、LG 回退」后，检出框 bbox 处在**所选图源的坐标系**。`SaveFace` 直接入库无归一化；命名迁移靠新旧框 IoU≥0.5。**同一媒体前后两次扫描若图源不同**（如首次只有 LG、后来原图可用了；或反之），坐标系不同 → IoU≈0 → `personID` 迁移失败 → **用户命名的人名静默丢失**。
- **影响**：潜伏性地雷——当前语料原图同为 1280 宽故未爆发；图源策略任何一次变化（或部分媒体原图缺失）即批量丢命名，且用户无感知。
- **建议**：`SaveFace` 前把 bbox 统一归一到**原图坐标系**（按 `src` 返回的缩放系数换算）；同时 `BestFaceMatch` 增加坐标系一致性断言/换算。修后用"同媒体 LG 扫 → 原图重扫"用例钉住命名保留。
