## 1. 管理界面交互设计

### 1.1 位置与样式
管理后台「转码」页签（`TranscodeTab.vue`，现有「自动 HLS 转码」开关所在卡片）内**新增第二个开关行**，样式复用现有 `.tc-row / .tc-switch` 开关行（16px 复选框 + 名称 + 动态提示 + 最近变更时间），保持同卡片视觉一致：

```
[x] 自动 HLS 转码                ← 既有（总闸门）
[ ] 播放时自动转码（实时转码）    ← 新增
    开启后：播放无 HLS 的视频时自动发起转码，完成后自动切换多档自适应流；
    转码期间普通视频先用原始文件播放，360° 视频显示转码进度。
```

### 1.2 启用提示文案（按状态切换）
- 总闸门关闭时（新开关禁用态）：「需先开启上方「自动 HLS 转码」总开关」
- 新开关开：「已开启：播放无 HLS 的视频时自动转码，多档码流按带宽自适应切换」
- 新开关关：「已关闭：保持手动发起转码（现状）」

### 1.3 持久化方式 [自行决策 D1/D2]
**数据库**（非配置文件）：`system_transcode_config` 新增列 `realtime_transcode BOOLEAN NOT NULL DEFAULT FALSE`（迁移 00040）。
理由：与既有开关同表同 upsert 语义，天然获得单行原子写、审计、管理 API 复用；配置文件会与现有「管理后台维护」心智冲突。

### 1.4 作用范围
**系统级、全站所有账号、对所有视频生效**：任何登录用户在播放器打开无 HLS 的视频（普通视频 + 360° 视频）都会触发自动转码；产物（HLS 文件 + media.hls_master）媒体级共享，转过一次全站受益。

### 1.5 与既有开关的关系 [自行决策 D1，本设计核心裁决]
**AND 关系，职责分离**：
- `auto_transcode`（既有）= **总闸门**：是否允许创建转码任务（手动+自动一律拦，409 语义、fail-closed、审计全部保留不动）；
- `realtime_transcode`（新）= **触发方式自动化**：开=播放器自动发起；关=维持现状手动按钮。

有效自动触发 = `auto_transcode AND realtime_transcode`。管理端把新开关做成「总闸门关时禁用」，避免歧义姿态；即便库中出现（关,开）组合，AND 语义也保证安全（不放行）。

候选方案对比（选 A）：
- A. 独立新字段 AND 语义（选中）：存量行为逐字节不变（新列默认 FALSE）；既有闸门安全资产全保留。
- B. 把新语义并入 auto_transcode（改造为枚举）：要迁移存量行语义、回滚复杂、一次改动动两个已验收 Job 的行为面，风险收益不成比例。
- C. 完全独立新表/新端点：与 F1 同表零收益，还多一套 upsert/审计样板。

## 2. 实时转码处理流程（开启后播放请求的完整链路）

```
播放器 load() 视频且无 hls_master
  │  ① GET /transcode/config（现取，新增 realtime_transcode 字段）
  │     有效自动触发 = auto_transcode && realtime_transcode（任一为假 → 走第 4 节回退）
  ▼
播放器自动 POST /transcode/job {media_id, auto: true}     ← [D3]
  │  ② 服务端既有全链不动：归属校验(404/403 口径不变) → 总闸门(409 语义不变)
  │  ③ 新增 attach-or-create：查该媒体最新 pending/running 任务
  │     ├─ 有 → 直接返回该 job_id（202 + job_id，幂等，防双击/多端并发重复任务）
  │     └─ 无 → 档位按 ProfileForSource(源宽,源高) 自动选取（与 CLI 补排同口径）[D4]
  │           → enqueueOne 写行+入队（回滚语义不变）
  ▼
前端轮询 GET /transcode/job/:id（2s，既有逻辑；连续失败 5 次停——沿用）
  ▼
transcode-worker 消费（顺序单工，F3 不变）→ ffmpeg 多档 HLS 落盘
  ▼
job=done → 前端重取 /media/:id/360 拿 hls_master
  ├─ 普通视频：若原文件已在播（blob），原地热切换 video.src → HLS（用户无感知升级）[D6]
  └─ 360 视频：进度提示消失，直接起播 HLS
```

**任务调度**：不新增调度器——复用既有 Valkey 队列 + transcode-worker；自动任务与手动任务同队列同优先级（FIFO），避免自动流量饿死手动请求的关键改动是 D3 的 attach（同一媒体不重复排队）。
**流输出与播放衔接**：沿用「ffmpeg 落盘静态 HLS + 鉴权静态服务 ServeHLS」（已审计），播放器经 hls.js 拉 master playlist。

## 3. 自适应切换逻辑（直播模式体验）

| 项 | 方案 | 依据 |
|----|------|------|
| 带宽探测 | **hls.js 内置 ABR**：对每次分片下载做吞吐估算，快/慢双 EWMA 平滑——不自研探测协议 | F8；EWMA 本身就是防抖平滑器 |
| 可选清晰度档位 | 转码产物多档 ladder（源 1080p → 1080p/720p/480p/360p 四档；4K 源 → 2160p/1440p/1080p/720p 四档，上限 maxRenditions=4） | F4 |
| 切换触发条件 | hls.js 默认规则：估算带宽 < 当前档位码率×安全因子 → 自动降档；持续富余 → 升档；另配 `capLevelToPlayerSize: true`（不投放超过播放器像素尺寸的档） | F4/F8 |
| 缓冲机制 | hls.js VOD 缓冲调优：`maxBufferLength=30s`、`maxMaxBufferLength=60s`、默认卡顿时先重试分片再降档；直播式「边下边播」由 VOD 渐进缓冲天然承担 | F8 |
| 手工带宽校准（可选增强） | 已有 `/bandwidth/self-test` 端点可测链路带宽，v1 **不接入**播放器（避免播放路径依赖额外探测请求）；列为可选项 | F7 |

## 4. 开关关闭时回退与向后兼容

| 场景 | 行为 |
|------|------|
| `realtime_transcode=false`（默认，存量部署） | **逐字节现状**：普通视频播原始文件；360 视频显示手动转码提示按钮 |
| `auto_transcode=false`（总闸门关） | 全部回退原始文件播放；新开关被 UI 禁用；即便库内为开也因 AND 语义不触发 |
| 转码失败 | 普通视频：保持原始文件播放 + 轻提示「转码失败，已保持原始播放」；360 视频：失败态 + 手动重试按钮（v1 不自动重试转码本身——队列层已有退避重试，见 §5） |
| 转码中途切走媒体 | 既有代次守卫（loadSeq）+ cleanup 停轮询；服务端任务继续跑完（产物落库，下次直接受益） |
| API 兼容 | `POST /transcode/job` 不带 `auto` 字段 = 旧语义（手动、写死/指定 profile、新建任务）；`GET /transcode/config` 新增字段为增量 key，旧前端忽略之不炸 |

## 5. 状态管理与异常处理

| 关注点 | 方案 |
|--------|------|
| 开关读取与缓存 | **不缓存**：沿用 F6「每次播放现取单行行」，管理端改写后下一次播放即生效；读失败时 `realtime_transcode` 按**关**处理（与总闸门「失败按开」相反：宁可退手动，不可误自动） |
| 转码失败降级 | 服务端两分档语义不动（F3：死信 vs 退避）；前端 `failed` 态降级路径见 §4；轮询连续失败 5 次停（既有 P2-06） |
| 带宽波动防抖 | hls.js 双 EWMA（默认 ~4s/15s 时间常数）+ 升档需持续富余（默认 up-switch 更保守），不自研防抖层 |
| 并发播放资源控制 | ①服务端 attach-or-create：同一媒体全站最多一个活动转码任务（D3）；②队列 FIFO + 单 worker 顺序消费（F3）；③前端单播放器实例单任务，cleanup 即停轮询；④自动触发请求与手动请求共用 60 令牌桶全局限流（既有，可能 429——播放器对 429 退避 3s 重试一次后提示） |
| 审计 | PUT /admin/transcode-config 审计 detail 增量带 `realtime_transcode`（键名无敏感子串，RedactDetail 不触及） |

## 6. 边界与限制（诚实声明）

- **v1 不做「边转边播」**（ffmpeg 边产出分片、播放器按 event playlist 拉直播沿）[D5]：那会绕过已验收的「写行+入队+回滚」任务语义，引入半态产物清理、 playlist 中途可见性等新风险面。本设计把「实时」落在**播放即触发、免手动、完成即热切换、多档自适应**，复用全部已审计链路。边转边播列为 v2 候选，届时独立 Job 评估。
- 360° 视频转码完成前无法播放（全景播放依赖 HLS 切片，现状如此）——进度提示 + 旋转指示。
- 自动触发对服务器算力的影响 = 手动转码的总闸门不变，仅触发者从「人」变「播放请求」；弱网/老视频首次播放仍需等待转码完成（分钟级，取决于源）。
