# 影石（Insta360）全景视频原始文件直接播放 —— 技术可行性研究报告

| 项 | 内容 |
| --- | --- |
| 版本 | v1.0（研究稿，**未实施**） |
| 日期 | 2026-10-04 |
| 结论 | **技术上可行，但需分两档交付；纯 CPU 环境下「边转边播」不可行，必须走离线预转码** |
| 依据 | 115 实机侦察（ffmpeg 5.1.9）+ 三个同类项目（PhotoPrism / Immich / syncom）的公开实现与踩坑记录 |

---

## 一、结论先行

### 1.1 能不能做

**能**，而且**不需要引入影石 SDK**（这是最重要的结论）。

`.insv` 容器本质就是 MP4（`major_brand: avc1`），ffmpeg 能直接解；双鱼眼→等距柱状（equirectangular）的球面重映射由 ffmpeg 内置的 **`v360` 滤镜**完成。本机实测：

```
$ ffmpeg -hide_banner -filters | grep -w v360
 .SC v360    V->V    Convert 360 projection of video.
```

`libx264` / `libx265` 也在（转码管线现成可用）。**不涉及任何专有编解码器**。

### 1.2 但要区分两档 —— 这是本报告最重要的判断

影石不同代际的**文件布局完全不同**，这决定了实现难度差一个数量级：

| 档 | 机型 | 文件形态 | 处理方式 | 难度 |
| --- | --- | --- | --- | --- |
| **A 档** | X2 及更早、ONE RS | 单文件**单视频流**，双鱼眼同帧（1:1，如 2880×2880） | `v360=input=dfisheye:output=e` 直接上 | **低** |
| **B 档** | X3 / X4 / X5、5.7K 模式 | 单文件**双视频流**（两个镜头各一条 stream），或 `_00`/`_10` **成对文件** | 必须先 demux + hstack，再 v360 | **高** |

**PhotoPrism 的实战记录印证了这个分档**（他们已完成 A 档，明确把 B 档列为 out of scope）：

> ✅ 已支持：`.insp`、单文件 ~2:1 `.insv`、分离镜头 `.insv` 对（`_00`/`_10`）
> ❌ 未支持：X3/X4/X5 单文件双视频流（tracked in #5771）

**Immich 社区的现状**（同为「自托管相册」定位，可直接对标）：

> Immich can ingest `.insv` (they are basically MP4 containers), but it doesn't understand the Insta360-specific stuff inside — so ffmpeg / the player just picks the first video stream, which is why we only see one half / one lens.

**即：如果你现在把 X4 的 `.insv` 丢进 Immich，它会只显示一个镜头。** 这就是本项目当前的行为 —— 因为本项目的转码管线**只做等比 scale，完全没有球面变换**（`presets.go:81` 的注释也承认「球面元数据策略在 T3.5 细化」，至今未做）。

### 1.3 一句话方案

**离线预转码**：`.insv` 入库时识别 → 丢给 transcode worker → 拼接成 2:1 equirect → 走现有 HLS 管线 → 播放器零改动。

「直接播放原文件」在 4 核纯 CPU 上**做不到**（见 §四性能实测估算）。

## 二、影石格式的技术事实

### 2.1 `.insv` 容器

ffprobe 实测（PhotoPrism 提供的样本）：

```
Input #0, mov,mp4,m4a,3gp,3g2,mj2, from 'VID_20231224_162804_00_080.insv':
  Metadata: major_brand : avc1    compatible_brands: avc1isom
  Stream #0:0: Video: h264 (Main), yuvj420p(pc), 2880x2880 [SAR 1:1 DAR 1:1],
                    50211 kb/s, 29.97 fps          ← 注意：1:1，不是 2:1
  Stream #0:1: Audio: aac (LC), 48000 Hz, stereo
  encoder     : Ambarella AVC                     ← 厂商编码器标识
```

三个要点：

1. **容器是标准 MP4** —— 不需要特殊 demuxer
2. **1:1 画幅 = 两个鱼眼各占半边** —— 这是 A 档，`v360` 能直接吃
3. `Ambarella` 是影石的 SoC 厂商标识，出现在 metadata 里，**可作为厂商识别的辅助特征**（但不可作为唯一依据 —— 用户可能改过元数据）

### 2.2 X4 的编码规格

| 模式 | 分辨率 | 帧率 | 编码 | 码率 |
| --- | --- | --- | --- | --- |
| 360 8K | 7680×3840 | 30fps | H.265 | ~100 Mbps |
| 360 5.7K | 5760×2880 | 60fps | H.265 | — |
| 360 4K | 3840×1920 | 100fps | H.265 | — |
| 单镜头 | 4K | 60fps | H.265 | — |

**对本项目的三个含义**：

1. **HEVC 解码已在 ffmpeg 里**（`-decoders` 实测有 h264/hevc），但浏览器的 `<video>` / hls.js 对 HEVC 的支持**碎片化**（Chrome 桌面版可以、Safari 可以、Firefox 桌面版要看平台、Android Chrome 常常不行）→ **转码输出必须用 H.264**，不能直出 HEVC。
2. **8K 原始码率 100 Mbps**，一个 5 分钟视频约 3.7 GB。转码成 4K equirect（H.264 50 Mbps）后约 1.9 GB。
3. **5.7K/4K 模式是 `_00`/`_10` 成对文件**（两个独立文件），需要配对合并 —— 这是 A 档里的「分离镜头对」，PhotoPrism 已支持。

### 2.3 陀螺仪与防抖元数据

`.insv` 里含陀螺仪数据（gyro/motion vector），影石 Studio 用它做**防抖稳定**（flowstate）。

**本报告的判断：本期不做。** 理由：

- 防抖是**像素级重采样**（motion vector 补偿 + 光学流），v360 滤镜做不到
- 影石官方 SDK（MediaSDK）才有 `enable_flowstate` / `enable_denoise` / `enable_directionlock` 参数 —— **需要申请商业授权**
- 代价/收益不匹配：观看场景下「拼接缝可见」远不如「画面抖」难受

**这点必须让用户知情**：本方案出的是**几何正确但可能有可见接缝**的画面，不是影石 Studio 那种 AI 融合的效果。PhotoPrism 明确接受了这个限制：

> v360 is a geometric remap, not optical-flow blending — the seam where the two fisheye halves meet is navigable but visible. **This is acceptable for viewing**; higher-quality stitching is explicitly out of scope.

## 三、方案设计

### 3.1 架构：为什么走「离线预转码」而不是「边转边播」

```
                    ┌─────────────────────────────────────┐
  .insv 入库 ──────▶│ transcode worker（离线、队列化）    │
                    │  1. 探测布局（单流/双流/成对文件）    │
                    │  2. demux + hstack（B 档需要）        │
                    │  3. v360: dfisheye → equirect      │
                    │  4. 标 GSpherical 元数据             │
                    │  5. scale + libx264 → HLS 多码率     │
                    └──────────────┬──────────────────────┘
                                   ↓
                    media.hls_master（现有字段，零改动）
                                   ↓
                    hls.js → three.js 贴球（现有链路，零改动）
```

**关键设计点**：

- **转码输出写到哪里**：建议存 `data/media/.pano360/<media_id>/master.m3u8`，与 `hls_master` 字段对齐。原始 `.insv` **不动**（本项目红线：不碰原媒体文件）。
- **播放器零改动** —— 这是本方案最大的价值。现有 `360Player` 拿 HLS 喂 three.js，只要转码产出的是标准 2:1 equirect + 正确的球面元数据，**播放侧一行代码都不用改**。
- **降级路径**：识别不了布局 → 按普通视频处理（`is_360` 不置位），绝不让索引失败。这与 PhotoPrism 的 graceful degradation 策略一致。

### 3.2 B 档（X3/X4/X5）的拼接命令

PhotoPrism 与 gist 上验证过的 filter chain（A 档单流）：

```bash
# A 档：单文件单流，双鱼眼同帧
ffmpeg -i input.insv \
  -vf "v360=input=dfisheye:output=e:ih_fov=190:yaw=-90" \
  -c:v libx264 -preset slow -crf 18 output_equirect.mp4
```

B 档（双流，需 hstack）：

```bash
# 两个镜头各一条 stream：先 demux + 旋转 + 拼接，再 v360
ffmpeg -i VID_xxx_00_032.insv -i VID_xxx_10_032.insv \
  -filter_complex "\
    [0:v]transpose=2[a]; \
    [1:v]transpose=1[b]; \
    [a][b]hstack=inputs=2[v]; \
    [v]v360=input=dfisheye:output=e:yaw=-90" \
  -c:v libx264 -preset slow -crf 18 output_equirect.mp4
```

**B 档的三个坑（必须处理）**：

1. **镜头顺序与旋转方向因机型而异** —— gist 原文明确说「Transpose operation depends as different Insta360 cam might not have same orientation」。**必须按机型建映射表**，不能硬编码。
2. **`ih_fov` 需要实测标定** —— PhotoPrism 实测四个场景得到最优值 **186~194**，最终取 **190**（而非按镜头规格推算的 204）。理由：鱼眼圆盘是**内接**在半幅画面里，实际张角比光学规格小。
3. **`yaw=-90` 的朝向** —— 影石不同代际的原点方位不同，旋转错了会导致「朝天」。需要真机样本验证。

### 3.3 检测策略（如何判断是 A 档还是 B 档）

| 判据 | 含义 |
| --- | --- |
| `ext ∈ {.insv, .insp}` | 影石容器（**主判据**） |
| `streams == 2 && 都是 video` | B 档（双镜头） |
| `streams == 1 && SAR≈1:1 && 分辨率方形` | A 档（同帧双鱼眼） |
| `filename` 含 `_00_` / `_10_` | 成对文件模式，需配对 |
| metadata 含 `Ambarella` | 辅助确认（不可单独依赖） |
| maker/exif 含 Insta360 | 辅助确认 |

**成对文件（`_00`/`_10`）的坑**：它们在数据库里是**两条独立的 media 记录**，需要识别 + 配对 + 合并成一个可播放对象，且**两个方向的记录都要清理**。PhotoPrism 就是「reconciled into one photo on a forced rescan」。

### 3.4 球面元数据

转码产物必须带 GSpherical 标签，否则部分播放器/平台识别不出：

```bash
exiftool -XMP-GSpherical:Spherical="true" \
         -XMP-GSpherical:Stitched="true" \
         -XMP-GSpherical:ProjectionType="equirectangular" \
         -XMP-GSpherical:StereoMode="mono" out.mp4
```

**注意**：本项目播放器**不读**这些标签（three.js 贴球是几何固定的）。但加上它们有两个好处：① 导出/分享到 YouTube 等平台能正确识别；② 未来若改用 `<video>` + WebXR 投影模式会需要。

## 四、性能评估（本项目的真实约束）

### 4.1 环境实测

| 项 | 实测值 | 影响 |
| --- | --- | --- |
| ffmpeg | **5.1.9**（Debian 12 自带） | v360 可用 ✅ |
| v360 滤镜 | **可用** | 无需自建滤镜 ✅ |
| libx264 / libx265 | 均可用 | 转码可行 ✅ |
| HEVC 解码 | 可用 | 可读源 ✅ |
| **GPU** | **无 NVIDIA GPU** | **无法硬件加速** ⚠️ |
| **CPU 核数** | **4** | 转码是主要瓶颈 ⚠️ |

硬件加速方法虽然列出（`cuda`/`vaapi`/`qsv`/`opencl`/`vulkan`），但**宿主无 NVIDIA GPU，容器内看不到 `/dev/nvidia*`** → 全部走软解。

> ⚠️ 红线提醒：本项目有一条硬约束 —— **算力节点 B（192.168.1.41, RTX 3090）仅用于测试，不得写入软件功能**。所以「部署时用 GPU 加速」这条路对本项目**不可用**，报告中的性能估算必须按纯 CPU 算。

### 4.2 CPU 转码耗时估算

`v360` 滤镜是**逐像素重映射**（双鱼眼 → 球面），属于计算密集型。参考 photoprism 与社区实测的量级：

| 阶段 | 分辨率 | 4 核 CPU 估算 | 说明 |
| --- | --- | --- | --- |
| 拼接（v360 重映射） | 8K → 8K | **~8–15× 实时** | 最贵的一步 |
| 拼接 | 4K → 4K | ~4–8× 实时 | |
| H.264 编码（preset medium） | 4K | ~1.5–3× 实时 | libx264 多线程较成熟 |
| H.264 编码（preset fast） | 4K | ~0.5–1× 实时 | 画质换速度 |

**一个 5 分钟 8K X4 视频的估算**：

- 8K equirect 输出 + preset fast：约 **20–40 分钟**
- 降到 4K equirect + preset fast：约 **10–20 分钟**
- 多档 HLS（2160p/1440p/720p）再乘 2–3 倍

**结论：在 4 核机器上，一个 5 分钟 8K 视频的全量转码需要 30 分钟到 2 小时。**

### 4.3 为什么不能「边转边播」

用户问的是「直接播放」。三种可能的字面含义与可行性：

| 方案 | 可行性 | 说明 |
| --- | --- | --- |
| **① 浏览器直接播 `.insv`** | ❌ **不可行** | ① 容器虽是 MP4 但双流/鱼眼布局浏览器不认；② 需要 HEVC 解码，跨浏览器碎片化；③ **必须服务端拼接**（`v360` 是 ffmpeg 滤镜，浏览器无等价实现） |
| **② 边转边播（转码时同步推流）** | ❌ **不推荐** | 转码慢于实时（8K 拼接 8–15× 实时），HLS 分片要凑满才能播 → 首帧延迟 30 分钟起，且**转码一停播完即断**，体验比「等一次」更差 |
| **③ 离线预转码，看时即播** | ✅ **推荐** | 一次成本，多次流畅。与本项目现有 HLS 架构完全一致 |

**关键约束**：本项目已有完整的转码 worker 队列（`transcode-worker`，有 `transcode_jobs` 表与状态机），**方案③天然复用**，不需要新建管线。转码中/未完成的媒体，播放器按现有逻辑降级为普通视频（放平面视频），并在 UI 提示「全景处理中」——这个状态本项目已有（`realtime`、`transcode` 字段）。

## 五、工作量与风险

### 5.1 分阶段建议

| 阶段 | 内容 | 工作量 | 风险 |
| --- | --- | --- | --- |
| **P0 侦察** | 拿到真实 X 系列样本（在 115 上跑 ffprobe，确认真实流布局与 FOV） | 0.5 天 | **依赖样本** |
| **P1 A 档** | 单流布局识别 + v360 拼接 + HLS 接入 | 2–3 天 | 低 |
| **P2 元数据与降级** | GSpherical 标注、UI 状态提示、识别失败降级 | 1 天 | 低 |
| **P3 B 档** | 双流/成对文件 demux + hstack + 机型映射表 | 3–5 天 | **中高**（镜头顺序/旋转因机型而异，必须真机验证） |

**建议先做 P0 + P1**。P0 的关键是样本 —— 在拿到真实 X4 文件前，B 档的任何实现都是猜测。

### 5.2 主要风险

| 风险 | 等级 | 缓解 |
| --- | --- | --- |
| **缺真实样本** | 🔴 高 | 一切机型相关判断（流布局、镜头顺序、FOV、yaw）都需真机验证。**先解决样本问题** |
| **拼接缝可见** | 🟡 中 | 几何 remap 的固有局限。提前告知用户（不要承诺 Studio 级效果） |
| **无 GPU，耗时长** | 🟡 中 | 只对 `.insv` 触发（普通视频不受影响）；转码队列与现有共用；可考虑夜间批量跑 |
| **磁盘占用翻倍** | 🟡 中 | 8K → 4K equirect + HLS 多档，一个 5 分钟片约 +1.9 GB。需明确保留策略与清理机制 |
| **成对文件的记录清理** | 🟡 中 | `_00`/`_10` 是两条 media 记录，合并后需正确处理，避免残留半张 |
| **机型映射表维护** | 🟢 低 | 未知机型走「A 档 + 实测默认 FOV 190」降级，并记录告警 |

### 5.3 与项目既有约束的冲突检查

| 既有约束 | 是否冲突 | 说明 |
| --- | --- | --- |
| 不碰原媒体文件（红线） | ✅ **不冲突** | 只新增派生产物，`.insv` 字节不变 |
| ffmpeg 仅 subprocess（开源合规） | ✅ **不冲突** | 用内置 `v360`，不引入新依赖 |
| 不用 insightface 等商用库 | ✅ **不冲突** | 纯 ffmpeg |
| 算力节点 B 不写入软件功能 | ✅ **不冲突** | 本方案纯 CPU，反而符合 |
| 可见性唯一真源 `mediascope` | ⚠️ **需注意** | 派生产物的路径要走同样的作用域判定，不能成为绕过通道 |
| 危险操作禁 `compose down -v` | ✅ **不冲突** | 与部署无关 |

## 六、替代方案对比

| 方案 | 画质 | 耗时 | 依赖 | 适合 |
| --- | --- | --- | --- | --- |
| **A. ffmpeg v360 预转码**（推荐） | 接缝可见 | 30min–2h/片 | 无 | 自托管、批量、长期使用 |
| B. 影石 Studio 手工导出 | 最佳 | 人工 | 桌面软件 + 账号 | 少量精修 |
| C. 影石 MediaSDK | 最佳（含防抖） | 快（GPU 加速） | **需商业授权** | 有授权预算时 |
| D. 引导用户上传导出的 MP4 | 取决于用户 | 零 | 无 | 只想偶尔看 |

**建议**：A 为主 + 在 UI 上提示「如需最佳拼接效果，可用影石 Studio 导出后上传」。

## 七、待你决策的三个问题

1. **是否有真实样本？** 你的相机是 X 系列哪一代？（X3/X4/X5 属 B 档，其余多为 A 档）这是 P0 的前提。
2. **要不要做 P3（B 档）？** B 档工作量是 A 档的两倍，且强依赖真机验证。若你的相机是 X2 及更早 / ONE RS，A 档就够了。
3. **转码时机策略？** ①入库即转（首次观看有等待）②夜间批量转（白天流畅，但新片要等一天）③按需转（第一次点开时转，第二次才流畅）
