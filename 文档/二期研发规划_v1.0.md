## 〇、规划前必须知道的三件事

### 0.1 实测性能基线（115，4 核纯 CPU）

我先做了实测再定工期。数据（`v360` + `scale` + `libx264 veryfast`）：

| 档位 | 每秒素材耗时 | 5 分钟素材 | 产物 |
| --- | --- | --- | --- |
| 720p | 1332 ms | **1.1 小时** | — |
| **4K（主档）** | **1930 ms** | **1.6 小时** | ~1784 MB @50Mbps |
| 8K | 4805 ms | 4.0 小时 | ~7 GB |
| 纯编码基线（无 v360） | 982 ms | 49 分钟 | — |
| **HLS 三档合计** | — | **约 2.9 小时/片** | ~1.4 GB |

**三个决定规划走向的发现**：

1. **拼接只占约 50% 耗时**（1930 vs 982 ms），编码占 50%。→ 优化重点不该只在拼接，**降低输出分辨率同样有效**。
2. **5 分钟 8K 视频三档转码需 2.9 小时**。→ **「入库即转」不可行**，必须做按需转 + 夜间批量。
3. `v360` **原生支持 `input=dfisheye`（dual fisheye）**，不需要手动 hstack；且有 `in_trans` 参数可直接处理镜头方向。→ **技术难度低于预估**。

### 0.2 项目红线（不可违反）

| 红线 | 对本规划的约束 |
| --- | --- |
| **算力节点 B（RTX 3090）仅测试，不得写入软件功能** | 全部方案按**纯 CPU** 设计。GPU 加速 v360、GPU 编码全部排除 |
| **不碰原媒体文件** | 360 去畸变产物是**派生物**，原片字节不变 |
| **ffmpeg 仅 subprocess** | 走 `internal/ffmpeg`，不引入 cgo 绑定 |
| **不用 InsightFace** | OCR 选 PP-OCRv5（Apache-2.0）；人脸沿用 YuNet+SFace |
| **Token 预算 4000/月** | 规划已考虑，每个迭代的「预估 token 消耗」见 §5 |

### 0.3 本期不做（明确排除，避免范围蔓延）

| 不做 | 理由 |
| --- | --- |
| 移动端 App | 与「Web/桌面全景」定位冲突，且是 Immich 主场（其护城河，用户开启后极难迁移） |
| GPU 加速 | 违反红线；PhotoPrism 也不做 |
| 陀螺仪防抖（flowstate） | 需影石 MediaSDK **商业授权** |
| 调色/滤镜 | PhotoPrism 无、Immich v3.0 刚移除，非全景核心 |
| VectorChord / pgvecto.rs | pgvector 已够用，不追 Immich 的选型 |
| 引入 InsightFace | 授权风险未解除 |

## 一、二期总体目标

### 1.1 战略定位（从对比报告得出的结论）

**不做「更好的通用相册」，做「唯一能正确处理全景媒体的相册」。**

对比数据支撑这个定位：

| 能力 | Panomint | PhotoPrism | Immich |
| --- | --- | --- | --- |
| 360 视频原生工作流 | 🏆 唯一 | ❌ | ❌ 明确拒绝跟进 |
| 360 原片去畸变 | 🏆 **待建** | ✅ 已实机验证 | ❌ |
| OCR 检索 | 🏆 **待建** | ❌ 明确不做 | ✅ 有 |
| 中文 AI 原生 | 🏆 Chinese-CLIP | ❌ 无专项 | ⚠️ 需选型 |
| 许可干净 | 🏆 无 InsightFace | — | ⚠️ InsightFace 未解除 |

**二期要建的三个护城河**：
1. **360 全链路**（原片去畸变 → 深缩放 → 视频自由视角）—— 唯一性最强
2. **中文全景检索**（中文 CLIP + OCR + 地理）—— 差异化明确
3. **轻量自托管**（4 核可跑 + API 稳定）—— 对标 Immich 的部署门槛优势

### 1.2 二期目标（可验证）

| 编号 | 目标 | 验收判据 |
| --- | --- | --- |
| G1 | 影石/理光等 360 原片能正确播放 | 真实样本入库后，播放器画面**无鱼眼畸变**；实测截图 + 像素断言 |
| G2 | 中文语义 + OCR 检索可用 | 搜「海边的日落」能命中无 caption 的照片；搜店招文字能命中 |
| G3 | 检索维度达到 PhotoPrism 的可用子集 | 过滤字段从 12 提到 **≥30** |
| G4 | 4 核机器上转码不拖垮服务 | 转码期间 `GET /media` P99 < 500ms（CPU 不打满） |
| G5 | 部署门槛保持 ≤4 核/4GB | 115 实测全栈内存 < 2GB |

## 二、技术选型对比（关键决策）

### 2.1 决策 1：360 去畸变的实现路径

| 方案 | 画质 | 耗时 | 依赖 | 授权 | 判定 |
| --- | --- | --- | --- | --- | --- |
| **A. ffmpeg `v360`** | 接缝可见 | 1930 ms/秒（4K，实测） | 无（ffmpeg 5.1.9 自带） | LGPL/GPL | ✅ **选定** |
| B. 影石 MediaSDK | 最佳（含防抖） | 快（GPU） | 需申请 | **商业授权** | ❌ 排除 |
| C. 自研 OpenGL 拼接 | 可控 | 快 | 需 GPU（本项目无） | 自有 | ❌ 违反红线 |
| D. 引导用户用 Studio 导出 | 最佳 | 人工 | 桌面软件 | 免费 | 🟡 作为**兜底提示**保留 |

**选 A 的实测依据**：115 上 `v360` 可用（`.SC v360 V->V`），且 `input=dfisheye` 原生支持双鱼眼同帧，`in_trans` 可处理镜头方向——**不需要手动 hstack，比预想简单**。

**A 档（X2/ONE RS）命令**（已实测 9.65 秒/5 秒素材）：
```bash
ffmpeg -i input.insv \
  -vf "v360=input=dfisheye:output=e:ih_fov=190:yaw=-90:in_trans=<T>,scale=3840:1920" \
  -c:v libx264 -preset veryfast -crf 20 output.mp4
```

### 2.2 决策 2：OCR 引擎

| 方案 | 许可 | 中文准确率 | 体积 | ONNX 可用 | 判定 |
| --- | --- | --- | --- | --- | --- |
| **PP-OCRv5（PaddleOCR）** | **Apache-2.0** | 官方支持中英日 | ~10MB/模型 | ✅ | ✅ **选定** |
| Tesseract | Apache-2.0 | 中文档差（需 chi_sim） | 大 | ❌（非 ONNX） | 🟡 备选 |
| 云 OCR API | 商业 | 好 | 0 | — | ❌ 隐私 + 成本 |

**选 PP-OCRv5 的决定性理由**：Immich 就是用它（Apache-2.0，**无 InsightFace 那样的授权风险**），而 **PhotoPrism 明确表示 OCR 不在 roadmap** → Panomint 与 Immich 都能做，但 PhotoPrism 不会做。

### 2.3 决策 3：360 深缩放的尺寸策略

实测：8K 档耗时是 4K 的 **2.5 倍**（4805 vs 1930 ms/秒），产物 4 倍。

| 策略 | 画质 | 耗时 | 存储 | 判定 |
| --- | --- | --- | --- | --- |
| **等比降采样**（8K 源 → 4K 交付） | 主流设备足够 | 1.6 h/5min | ~1.4 GB | ✅ **默认** |
| 保留 8K + 16K 缩略图 | 最佳 | 4 h/5min | ~7 GB | 🟡 **仅手动触发**（高级用户） |
| 全程 8K 三档 HLS | 最佳 | ~12 h/5min | ~10 GB | ❌ 不现实 |

**决策**：**默认 4K 三档 + 16K 静态缩略图**。16K 只出静态图（供查看器深度缩放），不出视频档 —— 这是 PhotoPrism 的做法（`fit_15360`）。

### 2.4 决策 4：转码时机（直接决定用户体验）

实测 2.9 小时/片的三档转码 ⇒ 只有三种可行策略：

| 策略 | 首次观看 | 成本 | 判定 |
| --- | --- | --- | --- |
| ① 入库即转 | 等待 2.9 h | 高（多数片没人看） | ❌ |
| ② **夜间批量** | 新片次日可看 | 低（利用空闲 CPU） | ✅ **默认** |
| ③ **按需转**（第一次点开时触发） | 首次等 2.9 h，第二次流畅 | 中 | ✅ **叠加**（用户明确想看才转） |

**选 ②+③ 组合**：夜间跑批量（cron 调低优先级），用户点开时若未转好则入队并提示「正在处理全景（约需 X 分钟）」。

### 2.5 决策 5：人脸模型（保持现状）

Panomint 现有 YuNet + SFace 已覆盖，且**规避了 Immich 的 InsightFace 授权风险**。二期**不换模型**，只补管理能力（对齐 PhotoPrism 的 CLI）。

## 三、迭代拆分（6 个迭代）

### 迭代 1：360 原片去畸变（A 档）—— 🏆 最高优先级

**目标**：影石 X2/ONE RS 等 A 档机型原片入库后能正确播放。

| 项 | 内容 |
| --- | --- |
| **交付** | ① 布局探测器（ffprobe → 单流/双流/成对文件）② `v360` 转码管线接入现有 transcode worker ③ FOV 标定配置（per-camera + fallback）④ 球面元数据（GPano XMP）⑤ 转码进度 UI |
| **改动范围** | `internal/ffmpeg`（新增 dewarp 预设）、`internal/index`（布局探测）、`internal/media`（投影字段）、`transcode-worker`（新 job type）、`frontend`（进度与状态） |
| **工期** | **8 个工作日** |
| **前置依赖** | 🔴 **必须有真实 A 档样本**（见 §6 风险 R1） |
| **验收** | ① 真实样本入库 → 播放器画面无鱼眼畸变（截图 + 像素断言）② 布局探测对 4 类样本判断正确 ③ 5 分钟片转码耗时 < 2 小时 ④ 识别失败时降级为普通视频，**索引不报错** ⑤ 原片 md5 前后一致 |
| **token 预估** | ~25 万 |

**技术要点**：
- **FOV 标定方法**（借鉴 PhotoPrism 的方法论，非代码）：不按镜头规格推算，而是按**存储的鱼眼圆盘实际张角**取值 —— 圆盘是内接在半幅画面里，实际张角比光学规格小。做法：在候选角度扫描接缝不连续性，取最优。**需实测**（建议起步值 190）
- **`in_trans` 处理镜头方向**：不同代际原点方位不同，转错会「朝天」。先用 A 档验证 `in_trans` 取值，再进 B 档
- **降级必须 fail-open**：布局探测失败 → 按普通视频处理 + 告警日志，**绝不让索引失败**

### 迭代 2：OCR 检索 —— 🏆 差异化最高

**目标**：搜「pizzeria」命中没写过 caption 的店招照片。

| 项 | 内容 |
| --- | --- |
| **交付** | ① PP-OCRv5 集成（ONNX，走现有 `ortx`）② 独立 `ocr-worker`（或复用 tag-worker）③ `media.ocr_text` 列 + 全文索引 ④ 搜索参数 `ocr:` ⑤ 缩略图叠加文字（可选，看板） |
| **改动范围** | `internal/ocr`（新包）、`internal/search`（参数与打分）、迁移 `00048` |
| **工期** | **6 个工作日** |
| **验收** | ① 10 张真实中文店招照片，OCR 命中率 ≥80% ② 搜店招文字能命中 ③ 英文/中文/日文各测 20 张，报告准确率 ④ OCR 不可用时搜索降级但不报错 |
| **token 预估** | ~18 万 |

**技术要点**：
- **PP-OCRv5 有 detector + recognizer 两段**，需要分别 ONNX 化；先用现成 ONNX 权重验证，不要自己转
- **存储成本**：每张图存 OCR 文本约 200~500 字节 → 10 万张约 30 MB，可接受
- **与 CLIP 的关系**：OCR 是「精确文字匹配」，CLIP 是「语义近似」，两者互补。搜索时应 **OCR 精确匹配权重高于 CLIP 近似**（Immich 就是分开处理的）

### 迭代 3：360 深缩放（16K）

**目标**：360 场景下放大不糊。

| 项 | 内容 |
| --- | --- |
| **交付** | ① 缩略图尺寸体系扩展（新增 16K `fit_15360`）② 静态/动态双尺寸上限（借鉴 PhotoPrism：`thumb_size` 索引期上限 + `thumb_size_uncached` 按需上限，**下限 720px** 因 AI 消费需要）③ 查看器深度缩放适配 ④ 存储成本监控 |
| **工期** | **5 个工作日** |
| **验收** | ① 8K equirect 缩略图最長边 ≥ 7680 ② 放大到 200% 清晰（对比度断言）③ 缩略图缓存分层正确 ④ 磁盘占用增长在预算内 |
| **token 预估** | ~15 万 |

**技术要点**：
- 存储成本随**面积**增长：16K (15360×8640) 单张约 1.5 MB JPEG → 10 万张 **150 GB**。必须配套清理策略与磁盘水位线（PhotoPrism 有 `STORAGE_FREE` 阈值，可借鉴）
- **下限 720px 是硬约束** —— AI worker（CLIP/人脸）消费缩略图，太小会失效

### 迭代 4：检索维度扩展

**目标**：过滤字段从 12 提到 ≥30。

| 项 | 内容 |
| --- | --- |
| **交付** | ① 感知哈希相似（`diff:`，复用已有 phash）② 邻近（`near:` 时间 + 地理）③ 相机/镜头维度（`camin`/`lens`/`focal`）④ S2 空间索引（替代纯 lat/lon）⑤ **无界手输查询语言**（`&` AND / `|` OR / `!` NOT / 通配 / 转义）⑥ 18 色主色过滤 ⑦ `panorama`/`fisheye` 投影过滤 |
| **工期** | **7 个工作日** |
| **验收** | ① 查询语言解析器有完整单测（含转义完备性）② 每个新过滤维度有 e2e 用例 ③ 过滤字段总数 ≥30 ④ 恶意查询串（SQL 注入尝试）全部安全 |
| **token 预估** | ~20 万 |

**技术要点**：
- **无界手输查询语言是最优性价比项** —— 低代码量、高功能密度（PhotoPrism 70+ 维度就靠它 + 大量过滤器）
- S2 索引：PG 扩展，实现比 H3 简单；**但要评估 PG 扩展的部署成本**（Immich 用 VectorChord 是个教训 —— 增加了升级风险）

3. **成对文件是两条 media 记录** —— 合并后两条记录都要正确处理，避免残留「半张」

### 迭代 2.5：幻灯片播放（增补，详见 `文档/幻灯片播放功能_技术设计_v1.0.md`）

**为什么放在迭代 2 之后**：它依赖「按当前筛选/搜索结果播放」的语义，而**迭代 2（OCR 检索）恰好
让「搜出一组照片 → 直接幻灯片播放」成为可能** —— 搜「海边的日落」得到 20 张，直接开幻灯片。
两者组合产生复利，单独看幻灯片只是个播放器。

**核心设计点**（详见设计稿）：

| 点 | 设计 |
| --- | --- |
| 视频不计算间隔 | 照片用定时器；视频用 `<video>` 的 `ended` 事件 + 兜底看门狗（防事件不触发） |
| 缩略图必须 blob 预加载 | `/media/:id/thumb` 挂 `authed` 组需 JWT，裸 `<img src>` 会 401；复用 `mediaLoader.loadThumbUrl` |
| 预加载前后各 2 张 | 避免切换白屏；视频不预载 blob（数百 MB），只预取元数据 |
| 转场用 GSAP | 项目已有 GSAP 且有 `gsap.context()` + `onBeforeUnmount` 的正确清理范式，必须复用 |
| 状态机抽 `useSlideshow.js` | 纯逻辑不含 UI → 排序/计时/边界可单测（符合项目纪律） |
| **背景音乐** | 用户上传 → 可复用选用 → 单曲循环（`audio.loop`）→ 批量删除。新表 `slideshow_track` + 5 端点；**流式播放必须 `http.ServeContent`**（项目在 `shares/handlers.go:515` 已踩过 `c.File` 不支持 Range 的坑） |
| **BGM 与视频原声** | 三选项：原声优先（BGM 压低，默认）/ BGM 独占 / 关闭 |
| **「倒序」= 当前显示顺序反转** | `items.slice().reverse()`，**不是**按时间倒序重查；必须先 `slice()` 否则原地改坏视图 items |
| 空列表禁用入口 | 避免点进去看空屏 |
| 分页视图显式提示 | 「仅播放已加载的 N 张」+ 加载全部选项，**不静默截断** |
| 间隔秒数 UI 标注 | 「仅照片生效，视频播完自动切换」—— 反直觉点必须写在设置项旁 |

**工期** 14.5 工作日（主体 7d + 背景音乐 5d + 音裁剪 2.5d）· **token** 约 98 万 · 优先级 P2（纯体验增强，不补能力缺口）

| **音裁剪（可选）** | 服务端 ffmpeg `-c:a copy`（实测偏差仅 **0.02s**、快 13 倍，不够再回退重编码）。裁剪段**存为独立曲目**（`parent_id` + `origin=clip`），因为「虚拟裁剪」会让 `ServeContent` 的 Range 字节偏移错位 |
| **BGM 占配额 / 按空间隔离** | 已确认：裁剪副本也占配额；每个 space 一套互不可见 |

**背景音乐**（用户追加需求）：上传 → 可复用选用 → 单曲循环 → 批量删除。
新表 `slideshow_track`（**不进 `media` 表**，否则污染时间线/缩略图/转码队列）+ 5 个端点。
关键技术点：`http.ServeContent` 提供 Range（`c.File` 不支持，项目已踩过）、
BGM 与视频原声的音量竞争、换曲的 `seq` 竞态守卫。
