### 本轮新增的工程教训：nginx `add_header` 的覆盖规则

首次把安全头写在 **server 块**里时，容器内 `grep` 到 5 处配置，但 **HTTP 响应里一条都没有**（只剩 `location /` 自己的 `Vary: Accept`）。

**根因（nginx 官方规则，极易反复踩）**：子 `location` 只要出现**任意一条** `add_header`，就**完全不再继承**父级 `server` 块的 `add_header` —— 不是逐条合并，是**整体覆盖**。本项目 `docker/web/Dockerfile` 里 `location /`、`@spa`、`= /sw.js`、`= /manifest.webmanifest` 四处各自都带 `add_header`，故写在 server 块里的安全头**一条都不会下发**。

**正解**：逐 `location` 重复声明。已覆盖全部 4 处并在文件头用大段注释记录此陷阱。CSP 同样受此规则约束，故也必须逐 location 写。

**验证方式**：`curl -I` 逐 location 断言响应头真实存在（不能只看配置文件里有没有 —— 配置文件有 ≠ 响应里有）。

## 高危（3 项，建议本轮内修复）

### H-1 SSRF：LLM 上游 base_url 无任何协议与内网地址校验

**位置**：`src/backend/internal/agentllm/agentllm.go:129`（保存）、`:196-210`（测试）、`:251`（代理）

**问题**：`base_url` 唯一的处理是 `strings.TrimRight(strings.TrimSpace(...), "/")`（第 129 行），**没有协议白名单、没有内网地址段拦截**。而 `TestConfig` 处理器会直接对该地址发起 HTTP 请求：

```go
// agentllm.go:196
req, err := http.NewRequestWithContext(c.Request.Context(), http.MethodGet, baseURL+"/models", nil)
if err != nil {
    httperr.Envelope(c, http.StatusBadRequest, "BAD_URL", "base_url 非法")
    return
}
resp, err := h.client().Do(req)   // ← 直接发出请求
```

`ProxyChat`（第 251 行）同样以 `r.BaseURL + "/chat/completions"` 拼接后转发。

**触发条件**：持有 `admin:system` 权限的用户（或攻破其会话后）调用 `POST /admin/agent/llm-config/test`，把 `base_url` 设为 `http://169.254.169.254/latest/meta-data/`、`http://127.0.0.1:5432/`、`http://192.168.1.1/` 等，服务器会代替请求者访问这些目标并把结果（状态码、部分响应）回显。`ProxyChat` 路径更进一步，会把请求体（含对话内容）发往任意目标。

**影响**：内网服务探测与元数据凭证窃取（云环境）、内网管理面越权访问；同时构成对内网其他服务的拒绝服务面（可携带任意请求体与头）。协议未限制还允许 `file://` 等非 HTTP 协议（受 Go `http.Client` 限制不可用，但缺少显式拒绝属防御纵深缺失）。

**修复建议**：

```go
// internal/agentllm/netguard.go（新增）
package agentllm

import (
    "fmt"
    "net"
    "net/url"
    "strings"
)

// validateUpstreamURL 校验上游 base_url：仅 http/https + 拒绝内网/环回/链路本地地址。
// SSRF 防线：管理员可配 URL ⇒ 必须当作「面向内网的可控请求原语」对待。
func validateUpstreamURL(raw string) (*url.URL, error) {
    u, err := url.Parse(strings.TrimSpace(raw))
    if err != nil {
        return nil, fmt.Errorf("URL 解析失败")
    }
    if u.Scheme != "https" && u.Scheme != "http" {
        return nil, fmt.Errorf("仅允许 http/https 协议")
    }
    host := u.Hostname()
    if host == "" {
        return nil, fmt.Errorf("缺少主机名")
    }
    // 字面量 IP 直接判定；域名交由下方解析后判定（防 DNS 重绑定在解析后二次校验）
    if ip := net.ParseIP(host); ip != nil && isInternalIP(ip) {
        return nil, fmt.Errorf("禁止指向内网地址")
    }
    return u, nil
}

func isInternalIP(ip net.IP) bool {
    return ip.IsLoopback() || ip.IsPrivate() || ip.IsLinkLocalUnicast() ||
        ip.IsLinkLocalMulticast() || ip.IsUnspecified()
}

// dialGuard 返回带内网拦截的 dialer，装配进 http.Transport：
// 拦「域名解析后落在内网」这一路（字面量 IP 之外的绕过路径）。
func dialGuard(ctrl *net.Dialer) func(ctx context.Context, network, addr string) (net.Conn, error) {
    return func(ctx context.Context, network, addr string) (net.Conn, error) {
        h, _, err := net.SplitHostPort(addr)
        if err != nil {
            return nil, err
        }
        ips, err := net.DefaultResolver.LookupIP(ctx, "ip", h)
        if err != nil {
            return nil, err
        }
        for _, ip := range ips {
            if isInternalIP(ip) {
                return nil, fmt.Errorf("目标解析到内网地址，已拒绝")
            }
        }
        return ctrl.DialContext(ctx, network, addr)
    }
}
```

在 `PutConfig`（保存前）与 `TestConfig` / `ProxyChat`（每次出站前）三处调用 `validateUpstreamURL`；同时把 `h.client()` 的 Transport 的 `DialContext` 换为 `dialGuard`。

**优先级理由**：这是本报告唯一「可达外网 + 可打内网」的组合。虽有 `admin:system` 前置，但该权限与内网服务之间不应存在这条通路——一旦 admin 账号被弱口令或会话劫持拿下，攻击面直达内网。建议列入本轮修复。

### H-3 会话撤销：access token 无服务端失效机制

**位置**：`src/backend/internal/auth/jwt.go:41-53`（签发）、`internal/auth/middleware.go:18-41`（校验）

**问题**：access token 是自证的纯 JWT，TTL 15 分钟（`jwt.go:17`）。`ParseAccess` 只验签与过期，**不查库、不比对任何会话状态或用户状态**。因此：

- 用户被 `DELETE /admin/users/:id` 禁用后，其已签发的 access token 在最长 15 分钟内仍可正常调用所有 API。
- 用户自助改密（`internal/auth/password.go:98` 已正确 `RevokeAllSessions`）、管理员重置密码后，旧 access token 同样不立即失效。
- 角色变更（`PATCH /admin/users/:id`）同理：JWT 里的 `role` 声明（`jwt.go:24,50`）在 15 分钟内保持旧值。虽然 `HasPerm` 有 30s 缓存且按 role 名查库（`internal/auth/store.go:426-450`），但 `RequirePerm` 拿到的是**token 里的 role 字符串**（`middleware.go:48`），旧 role 名仍能命中该角色的权限集合。

**触发条件**：任何持有有效 access token 的第三方（被盗 token、被恶意插件/浏览器扩展读取的 token）在改密/禁用操作后继续使用。

**影响**：账户禁用与改密的**即时撤销语义不成立**（延迟最长 15 分钟）。这与代码注释里已经意识到的同类问题形成对照——`handlers.go:427-429` 明确为 refresh 路径补了状态检查，说明这个权衡是逐路径补齐的，access 路径尚未补。

**修复建议**（三选一，按侵入性递增）：

1. **最小改动（推荐先做）**：缩短 `AccessTTL` 至 5 分钟，配合前端已有的 refresh 自动续期（`src/utils/tokenStore.js` + `http.js` 已有刷新链）。把暴露窗口从 15 分钟压到 5 分钟，改动零风险。
2. **会话版本号**：给 `users` 加 `session_ver int`，写进 JWT 声明；`ParseAccess` 后比对一次（可用与 `permCache` 同样的 30s 缓存，避免每请求查库）。改密/禁用/角色变更时 `session_ver++`，全部旧 token 立即失效。
3. **黑名单**：登出时把 jti 写入 Valkey（项目已有队列基础设施），`AuthRequired` 查一次。精确但每请求增加一次外部依赖调用。

考虑到本系统是自托管单实例、并发量低，方案 2 的性价比最高。

## 中危（6 项）

### M-1 加密密钥缓存存在 data race

**位置**：`src/backend/internal/storage/crypto.go:29`（`var cipherKey []byte`）、`:32-46`（`loadCipherKey`）

**问题**：`cipherKey` 是包级变量，`loadCipherKey()` 的「检查 → 写入」无任何同步保护。多个 goroutine 并发首次调用（如服务启动后同时到达的加密请求）会并发写同一 slice。虽因写入的值相同、不会产生错误密文，但**这是 Go 明确的数据竞争**，`-race` 下必报，且理论上 `go vet`/静态检查无法捕获。

**触发条件**：服务启动后首批并发请求同时进入 `EncryptCreds` / `EncryptString`。

**影响**：功能上无实际危害（幂等写入），但属于确定的并发缺陷，未来若改为惰性换密钥/轮换逻辑会演变为真实安全问题。修复成本极低。

**修复建议**：

```go
var (
    cipherKeyOnce sync.Once
    cipherKey     []byte
)

func loadCipherKey() []byte {
    cipherKeyOnce.Do(func() {
        raw := os.Getenv("STORAGE_CIPHER_KEY")
        if raw == "" {
            return
        }
        k, err := hex.DecodeString(raw)
        if err != nil || len(k) != 32 {
            return
        }
        cipherKey = k
    })
    return cipherKey
}
```

注意：`sync.Once` 意味着密钥在进程内只读一次，与当前「惰性加载」语义一致；`storage/crypto_test.go:14,60,74` 用 `t.Setenv` 改环境变量的测试需要改为每个用例一个进程或改用可注入的 key 源（测试已存在 3 个用例依赖动态改 env，**这条修复需同步调整测试**）。

### M-2 9 个文件遍历结果集后未检查 rows.Err()

**位置**（缺 `rows.Err()` 检查的文件）：

```
internal/audit/handlers.go        internal/audit/restore_history.go
internal/auth/perm_meta.go        internal/debug/commands_core.go
internal/folders/folders.go       internal/media/batch_store.go
internal/shares/handlers.go       internal/spaces/spaces.go
internal/storage/handler.go
```

**问题**：全仓 66 处 `Query` 调用，仅 47 处配套 `rows.Err()`。pgx 的 `rows.Next()` 返回 false 有两种原因——正常读完与迭代出错——必须靠 `rows.Err()` 区分。缺失时，DB 连接中断/网络抖动导致的迭代中途失败会被**静默当成"查完了"**，返回部分结果集。

**触发条件**：PostgreSQL 连接中途断开，或容器网络抖动。

**影响**：数据静默不全。例如 `internal/audit/handlers.go` 的审计列表、`internal/shares/handlers.go` 的分享列表会少返回若干行而客户端不知情；更糟的是若该行数被用于决策（如配额判断、去重判断），会基于不完整数据做错误决策。这类 bug 在生产环境的典型表现就是「偶发少一条数据，刷新又好了」，极难定位。

**修复建议**（以 spaces 为例，其余同型）：

```go
// internal/spaces/spaces.go:56 后
for rows.Next() {
    if err := rows.Scan(&r.ID, &r.Name, &r.Role); err != nil {
        httperr.Fail(c, http.StatusInternalServerError, "QUERY_FAILED", "查询失败", err)
        return
    }
    shared = append(shared, r)
}
if err := rows.Err(); err != nil {          // ← 补这一段
    httperr.Fail(c, http.StatusInternalServerError, "QUERY_FAILED", "查询失败", err)
    return
}
c.JSON(http.StatusOK, gin.H{"personal": p, "shared": shared})
```

建议同时加一条 lint 级守卫（类似 `httperr` 已有的 `TestEnvelopeShapeHasSingleImplementation` 思路），防止新代码重犯。

### M-3 WebDAV 完全绕过全局限流

**位置**：`src/backend/cmd/api/main.go:216-219`

```go
for _, m := range []string{"GET", "HEAD", "PUT", "DELETE", "PROPFIND", "MKCOL", "MOVE", "OPTIONS", "LOCK", "UNLOCK"} {
    r.Handle(m, "/dav", gin.WrapH(davHandler))
    r.Handle(m, "/dav/*path", gin.WrapH(davHandler))
}
```

**问题**：`/dav` 挂载在 `r`（根路由）上，**不走 `authed` 组**，因此不经过 JWT 中间件——这符合设计（DAV 用 HTTP Basic 认证，见 `dav.go:63`）。但根路由的中间件链里**包含 `middleware.RateLimit`**（`main.go:109`），所以限流实际是生效的。这里修正我最初的判断：DAV 请求**会**被限流保护。

真正的问题是另一面：**DAV 的 Basic 认证走 `davPasswordOK`（`dav.go:74`），每请求一次 bcrypt 校验**（`dav.go:20-22` 的注释已自认此性能代价）。而 `/dav/*path` 的限流豁免逻辑（`internal/middleware/ratelimit.go:20`）**只豁免 `*/thumb` 后缀**，`/dav/...` 不豁免，所以 DAV 受 60 令牌桶/10 每秒约束。

**风险点**：`PROPFIND` 一个大目录树会发出多次请求，客户端连接复用不受保证（`dav.go:20-22` 已注明）。若将来某天为 DAV 性能把 DAV 加入豁免名单（正如 thumb 被豁免那样），将同时失去限流保护。**这是一个需要加护栏的边界，而非当前正在 exploitable 的漏洞**。

**修复建议**：在 `ratelimit.go` 的豁免条件旁加显式注释与测试锁定当前策略；若将来确需豁免 DAV，必须改为「按用户身份而非 IP」限流。

```go
// internal/middleware/ratelimit.go
// ⚠️ 豁免名单是安全边界，改动须同步 review：当前仅 */thumb。
// 缩略图有 JWT + mediascope 双重鉴权，豁免的只是频控。
// **禁止**把 /dav 加入豁免：DAV 走 HTTP Basic（dav.go:63），
// 按 IP 限流是它唯一的暴力破解防护（每请求一次 bcrypt，天然慢）。
if c.Request.Method == http.MethodGet && strings.HasSuffix(c.Request.URL.Path, "/thumb") {
    c.Next()
    return
}
```

### M-4 `PUT /preferences/map` 与 `PUT /user/ui-prefs` 用读权限做写操作

**位置**：`src/backend/cmd/api/main.go:367`、`main.go:373`

```go

authed.PUT("/preferences/map", permRead, geoH.PutMapIconPref)   // ← 写操作挂 permRead
...
authed.GET("/user/ui-prefs", permRead, geoH.GetUIPrefs)
authed.PUT("/user/ui-prefs", permRead, geoH.PutUIPrefs)         // ← 写操作挂 permRead
```

**问题**：两个 PUT 端点用的是 `media:read` 权限位。按 `internal/auth/middleware.go:46-58` 的实现，`RequirePerm(store, "media:read")` 只检查 `media:read` 权限，**任何持有读权限的登录用户**（包括只读成员角色）都能改自己的地图图标偏好与 UI 偏好。

**触发条件**：任意持 `media:read` 的账号调用 `PUT /user/ui-prefs`。

**影响**：**低**。两处改的都是**调用者自己的账户级偏好**（`user_id` 来自 token 上下文，非请求体），不涉及他人数据或系统配置。但违反最小权限原则，且与 `authed.PUT("/user/password", ...)` 等「写自己的东西用 authed 组即可」的惯例不一致——代码里其他账户级写端点（`/user/password`、`/user/app-password`）都没挂任何 perm 中间件。

**修复建议**（三选一，建议选第 1 个）：

1. 改挂 `authed` 组、不加 perm 中间件（与 `/user/password` 保持一致，最贴合项目惯例）：

```go
// 自己账户级偏好，任何登录用户均可读写（与 /user/password 同惯例）
authed.PUT("/preferences/map", geoH.PutMapIconPref)
authed.PUT("/user/ui-prefs", geoH.PutUIPrefs)
```

2. 若坚持要权限位，改用 `permWrite`。
3. 若偏好是全局的（不该是），则应移到 admin 组另设端点。

### L-2 错误文本回显：`agentllm.go:207`

**位置**：`src/backend/internal/agentllm/agentllm.go:207`

