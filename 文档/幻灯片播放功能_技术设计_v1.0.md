## 二、关键设计决策（含实测依据）

### 2.1 决策 1：视频的「间隔」语义 —— 这是最容易做错的一点

用户要求「视频播放不计算间隔秒数，播放完即播放下一个」。

**技术实现**：

```
照片：定时器 N 秒 → 下一张
视频：等 <video> 的 'ended' 事件 → 下一张（定时器不参与）
```

⚠️ **必须避免的实现错误**：用 `setTimeout(间隔秒数)` 统一调度，然后靠「视频时长 > 间隔」兜底。这是错的 —— 视频时长不确定（可能 5 秒也可能 5 分钟），固定定时器会导致：
- 短视频还没播完就被切走
- 长视频播完后空等

**正确做法**：`ended` 事件驱动 + 一个「兜底看门狗」（视频时长超过预估 2 倍时强制切走，防 `ended` 不触发导致卡死）。

### 2.2 决策 2：缩略图必须走 blob 预加载（不能裸 `<img src>`）

**侦察发现**：`/media/:id/thumb` 挂在 `authed` 组（`main.go:247`），**需要 JWT**。

所以：

```html
<!-- ❌ 不可行：会 401 -->
<img :src="`/media/${id}/thumb?size=lg`" />

<!-- ✅ 可行：复用现有 fetchBlobUrl（mediaLoader.js 已有） -->
<img :src="await loadThumbUrl(item, 'lg')" />
```

**复用现有资产**：`mediaLoader.js` 的 `loadThumbUrl(item, size)` 已实现 fetch + blob URL + LRU 缓存（`MAX_CACHE=600`）+ `revokeObjectURL` 回收。**直接复用，不重写**。

### 2.3 决策 3：预加载策略 —— 前后各 2 张，避免切换白屏

幻灯片的体验成败在**切换是否露白**。

| 策略 | 内存 | 切换体验 | 判定 |
| --- | --- | --- | --- |
| 只预载当前 | 1 张 | ❌ 切换必白屏（网络 100ms+） | ❌ |
| **前后各 2 张** | ~5 张 blob（lg 约 200KB/张 = 1MB） | ✅ 基本无白屏 | ✅ **选定** |
| 全量预载 | 500 张 = 100MB | ✅ 但首次等 30s+ | ❌ |

**实现**：维护一个 `preloadQueue`，当前位置前进 2 / 后退 2 时静默 `loadThumbUrl`（该函数自带 dedupe，不会重复请求）。

**视频**不预载 blob（可达数百 MB，`MAX_FULL_CACHE` 只留 4 条）——改为**只预取元数据 + 延迟 src**：切到视频时才设 `src`，靠 `<video preload="metadata">` 先拿时长。

### 2.4 决策 4：转场效果用 GSAP（项目已有）

侦察确认项目已用 GSAP，且有**正确的生命周期范式**（`gsap.context()` + `onBeforeUnmount` 清理，见 `TimelineView.vue:89-92`）。

**必须复用这个范式**，否则转场动画会在组件卸载后继续跑（项目已有明确注释警告过这个坑）。

**转场清单**（GPU 友好优先，避免 layout 抖动）：

| 转场 | 实现 | 备注 |
| --- | --- | --- |
| 无（默认） | 直接切换 | 零风险 |
| 淡入淡出 | `opacity 0→1` | 最安全 |
| 横向滑动 | `x: ±40px` + opacity | |
| 缩放 | `scale 1.04→1` | |
| 旋转 | `rotate ±1.5deg` | |
| 模糊消散 | `filter: blur()` | ⚠️ 开销大，移动端慎用 |

**「随机」模式**：每次切换时从清单里随机挑一个（不重复上一个）。

### 2.4b 决策：三种排序的实现（**「倒序」是对当前数组反转，不重查**）

```js
// ⚠️ 关键：「倒序」= 当前显示顺序的反转，不是「按时间倒序重新查库」
//     因为当前显示顺序可能已被视图改过（筛选后的子集、用户选的排序、搜索结果顺序）。
//     反转当前数组才能保证「屏幕上是 A B C D，幻灯片就从 D C B A 播」。
function orderList(items, order) {
  if (order === 'forward') return items.slice()
  if (order === 'reverse') return items.slice().reverse()   // ← 当前显示顺序反转
  if (order === 'shuffle') return shuffle(items)            // Fisher-Yates
  return items.slice()
}
```

| 模式 | 实现 |
| --- | --- |
| 顺序 | `items.slice()` |
| **倒序** | `items.slice().reverse()` —— **反转当前数组**（已确认） |
| 随机 | Fisher-Yates 洗牌（避免 `sort(() => Math.random()-0.5)` 的偏斜 bug） |

⚠️ **必须 `slice()` 复制**再反转/洗牌 —— 直接 `reverse()` 会**原地改掉视图的 items**，
导致用户退出幻灯片后列表顺序被永久改乱。

### 2.5 决策 5：数据来源 —— 复用各视图已有的 items，不重新查

**侦察结论**：5 个视图的数据源已存在，且**可能分页**：

| 视图 | 数据源 | 分页情况 |
| --- | --- | --- |
| 时间轴 | `gridRef.value?.items` | 分页（cursor） |
| 相册详情 | 自己的 items | 分页 |
| 人物 | items | 待核实 |
| 地点 | items | 待核实 |
| 空间 | items | 待核实 |

**设计**：`SlideshowLauncher` 只接收一个 `items` 数组（调用方传自己的），组件内部不查数据。

⚠️ **分页的坑**：若某视图只加载了前 50 条，幻灯片就只播 50 张。**处理**：启动时检查 `items.length` 与该视图的「总数」，若未加载完则提示「仅播放已加载的 N 张」并提供「加载全部」选项（复用现有的加载更多逻辑）。**不静默截断**。

## 三、组件设计

### 3.1 架构

```
SlideshowLauncher.vue        ← 挂在 5 个视图的工具栏（按钮 + 图标）
   ↓ 点击
SlideshowSettingsDialog.vue  ← 设置面板（间隔/顺序/转场/范围确认）
   ↓ 确认
SlideshowPlayer.vue          ← 全屏播放器（核心）
   ├─ 复用 mediaLoader.loadThumbUrl / loadFullUrl
   ├─ 复用 GSAP（gsap.context 范式）
   └─ useSlideshow.js        ← 播放状态机（可单测的纯逻辑）
```

**关键设计**：把播放逻辑抽成 `useSlideshow.js` 纯逻辑 composable，**不含 UI**，这样排序/计时/边界能用 Vitest 直接测（项目纪律：逻辑要能单测）。

### 3.2 播放状态机

```js
// useSlideshow.js 的核心状态
{
  list: [],            // 媒体数组（已排序）
  index: 0,            // 当前位置
  playing: true,        // 播放中 / 暂停
  kind: 'photo',       // 当前项类型
  timer: null,         // 照片定时器
  watchdog: null,      // 视频兜底
  settings: { intervalSec, order, transition, transitionRandom }
}
```

**状态转移**：

| 事件 | 动作 |
| --- | --- |
| 定时器到期（照片） | `next()` |
| `<video>` `ended` | `next()` |
| `next()` / `prev()` | 清定时器 → 切换 → 重置（视频则设 src） |
| 暂停 | 清定时器 + `video.pause()` |
| 继续 | 照片则重启定时器；视频则 `video.play()` |
| 退出 | 清所有定时器 + 释放 blob 引用 + 卸载组件 |

**边界处理**（必须显式处理，否则是明显 bug）：

| 边界 | 行为 |
| --- | --- |
| 播到最后一张 | 停止并提示「已播完」，**不自动循环**（可提供「循环」开关） |
| 列表为空 | 入口按钮**禁用**（不给点进去看空屏） |
| 列表只有 1 张 | 允许播放，禁用前进/后退 |
| 视频加载失败 | 显示错误占位 + 3 秒后自动下一张，**不卡死** |
| 快速连按 next | 用 `seq` 代次守卫丢弃过期操作（项目已有此范式） |

### 3.3 键盘控制（桌面端必需）

| 键 | 动作 |
| --- | --- |
| `空格` | 暂停/继续 |
| `←` / `→` | 上一张/下一张 |
| `Esc` | 退出 |
| `F` | 全屏切换 |

移动端：点击画面中央切换控制条显隐（3 秒自动隐藏）。

## 四、设置面板的字段

| 字段 | 类型 | 默认 | 范围 |
| --- | --- | --- | --- |
| 间隔秒数 | number | 5 s | 1–60 s（**仅照片生效，需在 UI 明确标注**） |
| 顺序 | radio | 顺序 | 顺序 / 随机 / 倒序 |
| 转场 | select | 无 | 无 / 淡入淡出 / 横向滑动 / 缩放 / 旋转 / 模糊 |
| 转场随机 | checkbox | off | 开启后从清单随机（不重复上一个） |
| 循环 | checkbox | off | 播完是否从头 |
| 范围 | readonly | — | 显示「将播放 N 张（照片 X / 视频 Y）」 |

**UI 特别注意**：因为「间隔只对照片生效」是反直觉的，设置面板必须在间隔秒数旁边**直接标注**，例如：

> 间隔秒数（仅照片生效，视频播完自动切换）

否则用户会以为视频也被 5 秒打断——这是高频困惑点。

**设置持久化**：存 `localStorage`（键 `pano.slideshow.settings`），跨会话保留。

## 六、背景音乐（追加需求）

### 6.1 需求

| # | 需求 |
| --- | --- |
| 1 | 播放时可**选一首**背景音乐 |
| 2 | **播放不结束就循环播放**（单曲循环） |
| 3 | 背景音乐**用户自己上传** |
| 4 | 已上传的可**再次选用** |
| 5 | 可**管理删除**，**支持批量操作** |

### 6.2 数据模型

**新表 `slideshow_track`**（迁移 `00049`）：

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | UUID PK | |
| `space` | 空间枚举 | **复用现有 `mediascope` 空间体系**，不另造 |
| `owner_id` | UUID FK users | 上传者 |
| `filename` | VARCHAR(255) | 原始文件名（展示用） |
| `rel_path` | TEXT | 相对 `data/media` 的路径（**不存绝对路径**） |
| `mime` | VARCHAR(64) | audio/mpeg 等 |
| `size_bytes` | BIGINT | 用于配额与列表展示 |
| `duration_sec` | NUMERIC(8,2) | 时长（ffprobe 探测） |
| `created_at` | TIMESTAMPTZ | |

**索引**：`(space, created_at DESC)`（列表按上传时间倒序）。

⚠️ **不使用 media 表**：BGM 不是媒体，不该进 `media`（否则会污染时间线、缩略图、统计、转码队列）。

### 6.3 API 端点（4 个）

| Method | Path | 权限 | 说明 |
| --- | --- | --- | --- |
| `GET` | `/slideshow/tracks` | `media:read` | 列出当前空间的 BGM（含 duration/size） |
| `POST` | `/slideshow/tracks` | `media:write` | 上传（multipart），服务端探测时长 |
| `DELETE` | `/slideshow/tracks/:id` | `media:write` | 单条删除（**软删**，与媒体一致） |
| `POST` | `/slideshow/tracks/batch-delete` | `media:write` | **批量删除**（传 id 数组） |
| `GET` | `/slideshow/tracks/:id/stream` | `media:read` | **inline 流式播放（必须支持 Range）** |

⚠️ **可见性约束**（项目红线：作用域唯一真源是 `internal/mediascope`）：
- 列表只返回调用者有 `media:read` 的空间
- 删除时校验 `owner_id` 或空间权限，**不能删别人的**
- stream 端点同样走作用域判定，未授权 → 404（非 403，与项目既有口径一致）

### 6.4 关键技术决策

#### 决策 A：Range 支持是**硬需求**（侦察发现项目已有范式）

**侦察结论**：全仓只有 `shares` 包用了 `http.ServeContent`，且带明确注释：

> `②http.ServeContent 原生支持 Range（拖动进度必需），c.File 系不支持。`（`shares/handlers.go:515`）

**BGM 播放器必须能显示进度/拖动** → 必须用 `http.ServeContent` + `Content-Disposition: inline`。
**照抄这个范式**，不要用 `c.File`（这是项目已经踩过的坑）。

#### 决策 B：格式支持与探测

| 项 | 决定 | 理由 |
| --- | --- | --- |
| 支持格式 | `mp3` / `m4a` / `aac` / `flac` / `ogg` / `wav` | 浏览器 `canPlayType` 全覆盖；flac 渐进增强 |
| 大小上限 | **单文件 20 MB** | 20 分钟 mp3 约 20MB；超大文件对 `blob:` 预加载不友好 |
| 时长上限 | **30 分钟** | 幻灯片场景超长 BGM 无意义 |
| 时长探测 | 服务端 `ffprobe` | 前端 `Audio` 元数据不可靠（部分格式不报） |
| 存储格式 | **保留原格式，不转码** | BGM 不参与播放兼容性转码；转码会损失音质且耗时 |

⚠️ **浏览器不支持的格式**（如某些 wav 变体）：列表里**仍显示但标注「浏览器可能无法播放」**，
选中后若 `audio.play()` reject，给出明确提示而非静默失败。

#### 决策 C：音频与媒体的**竞争关系**（必须让用户选）

视频自带音轨。若同时播 BGM，会「两个声音叠着」。

**处理**：设置面板加一个选项：

| 选项 | 行为 |
| --- | --- |
| **媒体原声优先**（默认） | 视频播放时 BGM **自动压低**（`audio.volume = 0.15`），照片段 BGM 恢复 |
| BGM 独占 | 视频静音（`video.muted = true`），全程 BGM 满音量 |
| 关闭 BGM | 不用背景音乐 |

⚠️ 默认「媒体原声优先」而非「BGM 独占」—— 用户放 BGM 通常是想要氛围，但把视频原声完全吞掉
往往是意外的。压低是折中，且要在 UI 上可见（音量图标）。

#### 决策 D：单曲循环（用户明确要求）

`HTMLAudioElement.loop = true` —— 浏览器原生支持单曲循环，**不需要自己计数**。

⚠️ 但**换曲**时需重置 `currentTime = 0`（某些浏览器 loop 后 `currentTime` 累积）；
且换曲要在 `canplay` 事件后再播，避免连续快切时的竞态（用 `seq` 守卫，项目已有此范式）。

### 6.10 音裁剪（掐头去尾）—— 用户可选

#### 需求

| 项 | 内容 |
| --- | --- |
| 可选性 | **用户可选** —— 默认不裁；界面提供裁剪入口 |
| 时机 | ① 上传后可立刻裁 ② 列表中随时裁 ③ 裁剪后仍可再裁（**新曲**） |
| 结果 | **裁剪段作为独立曲目**入库，可与原曲并列选用 |

#### 实测数据（115，4 核，决定技术选型）

裁剪 15 秒片段（源 60s mp3）：

| 方案 | 耗时 | 产物 | 实际时长 | 偏差 |
| --- | --- | --- | --- | --- |
| **`-c:a copy`**（`-ss` 在 `-i` 前） | **101 ms** | 361 KB | 15.020 s | **0.020 s** |
| 重编码（`-ss` 在 `-i` 后 → aac） | 1308 ms | 255 KB | 15.000 s | 0.000 s |

裁剪 4 分钟源（贴近 20MB/30min 上限）：

| 方案 | 耗时 |
| --- | --- |
| `-c:a copy` | **< 1 s**（见日志） |
| 重编码 | **9374 ms** |

**关键结论**：

1. **`-c:a copy` 偏差仅 0.02 秒** —— 对 BGM 场景**完全听不出来**（mp3 帧长 26ms 是物理下限），却比重编码**快 13 倍**。→ **默认走 copy**。
2. 若用户把起点设在毫秒精度（如 30.5s），`-ss` 放 `-i` 后 + copy 的偏差是 **0.009 秒**（实测）—— 依然够用。
3. **精确切点 + copy 不可兼得**：真要 0 误差必须重编码（慢 13 倍）。→ 交互上**用「滑块取整到 0.1 秒」**，UI 显示的实际时长做服务端回填修正，用户不会察觉。

#### 技术方案

**裁剪命令**（服务端执行，遵循项目「ffmpeg 仅 subprocess」红线）：

```bash
# 默认：copy 模式（快，偏差 <0.02s）
ffmpeg -ss <start> -to <end> -i <src> -c:a copy -y <dst>
```

**为什么不在前端裁**：浏览器端 `decodeAudioData` + `encodeWAV` 只能输出 WAV（体积大 10 倍），
mp3 编码需引入 WASM 库（几百 KB + CSP 需 `wasm-unsafe-eval`）→ 得不偿失。服务端 ffmpeg 是正解。

#### 数据模型（在 `slideshow_track` 上扩展）

**不新建表** —— 裁剪段就是一条普通曲目记录：

| 列 | 值 |
| --- | --- |
| `parent_id` | 源曲 id（NULL = 原始上传） |
| `origin` | `upload` / `clip`（区分展示与审计） |
| `clip_start_sec` / `clip_end_sec` | 裁剪区间（原始上传为 NULL） |

⚠️ **裁剪段存为独立文件**（不是只存区间播放时裁）—— 理由：`ServeContent` 的 Range 在「虚拟裁剪」下
无法正确映射字节偏移（拖进度条会错位），且每次播放都要重新 seek。**物理裁剪是正确取舍**。

#### API 增补（第 6 个端点）

| Method | Path | 说明 |
| --- | --- | --- |
| `POST` | `/slideshow/tracks/:id/clip` | body `{start_sec, end_sec}` → 生成新曲目 |

⚠️ **必须服务端校验**（不信任前端）：
- `0 ≤ start < end ≤ 源时长`
- 裁剪后时长 ≥ **5 秒**（太短没有意义）
- 裁剪后大小 ≤ **20 MB**（与上传上限一致）
- **频率限制**：同一源曲的裁剪次数上限（如 5 次），防磁盘被裁剪副本撑爆

#### 前端 UI

`BgmPicker` 里每行加一个「裁剪」图标 → 打开裁剪对话框：

```
┌ 裁剪背景音乐 ─────────────────────┐
│ ▶ 试听（波形进度条，拖动定位）      │
│                                    │
│ 起点 [====|████████] 0:30          │
│ 终点 [==========|██] 3:45          │
│ 选中时长 3:15                       │
│                                    │
│ [取消]  [保存为新曲目]              │
└────────────────────────────────────┘
```

**波形图**是加分项（可用 `AudioContext.decodeAudioData` 画峰值，成本低收益高）。
不做波形也能工作（纯数值输入），但体验差很多。

⚠️ **对话框的时长是「源曲时长」**（服务端返回），不是裁剪后时长 —— 用户拖的是源曲位置。

#### 边界与降级

| 情况 | 行为 |
| --- | --- |
| 裁剪失败（copy 模式不适用某些格式） | **自动回退重编码** `-c:a aac -b:a 192k`；仍失败则报错并保留原曲 |
| 用户对同一曲反复裁 | 受频率限制（≤5 次/源曲） |
| 裁剪后删除源曲 | **级联删除**裁剪段（否则留下孤儿），或提供「保留裁剪段」选项 |
| 裁剪段占配额 | ✅ 是（用户已确认 BGM 占配额）—— 裁剪副本也占 |
