### ⚠️ 本轮挖出并修复的三个真实缺陷（均已复现→修复→复验）

## 八、T6.2 续：离线超时任务重派 + 心跳与任务执行解耦 —— ✅ 已交付并验证（`d2e2a4b`）

### ⚠️ 先修了一个**掩盖在协议之下的真实缺陷**：长任务会挡住心跳

原 `pollAndRun` 在返回前 `wg.Wait()`，于是 **tick 的耗时 = 最慢任务的耗时**，而心跳只在每个 tick 开头发一次。
后果不是"状态显示不准"这么轻：**一个跑得比离线阈值（180s）更久的转码，会让这个仍在干活的节点被判为
offline**，其名下 running 的任务随即被回收给别的节点 → **两个节点同时转码同一条媒体、产出互相覆盖**。
所以必须先解耦，重派机制才谈得上安全。

- `agent.go`：主循环只**派发**不等待（并发仍由 `sem` 信号量与 `pollQuota` 约束）；
  停机 `drain` 改用持久 `WaitGroup` + 超时，并以 `defer` 覆盖**所有**退出路径（原来显式调用会漏掉
  "循环顶部发现已取消"那条路径）
- `agent.go`：结果回传改用 `context.WithoutCancel` + 3s 超时 —— 否则停机时**已完成**的结果会被静默丢弃，
  任务白卡在 running 直到回收阈值，等于把做完的工作再跑一遍

### 重派策略（三问的答案）

| 问题 | 决定 | 理由 |
|---|---|---|
| **running 多久算僵死** | 判据是**节点心跳**，不是任务已运行时长；阈值 `2 × offlineAfter`（默认 360s） | 心跳已与任务执行解耦 → 健康节点跑几小时的大转码也不会被误回收；只有"节点不再报到了"才回收。比离线判定更保守，因为误回收（两节点写同一份产出）远贵于晚回收 |
| **谁触发** | **惰性**：节点来拉任务时顺带回收（`Poll` 先回收再认领），不引入常驻定时任务 | 与离线判定"只在查询侧做"的既有选择一致。没有节点来拉任务时，回收出来的任务也没人执行；反之只要有健康节点轮询，它每轮都会把僵尸任务捞回队列 |
| **原节点回传怎么处理** | 分两种：任务**仍无人持有**（已被回收但还没被领走）→ **接受**，避免让别的节点白跑；任务**已被别的节点领走** → **拒绝** | 前者是把做完的工作认下来，后者防止两个节点互相覆盖产出 |

另：管理员**显式下线**（`status_locked` + `offline`）的节点，其任务**立即**可回收（人的明确意图，不必等心跳超时）；
`COALESCE(last_heartbeat, created_at)` 给"刚登记、还没发过首次心跳"的节点等长宽限期。

### 结果回传的两道守卫（`submitResultSQL`）

1. **终态守卫** `status NOT IN ('done','failed')`：终态不可改写。否则一条延迟到达的重复回传能把已 done 改成 failed
2. **归属守卫**收紧为两分支（本节点持有 ‖ 已回收且无人持有），排除"已被别的节点领走"

回传命中终态返回 **409 `JOB_FINALIZED`**（与 404 分开：前者是"世界变了"的正常竞态，后者是"任务 id 记错"要查 bug）。
落空时反查一次任务状态以区分两者。

**验证**：`verify_reclaim.py` **37 项全 PASS** ——
认领 ✅ ｜ **健康节点不得抢走他人任务（回收的反例）** ✅ ｜ 心跳超时→回收并重派 ✅ ｜ 强制下线→立即回收 ✅ ｜
迟到回传被接受 ✅ ｜ 终态守卫 409 ✅ ｜ 归属守卫 404 ✅ ｜ 不存在任务 404 ✅ ｜ status 非法 400 ✅ ｜
**既有 17 行 `transcode_jobs` 逐行未变 + hls pending 不变** ✅ ｜ 清理 0 残留 ✅ ｜ 回归 faces=69 / media=93 / health=200 ✅

### 9.3 任务认领次数上限（迁移 00022，`27f3aab`）

§八 引入的回收重派**没有次数上限**：一个反复"领了任务就死"的节点会让同一条任务被无限重派，
每次白烧一遍算力，而管理端看到的是"一直在处理中"。

| 项 | 内容 |
|---|---|
| 迁移 00022 | `transcode_jobs.attempts INTEGER NOT NULL DEFAULT 0`。⚠️ `NOT NULL DEFAULT 0` 是必须的：缺默认值会让存量 17 行变 NULL，而认领条件 `attempts < 上限` 对 NULL 求值为 NULL（非 true）→ **这些任务再也领不到** |
| 计数时机 | **认领时**自增（`pollJobsSQL`）+ 认领条件加 `attempts < $4`。放在认领而非回传：一个"领了就崩"的节点永远不会回传，只有认领时计数才抓得住它。同时回传 `attempts`（`JobSpec.Attempts`），节点日志能直接打出"第几次尝试" |
| 回收不重置 | `attempts` 记的是"被领走过几次"而非"这一轮跑了多久"，故上限语义与**任务时长解耦**：跑 3 小时的长转码只要节点活着就不会被回收，attempts 停在 1 |
| 结算 | `exhaustJobsSQL` 把"已达上限且无人持有"的 pending 任务判 failed。**必须做**：认领条件含 `attempts < 上限`，这类任务再也不可能被领走，不判失败就永远卡在 pending（管理端看到"排队中"、实际"永远不动"，比 failed 难查得多）。守卫 `node_id IS NULL` 确保不碰正在跑的任务 |
| 顺序 | `ReclaimStale` 改为「先回收、再结算」，返回 `ReclaimResult{Requeued, Exhausted}`。顺序不能反：回收把 running 放回 pending，结算才可能看到本轮刚释放出来的那些 |
| 配置 | `COMPUTE_MAX_ATTEMPTS`（默认 3，与 TDD §6.1「3 次未收到心跳 → offline」同源）；非法或 <=0 一律回落默认 —— 0 会让认领条件恒假、任何任务都领不到 |

**验证**（`verify_reclaim.py` **48/48 PASS**，含新增 N 段）：让一条任务在 nodeE/nodeF 之间
反复"领了就死" → `attempts` 1→2→3 → 第 3 次僵死后被结算为 **failed** 且**不再被任何节点认领**。

⚠️ N 段用了一对**专属节点**：起初复用 nodeA/nodeB，结果"让它们僵死"把它们名下的**其它测试任务**
也回收了，那些任务按 `created_at` 排在前面被领走，断言看似"上限逻辑坏了"——实为测试设计缺陷。
已加前置守卫（N 段开始前断言无其它 pending+noop），把这类污染变成一条明确的失败。

### 9.4 NVENC 硬编接口 + 自动回退软编（`39253e4`）

**先做了一次环境侦察，结论直接决定实现方式**：

| 环境 | 结论 |
|---|---|
| 本机 Windows | ffmpeg 列出 `h264_nvenc`/`hevc_nvenc`，但**没有 NVIDIA 卡** → 实际编码以 `Cannot load nvcuda.dll` / 退出码 127 失败 |
| 测试服 192.168.1.115 | 无显卡、无 nvidia docker runtime；transcode-worker 容器里的 ffmpeg 是 Alpine 构建，**只启用 vaapi/vdpau/libvpl，没有 `--enable-nvenc`** |
| `pano-api` 镜像 | **根本没有 ffmpeg** |

也就是说：**当前没有任何环境能真正跑通 NVENC**。这决定了实现必须把"硬件路径不可用"当作
**一等公民**来设计，并且验证方式只能是**证明回退可用**。

| 项 | 内容 |
|---|---|
| 编码器抽象 | `ffmpeg.VideoEncoder`（`libx264` / `h264_nvenc`）+ `HLSArgsEnc`；`HLSArgs` 保留原签名并委托软编，**默认路径逐字节不变**（有断言） |
| ⚠️ preset 不通用 | x264 用 `veryfast`，nvenc 用 `p1..p7`；把 veryfast 传给 nvenc 会直接报 `Undefined constant or missing '(' in 'veryfast'`。已集中映射并断言"不许混用"——**这个错只在有卡机器上才暴露**，正是开发机最难发现的一类 |
| 未知取值 | 一律回落软编（不因一个配置笔误让每个任务都失败） |
| **自动回退** | `TranscodeHLS` 在硬编失败时**自动回退软编重跑一次**；两趟都在开头清 outDir（否则硬编半成品与软编产出混在一起 → 花屏/时长异常）。用"任何失败都回退"而非"匹配 stderr 错误串"：stderr 文案随 ffmpeg 版本/构建变化，靠匹配字符串是脆的；而回退无论如何都会再跑一次软编，若真是内容问题软编同样失败并报出软编的错误，掩盖原因的代价接近零 |
| 选择规则 | `EncoderForDevice(device, hasNVENC)`：**两个输入都看**。只看 device → `-device cuda` 在无卡机器上每次转码都先失败一次；只看 hasNVENC → 会占用运维显式让给别的任务的 GPU（`-device cpu`）。规则：显式非 cpu **且** 探测到 NVENC 才硬编 |
| 装配时机 | `cmd/nodeagent` 在 `NewAgent`（内部跑 nvidia-smi 完成能力探测）**之后**决定编码器，用**真实探测结果**而非配置字面值 → 配置写 cuda 但机器没卡时自然落到软编，节点照常上线（双接口原则：要求 GPU 而机器没有 = 降级，不是起不来） |
| 缩放仍在 CPU | 只有编码走硬编，`force_divisible_by=2` 取偶与分辨率阶梯完全复用既有实现，不必再维护一套 `scale_cuda` 变体 |

**验证**（本机实测走了**真实的回退分支**）：
```
转码 ... 编码器=h264_nvenc
硬件编码 h264_nvenc 未能完成（media=...），回退软编 libx264 重试一次: HLS 转码(h264_nvenc): ffmpeg 退出码 4294967295
转码 ... 编码器=libx264
回退路径产出：master + 1 个分片
```
产出完整（master + 分片都在），证明回退**不是**"吞掉错误留下半成品"。
该测试在有可用 NVENC 的机器上会走硬编分支，断言（成功 + 产出完整）依然成立，故无需为环境分叉。

**解除 NVENC 真机验证需要的条件**（缺一不可）：
① 有 NVIDIA 卡且驱动可用；② 该机器的 ffmpeg **编译时启用了 nvenc**（发行版自带常见不含；
需自编译或换用带 nvenc 的构建）；③ 若是容器，需 `--gpus`/nvidia runtime 把设备透进去。
代码侧已就绪，届时只需在有卡节点上以 `-device cuda` 启动并观察日志里的 `encoder=h264_nvenc`。

⚠️ 收尾：本次 NVENC 相关改动**未**做任何"为了让它看起来能跑"的妥协 —— 没有硬编可测就不假装测过，
只交付了"能回退"这一可验证的部分，并把上述前提条件写进登记簿。
