| 原则 | 说明 |

## 三、Phase 0 — 基础设施与合规前置（P0）

> 全部任务无业务代码依赖，是整个项目的地基。建议首轮整包执行。

### T0.1 开发环境核验 【P0 · 0.5 人日 · 依赖：无】

- **目标**：确认新电脑具备全栈开发环境
- **内容**：Docker Desktop（WSL2 后端）、Go 1.26+、Node 20+、ffmpeg 6 静态构建（需含 NVENC）、Git
- **验收**：
  - When 执行 `docker version / go version / node -v / ffmpeg -version`，全部正常输出版本号
  - When 执行 `ffmpeg -encoders`，列表中**必须**包含 `h264_nvenc` / `hevc_nvenc`

### T0.2 Docker Compose 基础编排 【P0 · 1 人日 · 依赖：T0.1】

- **目标**：一键拉起数据层三服务
- **文件**：`docker-compose.yml`、`.env.example`
- **服务**：`postgres:16`（启用 postgis + pgvector + pg_trgm 扩展）、`valkey:7-alpine`、`minio`
- **验收**：
  - When `docker compose up -d`，三个服务 60s 内全部 healthy
  - When 执行 DDL v1.1 全量脚本，psql 无报错、30 张表建成
  - When `valkey-cli PING`，返回 `PONG`

### T0.3 Valkey 许可替换验证 【P0 · 1 人日 · 依赖：T0.2】（README 续作建议 #1 前半）

- **目标**：证明 Valkey 对 Redis 的功能等价，消除 RSALv2/SSPL 商业化风险
- **文件**：`src/backend/internal/queue/`（Go 队列封装 + 测试）
- **内容**：
  - go-redis 客户端连通与连接池
  - 队列原型：入队 / 消费 / ack / 失败重试（指数退避 ≤3 次）/ 延迟任务（BullMQ 等效语义）
  - 令牌桶限流原型（对应 TDD §7 限额设计：登录/IP/API）
- **验收**：
  - AC-01：When `docker compose up`，Valkey 容器 5s 内 healthy
  - AC-02：When 发送 PING/SET/GET/DEL/HSET/HGET，响应与 Redis 协议一致
  - AC-03：When 生产者入队任务，消费者 2s 内拉取并处理
  - AC-04：If 任务失败且配重试，队列按指数退避重试 ≤3 次后进入死信

### T0.4 ffmpeg subprocess 封装层 【P0 · 1-2 人日 · 依赖：T0.1】（README 续作建议 #1 后半）

- **目标**：GPL 安全的 ffmpeg 调用封装（不链接 libav*，仅进程调用）
- **文件**：`src/backend/internal/ffmpeg/`（runner.go / parser.go / types.go + 测试）
- **内容**：
  - `exec.CommandContext` 进程管理：超时、取消、SIGTERM 优雅终止
  - `-progress` 管道输出解析：已处理时间 / 帧数 / 码率 / 速度 / 剩余时间
  - 结构化错误：退出码 + stderr 尾部 N 行 + 执行时长
  - 预设封装：缩略图 WebP 三档（SM/MD/LG）、HLS 多码率、360 equirect 元数据保持
- **验收**：
  - AC-05：When 执行转码，子进程正确启动、stdout/stderr 实时捕获、超时后 SIGTERM
  - AC-06：When ffmpeg 输出 progress，解析器提取时间/帧数/码率/剩余时间
  - AC-07：If 退出码非 0，返回结构化错误（退出码 + stderr 尾部 + 时长）
  - 集成：一段 H.265 样片转 H.264 成功，progress 解析正确

### T0.5 许可合规扫描 【P0 · 0.5 人日 · 依赖：T0.3、T0.4 go.mod 稳定】

- **目标**：依赖许可证审计，落实审查修正清单的行动项
- **内容**：go-licenses 扫描 Go 依赖；输出 `licenses.csv` 存档
- **验收**：
  - AC-09：扫描报告中**无** RSALv2/SSPL/GPL/AGPL 直接依赖（ffmpeg 仅二进制调用不在此列）

## 四、Phase 2 — 核心差异原型（P0，技术风险最高）

> 对应 README 续作建议 #2、#3。原型为独立可运行物，不依赖后端骨架，验证通过后再集成。

### T2.1 360 播放引擎原型 【P0 · 3-5 人日 · 依赖：T0.4】（README 续作建议 #2）

- **目标**：独立静态原型页，验证 360 视频交互全链路
- **文件**：`prototypes/360-player/`（独立 HTML/JS）
- **内容**（严格对照 TDD §4.2 六个子系统）：
  1. **球面渲染**：`SphereGeometry(500, 64, 32)` 内翻（`scale.z=-1`）+ ShaderMaterial UV.y 翻转 + `VideoTexture(flipY=false)` + 球心相机 `fov=75, near=0.1, far=1000`
  2. **基础交互**：拖拽/触摸 yaw/pitch；双指捏合 FOV 缩放
  3. **陀螺仪**：iOS 13+ `DeviceOrientationEvent.requestPermission()` 手势按钮触发；拒绝时降级纯拖拽
  4. **WebXR**：`isSessionSupported('immersive-vr')` → 用户点击 → `requestSession` → `sessionend` 清理资源恢复标准渲染；会话中断自动暂停
  5. **hls.js ABR**：`LEVEL_SWITCHED` 自适应；错误恢复（网络错误指数退避×3 / 媒体错误降档 / 不可恢复保留最后帧+提示）
  6. **移动端性能**：纹理上限 4096（4K equirect 降采样策略）、fps 监测 <30 自动降档、`powerPreference='high-performance'`
- **测试内容**：用 T0.4 封装生成多码率 HLS 测试流（360 样片 → 1080p/2K/4K 三档 master.m3u8）
- **验收**：
  - AC-10：桌面拖拽/缩放流畅（≥30fps）
  - AC-11：手机（iOS+Android）陀螺仪跟随视角，权限拒绝后降级可用
  - AC-12：弱网（限速 2Mbps）下 HLS 自动降档不卡死
  - AC-13：If 有 VR 头显，`immersive-vr` 会话进入左右分屏头追

### T2.2 地图模式原型 【P0 · 2-3 人日 · 依赖：T0.2】（README 续作建议 #3）

- **目标**：验证 bbox 聚合 + 坐标转换 + 双底图源三大技术点
- **文件**：`prototypes/map-mode/`（MapLibre 前端）+ 后端 `/map` 端点雏形
- **内容**：
  - PostGIS `geometry(Point,4326)` 写入批量测试数据（含中国境内点位）
  - supercluster 按 bbox+zoom 服务端聚合（对照 TDD §3.7 / API §7 `/map/items`）
  - **WGS-84 → GCJ-02 转换层**（应用层转换，不落库 —— PRD/TDD 明确约束）
  - 瓦片反代代理：中国走高德、国际走 OSM，前端不暴露 key（`system_map_config.china_api_key_enc` 加密存储的简化版）
  - MapLibre 前端：世界地图默认视野、城市级缩放、聚合计数高亮（照片最多城市优先）
- **验收**：
  - AC-14：When 请求 `/map/items?bbox&zoom`，返回按 zoom 聚合的点位簇
  - AC-15：同一 WGS-84 点位在高德底图上的显示位置正确（GCJ-02 偏移已应用）
  - AC-16：底图可在中国（高德）/国际（OSM）间切换，国界配置生效

## 十一、待确认问题（附提出原因）

> 以下问题影响执行序列与首日任务，请您判断后我按答案推进。

**Q1. 执行顺序确认** —— README 续作建议的顺序是「Valkey→360 原型→地图原型→迁移工具」（原型验证优先）。本计划遵循此顺序。另一种做法是 Phase 1 后端骨架先行、原型后移（工程连续性更好，但技术风险验证延后约 1 周）。
*提出原因：两种顺序各有合理性，且影响首周做什么，需要您拍板。我建议按 README 既定顺序。*

**Q2. 新电脑开发环境状态** —— Docker Desktop / Go / Node / ffmpeg 当前安装情况如何？
*提出原因：决定 T0.1 的实际工作量与首日可执行任务；若已装好可直接进入 T0.2。*

**Q3. 本机 GPU 情况** —— 本机是否有 NVIDIA 显卡？
*提出原因：NVENC 硬件编码与 360 ABR 多码率转码测试依赖 N 卡。若无，转码验证降级为软编（libx264），NVENC 留到 GPU 算力节点部署时验证；若有，T0.4 直接覆盖硬件编码路径。*

**Q4. 推进节奏** —— 单线程顺序推进（一次一个任务，验收后下一个），还是允许并行（如 T0.3 与 T0.4 同开、原型期前后端两线并行）？
*提出原因：影响排期密度与会话组织方式；并行更快但上下文切换多，单线程更稳。*
