## #5 微信陀螺仪：证书问题完整解决方案

### 5.1 根因分析

当前自签证书（openssl 生成，无 CA 链）在微信内置浏览器中：
- 微信 X5/XWeb 内核对证书校验**比系统浏览器更严格**，部分版本直接阻断加载或加载后 `window.isSecureContext=false`
- `isSecureContext=false` → `deviceorientation` 事件**静默不触发**（这正是「系统浏览器正常、微信失效」的最可能根因，等诊断截图确认）

### 5.2 证书问题排查步骤（确认根因用）

1. 微信内打开 `https://192.168.1.117:8443` 能否正常加载页面？（不能 → 证书被微信直接拦截）
2. 能加载时，打开页面「诊断」按钮看 `isSecureContext`：`false` → 确认证书信任问题；`true` 但事件 0 次 → 转向鸿蒙微信 App 级传感器权限（设置→应用→微信→权限→传感器）
3. 两项都正常但数据全 null → 内核数据缺陷，走降级策略（已有看门狗）

### 5.3 解决方案 A：Cloudflare Quick Tunnel（推荐，零配置）

**前提**：本机可访问 Cloudflare（您已有 WARP 环境，天然满足）；无需域名、无需账号、证书由 Cloudflare 签发（公网受信）。

**步骤**：
1. 下载 cloudflared（Windows 单文件）：
   ```
   curl --ssl-no-revoke -L -o cloudflared.exe https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-windows-amd64.exe
   ```
2. 本地原型服务照常跑（`python serve_https.py 8443` 或 HTTP 8765 均可，隧道末端不校验本地证书）
3. 启动隧道：`.\cloudflared.exe tunnel --url http://localhost:8765`
4. 输出中取得 `https://<随机串>.trycloudflare.com` —— **该 URL 自带公网有效证书**
5. 微信内直接打开该 URL（无需安装任何证书）

**局限**：每次启动 URL 随机变化（测试够用）；长期固定域名需 Cloudflare 账号+域名（免费方案可做，需要时再配）。

### 5.4 解决方案 B：mkcert 本地 CA（隧道不可用时的备选）

1. `winget install FiloSottile.mkcert` 或下载 mkcert.exe
2. `mkcert -install`（根 CA 装入本机受信根）
3. `mkcert 192.168.1.117 localhost 127.0.0.1` → 新 cert.pem/key.pem 替换 prototypes/360-player/ 下旧文件
4. 把 `%USERPROFILE%\AppData\Local\mkcert\rootCA.pem` 传到华为手机：设置→安全→更多安全设置→加密和凭据→安装证书→CA 证书（HarmonyOS 4.2 路径近似）
5. Pico 4：浏览器对用户 CA 支持不稳定，此路不通时回到方案 A

### 5.5 替代验证法（不改证书的快速验证）

- **微信开发者工具**（PC 版）：可模拟微信 webview 打开 localhost（无证书问题），验证 JS 逻辑与权限申请流程；**局限**：PC 无陀螺仪硬件，只能验证代码路径，不能验证传感器数据
- **降级路径验证**：微信内 HTTP 打开（8765），陀螺仪必然不可用，可验证看门狗自动降级拖拽的体验闭环（这本身是验收项之一）

### 5.6 证书解决后的陀螺仪验证步骤

1. 微信打开隧道 URL → 点「陀螺仪 开」（iOS 内核会弹权限请求，鸿蒙 XWeb 直接监听）
2. 点「诊断」，核对：`isSecureContext: true` / `deviceorientation 触发 >0` 或 `absolute 触发 >0` / `全 null 数据: 0` / 最近值 αβγ 随手机转动变化
3. 转动手机：视角应跟随；方向偏移时点「校准」归零
4. 若事件 0 触发且 isSecureContext=true：查鸿蒙微信传感器权限（5.2 第 2 步）
5. 验收标准：视角跟随延迟可感 < 100ms、无漂移累积、降级与校准按钮行为正确

## #7 Worker 常驻化：根因与方案

### 7.1 根因分析

当前 indexctl/transcodectl worker 必须手工启动，原因是**生命周期管理缺位**，具体三层：
1. **进程模型**：worker 是 CLI 子命令（`go run ./cmd/indexctl worker`），以前台进程挂在 shell 会话上，会话结束即被回收（开发期多次出现 worker 随 agent 会话结束而死）
2. **无服务注册**：未在任何进程管理器中登记（Windows 无服务项、服务器无 systemd unit、Docker compose 无对应 service）
3. **设计时序**：TDD §8.1 部署架构本就规划 worker 作为常驻容器服务，当前 Phase 3/4 属开发期，服务化被有意推迟到 Phase 6

即：这不是缺陷，是「开发态 CLI」与「生产态服务」之间的规划间隙，但**开发期已产生实际影响**（新上传媒体缩略图滞留队列）。

### 7.2 可选方案对比

| 方案 | 前提条件 | 优点 | 缺点 | 适用 |
|------|----------|------|------|------|
| A. Docker Compose 加 worker 服务（**推荐**） | 服务器已跑 compose（现状满足）；需为 Go 程序写 Dockerfile（多阶段构建） | 与 TDD §8.1 最终形态一致；`docker compose up` 一键全栈；崩溃自动重启（restart: unless-stopped） | 首次需写 2 个 Dockerfile（约 30 行） | 开发+生产同源 |
| B. 服务器 systemd unit | 二进制 scp 到服务器 + 2 个 unit 文件 | 不依赖 Docker 构建；资源占用最小 | 与容器化部署架构分叉，Phase 6 要重做 | 临时过渡 |
| C. Windows 任务计划程序 | 本机开发期立即可做 | 零迁移成本，开机自启 | 绑定 PC 开机状态；与服务器部署无关 | 仅本机开发期 |
| D. NSSM 注册 Windows 服务 | 需下载 nssm.exe | 比任务计划更健壮（崩溃重启） | 引入第三方工具 | 不推荐（多余依赖） |

### 7.3 方案 A 实施步骤（推荐）

1. 写 `docker/worker/Dockerfile`（多阶段：golang:1.26 构建 indexctl+transcodectl → alpine 运行，ENTRYPOINT 按 SERVICE 环境变量分发）
2. docker-compose.yml 增加两个 service：`index-worker`（command: worker，挂载 ./data 卷 + FFMPEG_PATH 环境）与 `transcode-worker`（同构）；ffmpeg 需打入镜像（ffmpeg-static 或 apt 安装）
3. `docker compose up -d index-worker transcode-worker`
4. 验证：上传一张图 → 30s 内 thumbnail_sm 自动落库；对视频发转码 job → hls_master 自动回写
5. 前置注意：镜像内 ffmpeg 须含 libx264/webp（T0.1 已验证的 full build 参数集）；队列地址用 compose 服务名 `valkey:6379`

**预估工作量**：约 250-400 token（含验证）；建议并入 Stage 2 后或 Phase 6 前执行，您指定时机即可。
