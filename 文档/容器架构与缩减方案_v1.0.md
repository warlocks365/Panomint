# Panomint 容器架构与缩减方案 v1.0

> 日期：2026-09-25｜范围：默认 Docker Compose 栈的容器职责、依赖关系、缩减可行性与最优部署形态
> 数据来源：测试服 192.168.1.115 实测（`docker stats --no-stream` / `docker images`，空闲态快照，2026-09-25 14:35）；compose 定义以仓库 `docker-compose.yml` 为准
> 结论有效期：对 main @ `7c0fbb0`（v1.1.0）有效；架构演进后需复核

---

## 一、TL;DR

1. **当前默认栈是 11 个常驻容器**（另有一个 minio 属于 s3 可选项，默认不启动）。10/11 个容器不是"拆得太碎"，而是**单进程容器原则 + 双 worker 模型 + 有状态/无状态分离**三条设计决策的自然结果。
2. **真实成本比直觉低**：5 个 AI/业务容器共享同一个 `panomint-app` 镜像（磁盘只占 1.16GB 一份）；11 容器空闲态总内存实测 **≈1.06GiB**，其中约 550MB 是 AI 模型会话（CLIP/打标/人脸）的**必要驻留**，合并容器省不掉这部分。
3. **缩减可行，分四档**：sweep 四合一（11→8，小改）→ 队列 worker 二合一（8→7，注意特权面）→ web 并入 caddy（7→6，中改）。再往下并就要伤到 db/valkey，**强烈不建议**。
4. **1 个容器：技术可行，工程不值**。所需改动清单与风险清单见 §四.6。唯一说得通的场景是"1-2GB 内存小 NAS 求能跑"，但即便如此 db 也应独立。
5. **最优推荐**：产品默认**维持现状 11 容器**（隔离收益 > 容器数量焦虑）；为小内存 NAS 提供可选 **light profile ≈7 容器**（档 2+3），代码改动约 1-2 天，见 §五。

## 二、为什么是 11 个容器

### 2.1 职责全表

| # | 容器 | 镜像 | 职责 | 工作模型 | 空闲内存实测 |
|---|------|------|------|----------|------------|
| 1 | pano-db | panomint-db:1.0.0（PG16+PostGIS+pgvector） | 元数据/向量/空间查询，唯一有状态核心 | 常驻 | 100MiB |
| 2 | pano-valkey | valkey:8.0-alpine | 会话/限流/队列（thumb、transcode 两条队列）/缓存 | 常驻 | 12MiB |
| 3 | pano-api | panomint-app（1.16GB，与 4-6 共享） | REST API、鉴权、扫描导入、复制/软删/恢复、AI 检索入口 | 常驻 | 266MiB |
| 4 | pano-embed-worker | panomint-app（共享） | CLIP 向量生成（512 维语义搜索） | **清扫式**：每 30s 轮询 `embedding IS NULL` | 241MiB |
| 5 | pano-tag-worker | panomint-app（共享） | 照片打标（标签/描述） | **清扫式**：每 60s 轮询未打标行 | 262MiB |
| 6 | pano-phash-worker | panomint-app（共享） | 感知哈希（重复照片检测），纯 Go 无模型 | **清扫式**：每 30s 轮询 `phash_scanned_at IS NULL` | 6MiB |
| 7 | pano-faces-worker | panomint-app（共享） | 人脸检测+特征（YuNet+SFace，128 维） | **清扫式**：每 30s 轮询 `faces_scanned_at IS NULL` | 90MiB |
| 8 | pano-index-worker | panomint-worker（352MB） | 缩略图队列消费 + **F4 挂载执行器**（rclone FUSE，需 SYS_ADMIN+/dev/fuse） | **队列式**：消费 Valkey `q:*` | 48MiB |
| 9 | pano-transcode-worker | panomint-worker（共享） | 4K/360° 视频 HLS 转码（ffmpeg subprocess） | **队列式**：消费 Valkey 转码队列 | 15MiB |
| 10 | pano-web | panomint-web（54MB，nginx） | 前端静态资源 + API 同源反代（SPA 回退/缓存头/分块上传透传） | 常驻 | 7MiB |
| 11 | pano-caddy | caddy:2-alpine | TLS 终结/HTTPS 入口（环境相关层，证书挂载） | 常驻 | 39MiB |
| (12) | pano-minio | minio（**profile s3 可选**，默认不启动） | S3 对象存储后端（不用 S3 时存储走本地卷） | 按需 | — |

**合计空闲内存 ≈1087MiB**；CPU 全部 <1%（转码/AI 批处理时相应容器才拉升）。

### 2.2 三条设计决策（回答"为什么拆这么多"）

**① 单进程容器原则。** 每个组件都是编译好的 Go 静态二进制（或 nginx/caddy/PG），一进程一容器是 Docker 最佳实践：独立重启、独立日志（`docker logs pano-embed-worker`）、独立健康检查、独立 CPU/内存限额、独立崩溃域。11 容器 = 11 个互不拖累的故障单元。

**② 双 worker 模型，资源画像不同。** 这是拆分的核心理由：

- **队列式 worker**（index、transcode）：任务重（一段 4K 转 HLS 可跑几十分钟、CPU 打满），经 Valkey 队列分发，**可水平扩容**（`--scale transcode-worker=2` 分摊转码），崩溃只丢当前任务可重试。
- **清扫式 worker**（embed/tag/phash/faces）：不接队列，周期轮询 DB 里"还没处理过的行"，把扫描时间戳复位即等价于重新入队。它们**常驻 AI 模型会话**（embed 的 CLIP ≈240MB、tag ≈260MB、faces ≈90MB），与 API 的"低内存高响应"画像完全不同——分开才能让 API 在 AI 批处理时不受内存压力挤压。

**③ 有状态/无状态分离。** db/valkey 挂数据卷、有官方镜像的升级与健康检查逻辑；其余 9 个无状态可随时 `up -d` 重建。升级 API 时数据库不动，升级数据库时业务容器不感知。

### 2.3 成本的真相：11 容器 ≠ 11 份资源

- **磁盘**：容器 4/5/6/7 与 api 共享同一份 `panomint-app:latest`（1.16GB 磁盘上只存一份）；8/9 共享 `panomint-worker`（352MB 一份）。自定义镜像合计 ≈2.2GB，不是 11 份叠加。
- **内存**：≈1.06GiB 里，**约 550MB 是模型会话的必要驻留**——只要系统要做语义搜索/打标/人脸，这部分内存无论拆成几个容器都必须存在。合并容器能省的只是每份 Go runtime 的重复开销（每容器约 10-30MB）与容器本体开销，**总省幅约 50-100MB，不是 4×241MB 这种错觉算法**。
- 真正的"贵"不在容器数量，在 AI 模型本身——而这恰恰是单进程化后做**惰性加载+空闲卸载**的动机（见档 2）。

## 三、依赖关系图

```
                      ┌─────────────────────────── 用户 ───────────────────────────┐
                      │ HTTPS :443                        HTTP :8088（LAN/隧道回源）│
                      ▼                                                           ▼
                 ┌─────────┐   反代    ┌─────────┐                                 ┌─────────┐
                 │ caddy   │─────────▶│   web   │  nginx 静态 + /api 同源反代      │ (无)     │
                 └─────────┘           └────┬────┘                                 └─────────┘
                                            │ /api
                                            ▼
 ┌──────────┐   SQL    ┌─────────┐                                        ┌──────────────┐
 │ (minio)  │◀────────▶│   api   │──── 会话/限流/缓存 ────┐                │ 4×sweep worker│
 │ s3 可选  │          └────┬────┘                        │                │ embed/tag/   │
 └──────────┘               │                        ┌────▼─────┐          │ phash/faces  │
                            │                        │  valkey  │◀── 2条队列│  轮询 DB     │
                     读写   │                        └────┬─────┘   消费    └──────┬───────┘
                            │                             │队列                    │轮询
                      ┌─────▼─────────────────────────────▼──────┐          ┌──────▼──────┐
                      │                  db                      │◀─────────┤  (同左轮询)  │
                      │        PG16 + PostGIS + pgvector         │           └─────────────┘
                      └─────▲──────────────▲──────────────▲──────┘
                            │              │              │
                     index-worker    transcode-worker  sweep workers
                     (缩略图+FUSE挂载)  (ffmpeg HLS)     (AI 批处理)
                            │              │              │
                            └──────────────┴──────┬───────┘
                                                  ▼
                                     mediadata 卷（/data 媒体+缩略图+HLS）
                                     ——7 个无状态容器全部只读/读写共享
```

依赖要点：
- **db 是全栈根依赖**：除 caddy/web/valkey 外全部 `depends_on: db (service_healthy)`。
- **valkey 次之**：api（限流/会话）、index-worker、transcode-worker 依赖；4 个 sweep worker 不依赖 valkey（它们只轮询 DB）。
- **mediadata 卷**：api + 4 sweep + index + transcode 共 7 个容器挂载；db/valkey/caddy/web 不挂。
- **入口链**：caddy → web → api，两层反代（§四.4 解释为什么不并成一层）。

## 四、缩减可行性分档评估

> 前提澄清：minio 已是 profile 可选项，默认栈常驻 11 容器。以下分档均指常驻容器数。

### 档 1｜sweep 四合一：11 → 8（改动小，性价比最高）

**做法**：新建一个 `sweep-worker` 入口（单二进制、4 条 goroutine，或 entrypoint 顺序拉起 4 个既有二进制），embed/tag/phash/faces 四容器替换为一个容器。

- **改动量**：小。watch 循环逻辑已封装在既有二进制里，主要工作是 compose override 文件（`compose.light.yml`）+ 一个聚合入口；无需动 AI 代码。
- **收益**：省 3 份 Go runtime + 3 个容器开销（≈50-100MB 内存）；日志面从 4 个容器变 1 个。
- **进阶收益（单进程化才好做）**：模型会话**惰性加载**——某 sweep 空闲超 N 分钟就卸载 ONNX session，有新任务再加载。四个独立容器做不到"错峰共享内存"，单进程可以。对 1-2GB 小 NAS 这是质变（AI 模型 550MB 常驻 → 按需 200-300MB 峰值）。
- **风险**：低。四类任务互不干扰（各自轮询各自的谓词列）；唯一注意点是 panic 域合并——一个 AI 任务 panic 会带倒四个 sweep（现状是只带倒自己），Go recover 兜住即可。

### 档 2｜队列 worker 二合一：8 → 7（可行，但注意特权面）

**做法**：index-worker 与 transcode-worker 合并为单容器（`WORKER_KIND=both`，两条队列各一条 goroutine 消费）。

- **改动量**：小。`docker/worker/Dockerfile` 的 entrypoint 分发已按 `WORKER_KIND` 实现，加一个 `both` 分支即可。
- **⚠️ 真实障碍——特权面扩大**：index-worker 因 F4 挂载执行器需要 `SYS_ADMIN + /dev/fuse + apparmor=unconfined`；合并后 **transcode 也生活在特权容器里**。转码 worker 处理外来视频文件，一旦被攻破，攻击者直接拿到 SYS_ADMIN。现状下这两个容器是隔离的。
- **缓解释**：挂载点本身只为"管理 NAS 映射目录"服务，若部署场景不用该功能，可出 `both-privileged=false` 变体（只跑队列不挂载）。自托管单机场景下该风险多数用户可接受，但**必须知情**。

### 档 3｜web 并入 caddy：7 → 6（可行，中改，回归风险点集中）

**做法**：Caddy 直接 serve 前端静态文件 + 反代 `/api`，删掉 nginx 层。

- **改动量**：中。要把 nginx 配置里的职责逐条在 Caddyfile 重写：SPA 回退（`try_files` 语义）、`.mjs/.wasm` 等 MIME、分块上传不缓冲、静态资源缓存头、**两组 API 前缀正则**（本项目在这里连踩三次坑：`search|albums|spaces|...` 一组、`ai|bandwidth|...` 一组，漏配症状是刷新拿 401 JSON 或 nginx 405）。
- **收益**：省 7MiB 内存 + 54MB 镜像 + 一跳反代延迟。
- **风险**：**中**。收益小而回归面集中——前端部署验证链条（`curl / → index.html → entry → chunk`）需要全量重测。caddy 层是"环境相关配置"（HTTPS 变体/证书挂载），并入产品静态服务后，"HTTP 简单部署"与"HTTPS 多站点"两个形态要在同一份 Caddyfile 里条件化，产品默认配置复杂度上升。
- **另一方向（web 并入 api，Go embed 静态资源）**：改动更大且要重实现 nginx 的全部判别逻辑，收益相同，**不推荐**。

### 档 4｜继续并：6 → 4（不推荐，列出仅示完整）

sweep 并入 api、caddy 并入 api/单入口。api 从"无状态高响应"变成"AI 批处理 + 静态服务 + AI 推理 panic 域"大杂烩，AI 批处理时的 GC 停顿会直接抖动 API 延迟，升级/回滚粒度也全丢。**没有部署场景真正需要这一档**——容器数 6 与 4 在运维上没有实质差别。

### 档 5｜db/valkey 合并：任何档都不建议

- PG 的 initdb/迁移/健康检查/权限逻辑在官方镜像里维护，自合并镜像要手工复刻且**失去官方安全更新节奏**（PostgreSQL CVE 修复 = 官方新镜像 pull 即得 vs 自合并镜像重构建）。
- db 进程与 app 进程同容器 = 数据库重启和业务发版绑定，破坏"有状态/无状态分离"这条最有价值的边界。
- valkey 只有 12MiB/40MB 镜像，合并毫无收益。

### 档 6｜1 容器专项分析（回答"缩到 1 个的可能性"）

**判定：技术可行、工程不值。** 除非接受自定义 init 镜像，且以下改动/风险全部照单全收：

**所需改动清单**：
1. **统一 init 进程**：容器内多进程需要一个 1 号进程做 supervise + 僵尸回收 + 退出传播。选项：s6-overlay（成熟但引入新依赖）、supervisord（Python 进镜像）、或 Go 自写 supervisor loop（可控但又是自研面）。
2. **合并全部入口**：api + 4 sweep + index + transcode + nginx(或 caddy) 至少 8 类进程；ffmpeg 是 subprocess 由 transcode 拉起。
3. **db/valkey 进镜像**（真·1 容器）：复刻 PG 官方镜像的 initdb + PostGIS/pgvector 扩展安装 + 首启迁移编排；或接受"1 个应用容器 + db 容器"的 2 容器形态。
4. **FUSE 特权上提**：整容器带 `SYS_ADMIN + apparmor=unconfined + /dev/fuse`——攻击面从 1 个 worker 扩到**含数据库在内的全部进程**。
5. **前端服务化**：静态资源进 Go embed 或容器内多跑一个 caddy 进程；nginx 的 SPA 判别/缓存头/分块上传/MIME 全部重实现并重测。
6. **TLS 证书编排**：证书挂载、续期（到期 2026-10-13 的泛域名证书这类手动流程）并入同一容器的配置面。
7. **健康检查重定义**：`healthcheck` 只能有一个探针——需要自研聚合探针（db+valkey+api+队列活性），任一层假活都会骗过 Docker 重启机制。

**风险清单（按严重度排序）**：
1. **崩溃域全域化**：任一组件 panic/OOM（如 ffmpeg 转码被畸形视频打崩）→ 1 号进程拉全栈重启 → **数据库连接闪断**，正在写的会话/上传全部中断。现状：转码崩了只有转码容器重启，用户无感。
2. **升级耦合**：改一行前端 → 重建含 PG 二进制的镜像 → 数据卷格式与镜像版本组合矩阵爆炸；回滚一个组件=回滚全部。现状：11 容器各自 `up -d` 毫秒级切换。
3. **资源隔离丧失**：ffmpeg 打满 CPU 时 API/DB 抢不到时间片，浏览体验随转码抖动；无法 `--scale` 扩转码；无 per-service memory limit，AI 模型 OOM 会直接带走 db。
4. **安全面全域扩大**：SYS_ADMIN + apparmor unconfined + db 同容器——任何一层被攻破即全域沦陷。
5. **可观测性退化**：`docker logs/stats` 按容器切分的天然边界消失，监控要下沉到进程级自建。
6. **与本项目两条红线的冲突**：算力分离设计（Compute Node agent 独立进程）与"任何只在某形态成立"的耦合审计都更难做——单容器里的隐式耦合正是兼容性审计要消灭的东西。

**唯一说得通的场景**：1-2GB 内存的小 NAS 上"能跑就行"。但即便该场景，正确答案也是 §五 的 light profile（7 容器），而非 1 容器——因为该场景最痛的是**模型内存**，档 1 的惰性加载直接解决它，而 1 容器不解决它。

## 五、最优方案推荐

| 形态 | 容器数 | 适用场景 | 状态 |
|------|-------|---------|------|
| **默认形态** | 11 | 标准 NAS/服务器 ≥4GB RAM；要独立扩缩、独立升级、最小崩溃域 | **✅ 现状，维持为产品默认** |
| **light profile** | 7（sweep 四合一 + 队列二合一） | 2-4GB 内存 NAS；容器焦虑型用户；可接受 transcode 与 FUSE 特权共存 | 推荐立项：改动 ≈1-2 天，做 `compose.light.yml` + 聚合入口 + 惰性加载（可选进阶） |
| **极限形态** | 6（再并入 web→caddy） | 极简偏好者 | 不主动推荐：收益 7MiB/54MB，回归面集中 |
| **1 容器** | 1 | 无 | **不推荐**，理由与代价见 §四.6 |

**推荐结论**：

1. **产品默认维持 11 容器**。"容器多"的观感成本已被两个事实抵消：磁盘共享（2.2GB 自定义镜像总量）与空闲内存 1.06GiB 中 550MB 是模型必要驻留。隔离带来的独立升级/扩缩/崩溃域，正是这套系统跑"4K+360°+AI"这种资源画像差异极大的负载的本钱。
2. **light profile（7 容器）值得做**，定位"小内存 NAS 可选项"，核心卖点不是容器数而是 **AI 模型惰性加载**（单进程化后才能实现），预估把 AI 常驻内存从 ~550MB 压到按需 200-300MB。
3. **1 容器方案存档不实施**：其全部真实诉求（省内存、省资源）light profile 已覆盖；其代价（崩溃域/升级耦合/安全面）与项目"部署/兼容性不绑定单一形态"的定位相悖。

## 六、附录：与本项目既有决策的衔接

- **worker 镜像矩阵**（登记簿既有事实）：api/embed/tag/phash/faces 共用 `panomint-app`（build 后逐个 `up -d` recreate）；index/transcode 走 `docker/worker/Dockerfile` 独立镜像按 `WORKER_KIND` 分发。档 1/档 2 均在此矩阵内做加法，不破坏既有部署流程。
- **扫描导入（Job000113）与清扫模型的衔接**：R1-b 扫描导入只写 DB 行、复位扫描时间戳，AI 处理交给 sweep worker 轮询——即"复位即入队"。无论 sweep 容器是 4 个还是 1 个，该语义不变。
- **F4 挂载执行器**（Job000070）：index-worker 的 SYS_ADMIN 特权只服务于 rclone FUSE；light profile 合并后特权面评估见档 2。
- 实测数据采集于 Job000115 发布核验当日；后续架构变更（如立项 light profile）应以新 Job 记录并更新本文档版本。
