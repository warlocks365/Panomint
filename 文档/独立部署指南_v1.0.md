# 独立部署指南 v1.0（无容器的独立服务器安装）

> 适用对象：希望把 Panomint 装在一台**普通 Linux 服务器**上（systemd 管理，不使用 Docker）的部署者。
> 定位：本系统是**通用相册系统**，本文档与 `deploy/systemd/`、`scripts/install-standalone.sh` 共同构成
> "独立服务器安装部署"形态的**最小可用交付基线**。
> 编制日期：2026-09-18 ｜ 对应当前基线 `main`（文档口径改写与独立部署基线同批提交）

## 2. 依赖清单（全部需你自行准备）

| 依赖 | 版本/要求 | 用途 | 校验方式 |
|---|---|---|---|
| Linux | 主流发行版 + systemd | 服务管理 | `systemctl --version` |
| Go | **≥ 1.26**（`go.mod` 声明 `go 1.26.0`） | 编译后端二进制（仅构建期需要，运行期不需要 Go） | `go version` |
| PostgreSQL | **16**，且含 **PostGIS 3** 与 **pgvector** | 元数据 / 向量 / 空间查询 | `psql -c 'select 1'`；扩展见 §5 |
| Valkey | Redis 协议兼容（8.x 建议） | 任务队列（自研队列，非 BullMQ） | `redis-cli -h <host> ping` |
| ffmpeg | 6.x（含所需编解码器；有 N 卡再谈 NVENC） | 缩略图 / HLS 转码 | `ffmpeg -version` |
| 反向代理 | nginx（或 Caddy/traefik） | 对外 HTTPS + 前端静态托管 + API 反代 | 见 §7（**必须复刻**） |
| 系统用户 | 非 root | 运行服务 | `useradd --system` |

> ⚠️ **ONNX Runtime 原生库与模型**由 `assets/` 提供（`.gitignore` 排除，全新克隆必缺）。
> 运行 `bash scripts/fetch-all-assets.sh` 获取；**arm64 暂不承诺**（2026-09-18 决议，见 `文档/部署方案与兼容性_v1.0.md` §11）。

## 3. 安装步骤

### 3.1 准备仓库与资产

```bash
sudo mkdir -p /opt/panomint && sudo chown "$USER" /opt/panomint
git clone <本仓库> /opt/panomint
cd /opt/panomint
bash scripts/fetch-all-assets.sh          # 取 ONNX Runtime + CLIP/Chinese-CLIP/人脸模型
cp .env.example .env && "${EDITOR:-vi}" .env    # 填 PG_DSN / VALKEY_ADDR / MEDIA_ROOT 等
```

> ⚠️ 实测事实（勿想当然）：`.env.example` 里 `PG_DSN`、`VALKEY_ADDR`、`MEDIA_ROOT` 等**是注释状态**
> （形如 `#PG_DSN=...`，示例文件里只有 `POSTGRES_*` / `VALKEY_PORT` / `MINIO_*` 是未注释的），
> 仓库内既有的 `.env` 同样只有这些容器编排用的键。
> 所以**必须手动取消注释并填写**这三项 —— 否则 `APP_ENV=prod` 的门禁会直接拒绝启动（见 §6），
> 安装脚本的依赖检查也会如实报 `[FAIL] 未取到 PG_DSN`。

### 3.2 一键检查 + 编译 + 迁移 + 生成 unit

```bash
bash scripts/install-standalone.sh --dir /opt/panomint --user pano
```

脚本做四件事（**每一步都会打印 OK/FAIL/SKIP，不会静默跳过**）：

1. 平台 / 权限 / systemd 探测（非 Linux 或无 systemd 时**诚实降级**，只给指引）；
2. 依赖检查：Go 版本、ffmpeg、curl、PostgreSQL 连通性、Valkey 连通性、nginx（可选）；
3. 编译 4 个二进制到 `bin/`：`pano-api`、`pano-indexctl`、`pano-transcodectl`、`pano-migrate`；
4. 执行数据库迁移，并把 systemd unit **生成到临时目录**（**不写 `/etc`**），打印安装命令。

常用参数：`--no-build`（用已有二进制）、`--no-migrate`（自行迁移）、`--env-file <路径>`、`--user/--group`。

### 3.3 迁移为什么必须"从主机跑"

`cmd/migrate` 使用 goose 的相对路径 `migrations`（`src/backend/cmd/migrate/main.go:41`），
因此**必须在 `src/backend` 目录下执行**：

```bash
cd /opt/panomint/src/backend && /opt/panomint/bin/pano-migrate up    # 或 status
```

它**不进任何镜像**——`docker/api/Dockerfile` 只编译 `api/embedgen/taggen/facesgen/migrateplan/phashgen`，
**没有 `migrate`**（这是刻意的：迁移是运维动作，不应随应用镜像分发）。

### 3.4 安装并启动服务（需 root）

```bash
sudo useradd --system --home-dir /opt/panomint --shell /usr/sbin/nologin pano
sudo chown -R pano:pano /opt/panomint/data

sudo cp <脚本打印的临时目录>/pano-api.service        /etc/systemd/system/
sudo cp <脚本打印的临时目录>/pano-worker@.service    /etc/systemd/system/
sudo cp <脚本打印的临时目录>/pano-worker-dispatch.sh /opt/panomint/deploy/systemd/
sudo chmod +x /opt/panomint/deploy/systemd/pano-worker-dispatch.sh

sudo systemctl daemon-reload
sudo systemctl enable --now pano-api
sudo systemctl enable --now pano-worker@index pano-worker@transcode
```

### 3.5 验证

```bash
curl -fsS http://127.0.0.1:8080/ready     # 期望 2xx（readiness：PG + Valkey + 磁盘）
systemctl status pano-api pano-worker@index pano-worker@transcode
journalctl -u pano-api -f
```

## 6. 环境变量（`.env`）

关键项（完整清单见仓库根 `.env.example`）：

| 键 | 说明 |
|---|---|
| `APP_ENV=prod` | **生产门禁开关**：为 `prod` 且 `PG_DSN`/`VALKEY_ADDR`/`MEDIA_ROOT` 仍是本机开发默认值时，进程**启动即失败**（`config.go:96-121`）。这是刻意设计，不是 bug。 |
| `PG_DSN` | `postgres://user:pass@host:5432/pano_album` |
| `VALKEY_ADDR` / `VALKEY_PASSWORD` | 队列后端 |
| `MEDIA_ROOT`、`UPLOAD_DIR`、`UPLOAD_TMP`、`HLS_DIR` | 媒体路径（相对 `WorkingDirectory` 或绝对路径） |
| `API_PORT` | API 监听端口，默认 `8080`（`config.go:76`） |
| `CORS_ORIGINS` | 允许的跨域源；**显式置空 = 不允许任何跨域源**（`splitOrigins` 会过滤空串） |
| `AMAP_KEY` / `AMAP_SECRET` | 可选：高德逆地理编码与瓦片；缺省不启用但**不会 500** |
| `TILE_CACHE_DIR` | 可选：地图瓦片磁盘缓存（空 = 不缓存） |

## 7. ⚠️ 必须自行复刻的反代规则（6 条）

以下规则**逐条从 `docker/web/Dockerfile` 内嵌的 nginx 配置中读出并核实**（该文件用 heredoc 把配置写进镜像，
不落地为仓库内的 `.conf` 文件，故引用其行号）。独立部署时这些规则**必须**在你自己的反代上重现，
否则会出现"前端能开、某类请求 404 / 403 / 静默不渲染"的隐蔽故障。

> 通用改写：把配置里的 `proxy_pass http://api:8080;` 换成你的后端地址，例如
> `proxy_pass http://127.0.0.1:8080;`（容器里 `api` 是服务名，独立部署下就是本机端口）。

### 规则 1 — SPA history 回退

- **出处**：`docker/web/Dockerfile:148-151`
  ```nginx
  # Vue SPA history 路由回退（/timeline /player/:id /share/:token /login 等）
  location / {
      try_files $uri $uri/ /index.html;
  }
  ```
- **为什么必须**：Vue Router 用 history 模式，刷新 `/timeline` 这类路径时服务端没有对应文件，不回退就是 404。
- **等价要求**：任何"未命中静态文件 → 返回 `index.html`（200）"的兜底；同时**不能**把 API 前缀也一起兜进 `index.html`（见规则 2）。

### 规则 2 — 前端路由与 API 前缀的冲突消解

- **出处**：`docker/web/Dockerfile:16-20`（判别 map）与 `:55-72`（冲突组 location）
  ```nginx
  # 浏览器导航判别：GET 且 Accept 含 text/html → 视为页面访问
  map $request_method:$http_accept $spa_nav {
      default 0;
      ~*^GET:.*text/html 1;
  }

  location ~ ^/(search|albums|spaces|folders|people|tags|map)(/|$) {
      error_page 418 = @spa;
      recursive_error_pages on;
      if ($spa_nav) { return 418; }
      proxy_pass http://api:8080;
      ...
  }
  ```
- **为什么必须**：`/search`、`/albums`、`/spaces`、`/folders`、`/people`、`/tags`、`/map`
  **既是前端路由（页面）又是 API 前缀**。用一条简单规则无法同时满足两者。
  本项目的判别标准是 **HTTP 方法 + Accept 头**：`GET` 且 `Accept` 含 `text/html` → 浏览器导航 → 回退 SPA；
  其余（axios 发 `application/json`、fetch/hls.js/img 发 `*/*`、curl）→ 透传给 API。
- **等价要求**：等价于"Accept 协商"或"路径白名单 + 方法判别"的任意实现；
  **关键是不能只看路径**，否则要么 `/albums` 页面 404，要么 API 被回退成 HTML。
- **注意**：`/tags` 与 `/map` 属于本组而**不属于**规则 3 的纯 API 组
  （`docker/web/Dockerfile:78` 有明确注释："tags / map 不在此列——它们同时是前端路由，已上移到上面的导航判别组"）。

### 规则 3 — 纯 API 前缀清单（必须与后端路由表手工同步）

- **出处**：`docker/web/Dockerfile:74-89`
  ```nginx
  location ~ ^/(auth|media|transcode|shares|public|admin|health|ready|metrics|geo|tiles|preferences|user|ai|bandwidth|compute-nodes)(/|$) {
      proxy_pass http://api:8080;
      ...
  }
  ```
- **清单（16 项，逐字抄自上述正则）**：
  `auth` · `media` · `transcode` · `shares` · `public` · `admin` · `health` · `ready` · `metrics` ·
  `geo` · `tiles` · `preferences` · `user` · `ai` · `bandwidth` · `compute-nodes`
  （另加规则 2 的 7 个"双身份"前缀：`search` `albums` `spaces` `folders` `people` `tags` `map`）
- **⚠️ 必须手工同步**：这份清单是**手工维护**的，权威来源是 `src/backend/cmd/api/main.go` 的路由注册。
  例如 `/compute-nodes/agent/*` 也在同一前缀下，**必须整体透传**
  （`docker/web/Dockerfile:77-78` 记录了原因：只透传管理面会让节点侧的 POST 落到静态目录 → nginx 405，**实测踩过**）。
  后端新增顶层前缀时，这里必须同步，否则新 API 会被规则 1 的 SPA 兜底吞掉。
- **等价要求**：反代层需要一份"API 前缀 → 后端"的映射，且**与 `main.go` 保持一致**。
- **⚠️ `/metrics` 暴露面**：该端点无鉴权暴露 `go_*`/`process_*` 进程级指标（内存、goroutine、FD、GC 节奏），
  生产建议在反代层限制来源（如 nginx `allow`/`deny` 只放行监控网段），不要直接对公网开放。

### 规则 4 — `.mjs` 的 MIME 必须是可执行的 JavaScript

- **出处**：`docker/web/Dockerfile:104-109`
  ```nginx
  # maplibre worker（.mjs 必须可执行 MIME，否则 module worker 被浏览器拒绝 → GeoJSON 图层静默不渲染）
  location ~ \.mjs$ {
      types { }
      default_type application/javascript;
      try_files $uri =404;
  }
  ```
- **为什么必须**：MapLibre GL v6 的 GeoJSON worker 以 module worker 形式加载 `.mjs`；
  若响应是 `application/octet-stream`（nginx 默认），浏览器**拒绝执行**，症状是"地图图层静默不渲染"（无报错）。
- **等价要求**：`.mjs` → `text/javascript` 或 `application/javascript`。

### 规则 5 — `sw.js` 必须 no-cache

- **出处**：`docker/web/Dockerfile:91-95`
  ```nginx
  # PWA：Service Worker 必须 no-cache（否则旧 SW 长期驻留，升级不生效）
  location = /sw.js {
      add_header Cache-Control "no-cache, no-store, must-revalidate";
      try_files $uri =404;
  }
  ```
- **为什么必须**：Service Worker 被长期缓存会导致"发版后用户仍跑旧版本"且难以定位。
- **等价要求**：`/sw.js` 响应带 `Cache-Control: no-cache, no-store, must-revalidate`。

### 规则 6 — `manifest.webmanifest` 的 MIME

- **出处**：`docker/web/Dockerfile:97-102`
  ```nginx
  # PWA：Web App Manifest 需正确 MIME（application/manifest+json）
  location = /manifest.webmanifest {
      types { }
      default_type application/manifest+json;
      try_files $uri =404;
  }
  ```
- **为什么必须**：MIME 不对时浏览器不认 PWA 清单（表现为无法安装、主题色/图标不生效）。
- **等价要求**：`application/manifest+json`。

### 附加（不属于 6 条硬规则，但**忽略会出问题**）

| 项 | 出处 | 说明 |
|---|---|---|
| 分享页 `/share/<token>` 三出口 | `docker/web/Dockerfile:111-141` | ① `?spa=1` 强制 SPA；② 抓取器 UA → 服务端 OG 页；③ 其余 → SPA。**两条 `if` 的先后顺序是功能正确性的一部分**（`$arg_spa` 必须在前，否则微信真人会被困在极简 OG 页）。 |
| 上游协议透传 `X-Forwarded-Proto` | `:34-40` | 若你的反代在 HTTPS 终止后转发，必须透传 proto，否则分享链接与 `og:image` 会退回 `http://`（微信抓图可能失败）。 |
| 超时与体积 | `:52-53`、`:70-71`、`:87-88` | `client_max_body_size 100m`（分块上传）、`proxy_read_timeout 300s`（HLS 大响应）。 |
| gzip | `:48-50` | `text/css application/javascript application/json image/svg+xml`，`gzip_min_length 1k`。 |
| 后端地址 | `:64`、`:81`、`:134` | `proxy_pass http://api:8080` → 独立部署改为 `http://127.0.0.1:8080`。 |

## 9. 已知限制（不做 / 做不到，如实列出）

1. **arm64 暂不承诺**（2026-09-18 决议）：镜像与二进制已按目标架构参数化，但**未投入多架构流水线、无 arm64 真机证据**；见 `文档/部署方案与兼容性_v1.0.md` §11。
2. **容器运维脚本不适用于本形态**：`scripts/backup.sh`/`restore.sh`/`ops_check.sh` 依赖 `docker compose`。
3. **GPU/NVENC 非必需**：无 NVIDIA 卡时转码与推理自动回落 CPU，但 4K+ 全景转码会明显变慢（这正是"存储与算力分离"要解决的问题，见 TDD §6）。
4. **本指南未在真实独立服务器上端到端验收**：本基线交付的是脚本与 unit 模板，脚本已在本机跑到"依赖检查 + unit 生成"阶段（见提交说明）；**"systemd 起服务 + 反代 + 真机播放"全链路未经实测**。
