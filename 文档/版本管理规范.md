# Panomint 版本管理规范（v1.0 起施行）

> 权威真源。本次构建为 **v1.0.0**，此后所有迭代严格按本规范执行版本递增。

## 1. 版本号结构

三段式：`大版本.中版本.小版本`（MAJOR.MINOR.PATCH），纯数字，不带前导零；对外展示加 `v` 前缀（git 标签、Release Notes、`/version` 端点）。

## 2. 递增规则（裁决标准）

| 变更类别 | 递增 | 判定要点 |
|---|---|---|
| **结构化变更**：数据库表结构变更（新增迁移）、API 契约的不兼容调整、部署架构/板块级重组 | 大版本 +1（中、小归零） | 升级可能需要迁移数据或调整部署 |
| **功能模块新增或改动**：新端点/新页面/新 worker、既有模块的功能性扩展、契约的兼容式增补 | 中版本 +1（小版本归零） | 纯增量升级，既有数据与部署方式不受影响 |
| **优化 / BUG 修复 / 体验改进**：不改变任何对外契约与数据结构的行为修正、性能优化、文案与样式调整 | 小版本 +1 | 升级即替换产物，无需任何额外动作 |

判定争议时按「就高不就低」处理：拿不准是结构化还是功能性，取大者。安全修复视同 BUG 修复（小版本 +1），但需在 Release Notes 中显著标注。

## 3. 唯一真源与注入

- 仓库根 `VERSION` 文件是版本号的**唯一真源**（裸文本，如 `1.0.0`）。
- 发布产物由 `release/build.sh` 读取 `VERSION`，经 `-ldflags -X panoalbum/internal/version.*` 注入二进制；`GET /version` 端点对外暴露 `{version, commit, build_date}`，任何部署可curl 验证产物版本。
- 开发构建不注入，`/version` 返回 `dev` —— 「dev」即「非发布产物」的明确标识。

## 4. 发布流程（每次迭代必须全做）

1. 按 §2 裁决新版本号，更新 `VERSION`；
2. 全量构建 + 测试全绿（后端 `go build ./... && go test ./...`、前端 `vite build` + org 棘轮）；
3. 登记簿 §二十七落账本次 Job 行（含版本号与证据链）；
4. 提交并推送后打 git 标签 `vX.Y.Z` 并推送（标签即版本归档锚点）；
5. 产出 `文档/Release_Notes_vX.Y.Z.md`：版本号、按域分类的更新摘要、三种形态部署指引、升级注意事项；
6. `release/build.sh` 产出三形态发布包（裸机 / 集成包 / Docker），产物命名内嵌版本号。

## 4.5 发版一致性校验（2026-09-27 固化，Job000130，每次发版默认执行）

发版链「手册 → 版本 → 镜像」完成后，**必须**执行 `.workbuddy/release_consistency_check.py vX.Y.Z` 逐项核验，全部 PASS 才算发布完成；任何一项 FAIL 即回查对应环节，不带着不一致交付。六大渠道 nineteen 项断言：

| 渠道 | 断言 |
| --- | --- |
| GitHub 仓库 | 远端 `main` 与 `vX.Y.Z` 标签存在且同指一发（ls-remote 核验） |
| 仓库版本文件 | `VERSION`、`package.json`、`versionHistory` 头条目、群晖模板 tag（≥10 处）、Release Notes 文件存在 |
| 操作手册 | 文档版手册尾注含 vX.Y.Z；服务器源码树应用内手册已同步 |
| Docker Hub | `panomint-{app,worker,db,web}` 四镜像 `X.Y.Z` tag 存在且 **digest 与 `latest` 完全一致**（Hub API 独立查询，注意加间隔防限流） |
| 系统内版本 | 测试服 `/version`（HTTP 与 HTTPS SNI 双通道）实测 = X.Y.Z；运行态必须切到**发版镜像**（非开发构建）后实测 |
| 产物一致性 | web 容器内 dist 关键 chunk sha256 = 本机构建；服务器源码树 `VERSION` = X.Y.Z；容器全 Up |

配套纪律（历次教训固化）：
- Hub 推送**写死命令逐条执行**（多 tag 循环变量会被双层 shell 吃掉；`set -e` 循环中断会导致后续 tag 未打——推送前 `docker images` 核验 8 个 tag 指向，digest 与上版相同即红灯）；
- digest 三方核验 = 服务器 push 日志 + 本机 Hub API 独立查询，两边逐字一致；
- 运行态对齐后必须 restart web（nginx upstream IP 缓存坑）与 `--force-recreate`（坑位 38）。

## 5. 兼容性承诺

- 同一**大版本**内：数据库可滚动升级（迁移只增不改旧语义）、API 契约保持向后兼容；
- 跨**大版本**：允许不兼容变更，Release Notes 必须给出迁移指引；
- 回滚：小/中版本升级可通过重新部署旧产物回滚；大版本升级回滚需按 Release Notes 的数据迁移指引执行。

## 6. 热修复分支

紧急修复从对应标签切 `hotfix/x.y.z+1` 分支，修复后按 §4 全流程度出补丁版本并合并回主线。

## 7. 交付前验证门禁（2026-10-10 固化）

**任何功能，未经验证或验证不通过，一律不得进入验收汇报，也不得计为完成。**

### 7.1 硬性要求

每个功能实现后必须**实际反复验证**，确认达到设计预期，才允许汇报。验证须**多维度交叉证实**，单一手段不算通过：

| 手段 | 要求 |
| --- | --- |
| 运行结果截图 | 含**改动前后对比**，仅截"看起来正常"不算 |
| skill 浏览器实测 | 通过浏览器技能抓**真实访问结果数据**（响应体、DOM 属性、请求状态码），不接受"页面没报错" |
| Windows MCP 实操 | 在**真实浏览器**执行完整交互链路（如点击、切换、跳转），记录每步实际结果 |
| 可重复脚本 | 交互类改动须落成脚本（如 `.workbuddy/verify_*.js`），能一键复跑，而非人工单次点击 |
| 纯逻辑单测 | 能脱离浏览器判定时优先写单测，并做**变异验证**（改坏实现看测试是否变红）——全绿但改坏也不红的测试视为无效 |

### 7.2 多维度交叉证实

同一功能至少覆盖：**正常路径**、**边界**（空数据/极值/非法输入）、**重复执行**、**跨维度**（跨年/跨月/多档位切换）。单次成功不构成证据。

### 7.3 必须如实交代的三件事

1. **未验证的部分**要明说，不能用"应该可以"带过；
2. **验证不通过**要直说，不得改口径为"部分可用"；
3. **观测工具的局限**要交代：无障碍树会省略元素，**元素缺失 ≠ disabled**；懒加载列表只看首屏会**严重取样偏差**。

### 7.4 阻塞与失败必须可见

静默失败（`catch {}` 后返回空、守卫直接 `return`、配置项为空即空转）一律视为缺陷。
关键路径失败必须**上报可观测信号**（降级事件 / 明确错误码 / 日志），不得无声通过。

> 该条来自 2026-10-10 夜间实战：定位问题连续三次因"静默 return / 静默 catch"而无法定位，
> 把静默 return 改为降级事件上报后，第一轮实测即读出破案关键信息。

### 7.5 验证脚本须随代码入库

交互类验证脚本统一放 `scripts/`（可入库、**不得含凭据字面量**）；临时探针放 `.workbuddy/`（不入库）。
脚本输出须包含**判定结论**（PASS/FAIL 与依据），而非仅打印中间状态。
