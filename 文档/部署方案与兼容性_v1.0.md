## 1. 一句话目标与"不是什么"

**目标**：Panomint 是一套**通用相册系统**，必须支持

1. **任意平台的容器化部署**（Docker Compose 为基线形态，不绑定某一台机器、某一个发行版、某一个 CPU 架构）；
2. **独立服务器安装部署**（无容器：二进制 + systemd + 外部 PostgreSQL/MinIO/Valkey）。

**"不是什么"**：

- - **DS1819+ 不是目标平台**。它只是"当前已有的环境条件"之一。仓库中所有围绕 `DS1819+`、`Atom C3538`、`4 核 / 7.8G`、`192.168.1.115`、`warlocks.cn` 做出的设计取舍，**都是耦合**，应改为"某类环境的一个实例"。
- - 不以"某台机器上能跑"作为验收标准。验收标准是 §2 的支持矩阵逐档通过。
- - 不假设"用户有一台 NAS"、不假设"用户有 NVIDIA GPU"、不假设"用户在中国境内且有外网访问 GitHub/HuggingFace"、不假设"用户的数据盘一定挂在 `/home`"。

**已有的正确口径（应作为基线继承）**：

> `文档/阶段性快照_Job000005节点.md:223`
> "**项目定位**：独立相册系统，可部署任意主流 Linux / Docker，**不绑定群晖**；媒体源位置无关（SMB/NFS/本地/远端）。任何功能不得表述为「群晖专用」。"

这句话已经是"通用部署"的立场，但它目前只存在于一份**过程快照**里，未进入 README / TDD 的正式口径；README 与 TDD 反而把群晖与具体机型写成了定位本身。

1. **SPA history 回退**：`location / { try_files $uri $uri/ /index.html; }`（`:149-151`）。前端路由共有：`/login`、`/share/:token`、`/timeline`、`/map`、`/spaces`、`/folders`、`/upload`、`/player/:id`、`/search`、`/albums`、`/albums/:id`、`/tags`、`/people`、`/toolbox`、`/settings`（`src/frontend/src/router/index.js:6-97`）。缺这条 → 刷新任意子路由 404。
2. **"前端路由 vs API 前缀"冲突消解**：`/search`、`/albums`、`/spaces`、`/folders`、`/people`、`/tags`、`/map` 既是前端页面又是 API 前缀 → nginx 用 `map $request_method:$http_accept $spa_nav`（`:17-20`）+ `error_page 418`（`:60-63`）区分：浏览器导航给 SPA，`Accept: application/json` 给后端（`:60-72`）。缺这条 → 刷新 `/people` 等页面会拿到 JSON。
3. **纯 API 前缀整体反代**：`^/(auth|media|transcode|shares|public|admin|health|ready|metrics|geo|tiles|preferences|user|ai|bandwidth|compute-nodes)(/|$)` → `proxy_pass http://api:8080`（`:80-89`）。⚠️ 该清单**必须与 `cmd/api/main.go` 的路由保持同步**：代码注释已明确记录"漏配会拿到 index.html，本项目已因此踩坑三次"（`src/backend/cmd/api/main.go:246-247`）。清单是硬编码的，**没有"从代码生成"的机制** —— 这是长期耦合点。
4. **`.mjs` 的 MIME 必须是 `application/javascript`**（`:104-109`）：否则 maplibre 的 module worker 被浏览器拒绝 → **GeoJSON 图层静默不渲染**（`overview.md:247` 记录了该坑）。缺这条 → 地图功能静默失效，且**无报错**。
5. **`sw.js` 必须 `no-cache`**（`:91-95`）：否则旧 Service Worker 长期驻留，升级不生效。
6. **`manifest.webmanifest` 的 MIME 必须为 `application/manifest+json`**（`:97-102`）。

**独立部署的结论**：技术上**可行且基础良好**（配置全环境变量化、迁移工具纯 Go、worker 无 CGO、前端纯静态），但**零交付物**——没有 unit 文件、没有安装脚本、没有把上述 6 条规则文档化的安装说明，且运维三件套（备份/巡检/恢复）100% 绑死 `docker compose`。要做成"支持"，需要补的是一套**安装与运维资产**，而不是改动核心代码。

## 6. 不做的事与理由（避免范围蔓延）

| 不做的事 | 理由 |
|---|---|
| **不支持 Windows 原生部署**（非容器、非 WSL） | ① 后端依赖 `ffmpeg` + `libonnxruntime` 的原生动态库（`internal/ortx/ortx.go:60` 已支持 `onnxruntime.dll`，但无 Windows 部署脚本/服务管理）；② Windows 无 systemd 等价物，运维三件套（`flock`、`df --output=avail`、路径语义）全为 POSIX；③ 收益低（`WSL2`/Docker Desktop 已可覆盖），成本高。**结论：Windows 仅作为"开发机"支持**（当前 `assets/lib-ort-gpu/*.exe` 正是这一用途的产物）。 |
| **不把 macOS 作为一等部署目标** | ① ORT 的 `osx` 版本在 `fetch-clip-assets.sh:72` 有 `darwin-x64` 分支，但仓库内无资产、无验证；② Apple Silicon 属 arm64（见 §7 O1），需先解决 arm64 才能谈 macOS；③ 相册系统主要场景是常开的服务器/NAS，不是 Mac。**可作 P2**。 |
| **不承诺"任意架构"** | 明确只承诺 **x86_64** 与 **arm64** 两种；其余（riscv64、ppc64le 等）不承诺，因为 ONNX Runtime 上游不提供预编译库。 |
| **不把 K8s 作为交付形态** | `README.md:31` 写"Compose → K8s"属长期方向描述；当前无任何 Helm/Manifest。本轮只把 **Compose** 做扎实，K8s 作为后续独立命题。 |
| **不要求 GPU** | 已确认 GPU 全程可选（§3.3）。文档不得把 NVIDIA 写成前置条件，只在"性能建议"中提及。 |
| **不为"多实例/横向扩展"做改造** | 当前 `container_name` 写死（`docker-compose.yml:12` 等）、worker 为"清扫式"单实例模型（`docker-compose.yml:115-228`），横向扩展需专门设计。本轮不做，但不应阻碍（P0-5 清理 `container_name` 为将来留门）。 |
| **不改动历史工作日志** | `工作日志/*`、`文档/工作日志_交接版.md` 是历史记录，回改会破坏"当时事实"。仅建议加"历史记录"标注 + 口令脱敏（P2-5）。 |

## 附二、资产获取（P0-3 已处理）

> 本节为**落地改动后的追加说明**，对应 §4 的 **P0-2**（ONNX Runtime 按目标架构选择）与 **P0-3**（资产获取显式化）。
> 上文为只读审计原文，**未作任何修改**；本节只描述"现在该怎么做"。

### 10.1 一条命令拿全资产

```bash
bash scripts/fetch-all-assets.sh     # 平台/架构按 uname 自动识别；幂等，可重复执行
```

> 为什么带 `bash`：仓库里所有脚本在 git 中都是 `100644`（`core.filemode=false`），
> 全新克隆**没有执行位**，直接 `scripts/xxx.sh` 会 Permission denied；带 `bash` 在任何平台都可用。

它依次调用三个脚本，并把结果放在镜像构建所需的相对路径上：

| 步骤 | 脚本 | 拿到什么 |
|---|---|---|
| ① | `scripts/fetch-clip-assets.sh` | OpenAI CLIP 模型 + **当前平台/架构**的 ONNX Runtime 原生库 |
| ② | `scripts/fetch-chinese-clip-assets.sh`（**本次新增**） | Chinese-CLIP 模型 + 调用 `scripts/split_clip_onnx.py` 切分出的单塔模型 |
| ③ | `scripts/fetch-face-assets.sh` | 人脸模型 YuNet（检测）+ SFace（识别） |

常用参数：

| 参数 | 作用 |
|---|---|
| `--platform <p>` | `linux-x64` \| `linux-arm64` \| `win-x64` \| `darwin-x64`；**省略则按 `uname` 自动识别** |
| `--gpu` | 取 CUDA 版 ONNX Runtime（上游只有 x64 有预编译包；可用 `ORT_CUDA=cuda12\|cuda13` 指定） |
| `--skip-faces` | 不取人脸模型（约 37MB） |
| `--dir <仓库根>` | 显式指定仓库根（默认取脚本上一级目录） |

脚本结尾会**对照 `docker/api/Dockerfile` 的 COPY 清单逐项校验**（含按平台推导的 ORT 目录名），缺任何一项都直接 `exit 1`，不会留一个"看起来跑完了"的假成功。

### 10.2 各资产来源与版本

| 资产 | 来源 | 版本 / 文件 | 落地路径 | 约体积 |
|---|---|---|---|---|
| ONNX Runtime 原生库 | `github.com/microsoft/onnxruntime` Releases | **1.29.0（必须）**；`onnxruntime-linux-x64` / `onnxruntime-linux-aarch64`（GPU 版为 `-gpu_cuda12` / `-gpu_cuda13`） | `assets/lib/onnxruntime-linux-<x64\|aarch64>-1.29.0/lib/` | 28MB |
| OpenAI CLIP | HuggingFace `Xenova/clip-vit-base-patch32`（MIT） | `onnx/text_model_quantized.onnx`、`onnx/vision_model_quantized.onnx`、`tokenizer.json`、`vocab.json`、`merges.txt`、`preprocessor_config.json`、`config.json` | `assets/models/clip/` | 156MB |
| Chinese-CLIP（**默认模型族**） | HuggingFace `Xenova/chinese-clip-vit-base-patch16`（上游 `OFA-Sys/chinese-clip-vit-base-patch16`） | 原料 `onnx/model_quantized.onnx`(190MB) + `tokenizer.json`、`vocab.txt`、`tokenizer_config.json`、`config.json`、`preprocessor_config.json`；**切分产物 `text_only.onnx` / `vision_only.onnx` 才是运行时需要的** | `assets/models/chinese-clip/` | 下载 191MB + 切分产物 |

### 10.3 全新克隆为什么会失败（以及现在的失败长什么样）

`assets/` 整个目录被 `.gitignore` 排除（`git ls-files assets` = **0**），而 `docker/api/Dockerfile` 会 `COPY assets/models/...`。所以：

| 场景 | 改造前 | 现在 |
|---|---|---|
| 全新克隆直接 `docker compose build api` | Docker 抛一句难懂的 `COPY failed: ... not found`，或（目录在但文件缺）构建"成功"、运行期崩溃循环 | **构建期**列出**具体缺失的文件**，并直接告诉你执行 `bash scripts/fetch-all-assets.sh` |
| 用错架构的 ORT 库（例如 arm64 机器上放了 x64 的 `libonnxruntime.so`） | 构建通过，运行期 `dlopen` 失败且极难定位 | **构建期**读取 `.so` 的 ELF `e_machine` 与 `TARGETARCH` 比对，不一致即 **build 失败**并指出是哪个目录放错了 |

这两条检查都在**独立的多阶段（不进入运行镜像、不安装 `file`/`binutils`、构建开销≈0）**里完成，amd64 的最终产物与改造前逐字节一致（同 ORT 版本、同 `/opt/onnxruntime/lib/` 路径、同 `EMBED_LIB`/`EMBED_MODEL_DIR`/`EMBED_FAMILY` 默认值）。

### 10.4 离线 / 内网环境

`assets/` 不在版本库里，离线时**必须带外传递**：

1. 在一台**与目标机同 OS/同架构**的联网机器上执行（显式指定平台，避免自动识别错）：
   ```bash
   bash scripts/fetch-all-assets.sh --platform linux-arm64     # 例：目标机是 ARM NAS
   ```
2. 打包这两处，拷到目标机仓库的**相同相对路径**：
   ```bash
   tar czf assets-offline.tgz assets/models assets/lib/onnxruntime-linux-<x64|aarch64>-1.29.0
   ```
   - `assets/models/`（约 400MB）
   - `assets/lib/onnxruntime-linux-<x64|aarch64>-1.29.0/`（只这一层，约 30MB；`include/` 与 win-x64、GPU 版不需要）
3. 目标机上校验：重跑 `bash scripts/fetch-all-assets.sh`（幂等，会全部跳过下载并做完整性校验）。
4. **切分 Chinese-CLIP 需要 python + `onnx` 包**（只在准备资产时用，运行镜像里没有 python）。若准备机装不上 `onnx`，在容器里切分即可：
   ```bash
   docker run --rm \
     -v "$PWD/assets/models/chinese-clip:/m" -v "$PWD/scripts:/w" \
     python:3.13-slim bash -lc "pip install onnx && python /w/split_clip_onnx.py /m"
   ```
   > 190MB 的 `model_quantized.onnx` 已被 `.dockerignore` 排除，**不需要**传进镜像；镜像只需要切分后的 `text_only.onnx` / `vision_only.onnx` + `tokenizer.json`。

   > ⚠️ **Windows 上不要在本机直接切分**（2026-09-18 实测，此前只记录在被 gitignore 的
   > `.workbuddy/memory/` 里，部署者看不到）：`pip install onnx` 装出的 onnx 在切分这个
   > 3395 节点的合并模型时会直接崩（`Windows fatal exception: access violation`），崩溃点在
   > onnx 的 C++ 扩展 `onnx.checker.check_model` 与 `onnx.shape_inference.infer_shapes`；
   > 而 `onnx.load()` 本身是正常的（能用它确认模型的输入/输出名与
   > `scripts/split_clip_onnx.py` 的目标一致：输入 `input_ids`/`attention_mask`/`pixel_values`，
   > 输出含 `text_embeds`/`image_embeds`）。**Windows 请直接走上面的容器方式切分**；
   > Linux 上则没有这个问题（本仓库现有的单塔模型就是 2026-09-12 在服务器容器内切出来的）。
   > `scripts/fetch-chinese-clip-assets.sh` 遇到这种情况会保留已下载的模型并给出容器切分指引，不会删文件。

### 10.5 默认模型族：**维持 chinese-clip**（本次不改默认值）

本次选择的是"**补资产获取脚本**"而不是"改默认族"。依据：

- 默认族不是随手写的 `ENV`，而是**有标定支撑的产品决策**：`internal/tags` 的零样本打标阈值是在真实库（72 条媒体 × 118 个标签）上按 chinese-clip 标定的；`internal/search` 的相似度区间也是按该族实测的。
- 改默认族 = **检索语义变更**：两族向量空间不同，`media.embedding` 里已有的向量对另一族**没有意义**。
- 本次问题的本质是"**默认族的资产拿不到**"，而不是"默认族选错了"。补脚本即可消除矛盾，且不触碰线上检索结果 —— 风险最低。

**当前取值（多处一致，改一处不会生效，需一起改）**：

| 位置 | 取值 |
|---|---|
| `docker-compose.yml` | `EMBED_FAMILY: ${EMBED_FAMILY:-chinese-clip}`；`EMBED_MODEL_DIR: ${EMBED_MODEL_DIR:-/opt/models/chinese-clip}` |
| `docker/api/Dockerfile` | `ENV EMBED_FAMILY=chinese-clip`、`ENV EMBED_MODEL_DIR=/opt/models/chinese-clip` |
| 后端代码 | `EMBED_FAMILY` 为空时按 chinese-clip 处理 |

**如果将来确实要切到 `clip`（或切回），代价如下 —— 这是一次产品行为变更，不是配置开关**：

1. 必须全量重算向量：`embedgen -mode encode -force`（旧向量与新文本塔不同空间，混用会让检索结果无声劣化）；
2. 标签需重跑 `taggen`：两族文本塔**互不认识对方的提示词语言**（chinese-clip 不认英文提示词、clip 不认中文），且相似度下限的标定值不同；
3. 两族资产都必须存在（`assets/models/clip` 与 `assets/models/chinese-clip` 都在镜像里），所以**切族不需要重新构建镜像**，只需改环境变量 + 重算数据。
