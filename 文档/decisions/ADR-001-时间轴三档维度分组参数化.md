# ADR-001：时间轴三档维度采用「纯前端分组参数化 + 后端仅补 day 粒度」

## Status

Accepted（2026-10-08，Panomint v1.9.4 增量需求「中台 Timeline 三档维度」）

## Context

### 需求（用户已锁定 4 项，不再讨论）

1. 三档维度 = **仅切换分组标题粒度**：年档只显示 `2024年`、月档只显示 `2024年6月`、日档只显示 `2024年6月14日`，**媒体数据流不变**。
2. 日期选择组件 = **锚点跳转**，不改变媒体范围（不筛选）。
3. Logo 落位 = 全站品牌位（不在本 ADR 范围，见「影响面外」）。
4. 允许改后端：`/media/date-histogram` 扩到支持 `day`；day 粒度的用途是**让日期选择器高亮「当天有照片」的日期**。

### 现状事实（已逐行核实，非推测）

| 事实 | 证据 |
|---|---|
| 后端路由**无 `/api/v1` 前缀**，直挂 `/media/date-histogram` | `src/backend/cmd/api/main.go:226` |
| media 侧粒度白名单有**两份**：handler 硬编码 `if` + store 的 `histogramTrunc` map | `internal/media/handlers.go:140`、`internal/media/histogram.go:23-26` |
| geo 侧白名单**只有一份**（store map），handler 不预校验，靠 `err == ErrInvalidGranularity` 分流 | `internal/geo/media_store.go:81-85`、`internal/geo/handlers.go:247-256` |
| geo 侧**已有** `year\|month\|day` 三粒度，可直接作范式 | `internal/geo/media_store.go:81-85` |
| `/media/timeline.go` 的 `viewTrunc` **也已含 day**，且 `GET /media?view=day` 已在返回 `buckets` | `internal/media/timeline.go:95-99, 238-252` |
| 前端 `MONTH_H=46` / `DAY_H=34` 为模块常量，与 CSS `.tl-header.month/day` 的 `height` 手工对齐 | `useTimelineGrouping.js:7-8`、`TimelineGrid.vue:283-296` |
| 前端**无任何测试文件**（无 `*.spec.js` / `*.test.js`） | `find src/frontend/src -name "*.spec.js" -o -name "*.test.js"` → 空 |

### 决策驱动因素

- **改动面最小**：媒体数据流不变 ⇒ 不触碰 `useTimelinePager` 的 `/media` 分页契约、不触碰游标语义、不触碰 `buildWhere`。
- **回归面最小**：后端仅动一个 map 的一个 entry + 文案；前端仅动分组层，不动取数层。
- **复用既有正确实现**：geo 侧三粒度 + `viewTrunc` 三粒度均已在本仓跑过，`day` 的 `to_char` 格式与 `date_trunc` 组合是**已验证口径**，不是新发明。

## Decision

**采用纯前端分组参数化，后端只把 `/media/date-histogram` 的 `granularity` 白名单从 `year|month` 扩到 `year|month|day`。**

具体形态：

1. **后端**：`histogramTrunc` 增 `"day": {"day", "YYYY-MM-DD"}`；`ErrInvalidGranularity` 文案由 `granularity 仅支持 year|month` 改为 `granularity 仅支持 year|month|day`，与 geo 侧逐字一致。**不新增端点、不改 SQL 骨架、不加迁移、不改索引。**
2. **前端**：分组标题粒度由**单一维度参数** `dimension ∈ {year, month, day}` 驱动，**该档位是唯一可见的标题粒度**——year 档只产出 `2024年` 标题、month 档只产出 `2024年6月`、day 档只产出 `2024年6月14日`；标题高度按档位差异化（年 > 月 > 日）。`monthIndex` 泛化为 `headerIndex`（键随档位收窄：`2024` / `2024-06` / `2024-06-14`）。
3. **锚点跳转**：seek 载荷统一为**该档位下的分组键**，定位算法改为「先查 `headerIndex` 精确命中 → 未命中则取 `<= target` 的最近分组 → 命中其 `offsets[i]`」，保证落点永远是**分组标题行的顶部**，不会落到标题中间的媒体格。

### 为什么不选其他方案

| 备选 | 否决理由 |
|---|---|
| A. 后端新增 `/media/date-histogram?granularity=day` 独立端点 | 与既有端点语义重复（同一条 SQL、同一套 `scopeConds`），只多一条路由和一份契约条目，属镀金。 |
| B. 复用 `GET /media?view=day` 的 `buckets` 替代直方图 | **不可行**：`view=day` 的桶走 `buildWhere()`，会随 `type/favorites/place/folder` 过滤而变；直方图走 `scopeConds()`，是**全量密度**。且 `/media` 是分页取数端点，为拿滑块密度而调它等于用分页接口当统计接口，语义混淆。 |
| C. 维度切换时改媒体取数（真按年月筛选） | 与用户锁定决策 1 直接冲突（媒体数据流不变），且会作废游标分页与 `buildWhere` 的 `Date` 语义。 |
| D. 档位高度写死成三张表并按档位 `switch` | 高度是「档位 × level」的二维量，`switch` 会退化成三份重复分支；用查表 `{[level]: {[dimension]: px}}` 保持单一真源。 |

## Consequences

### 正面

- 后端改动落在**一个 map 的一个 entry + 一条文案**，无新文件、无迁移、无 SQL 骨架变更，`go vet` + `go test` 风险面极小。
- `day` 粒度直接沿用 geo 侧与 `viewTrunc` 的 `to_char(date_trunc('day', …), 'YYYY-MM-DD')` 口径，**三处桶键格式必然一致**，不会出现「滑块 day 键与后端 day 桶键格式不同」的静默错位。
- 前端取数层（`useTimelinePager`）零改动 ⇒ 分页/游标/代次守卫的回归面为零。

### 负面 / 代价（明确接受）

- **文案变更触及两处既有测试断言**（详见设计文档「回归面」章节）：`errtext_endpoints_test.go:289-290` 与 `errtext_guard_test.go:94` 的 geo 侧理由串。**注意：这两处断的是 geo 侧，不是 media 侧**——见下方「纠正」。
- day 粒度下桶数量上界从「年/月级数十~数百」升到「**按天计，上界约 3660/年**」。响应体积与 `ticks` 渲染项数随之上升，须由前端做**桶数量上限保护**（见设计文档）。
- 前端**零测试覆盖**（已核实无任何 spec/test 文件），三档泛化的正确性无法由既有单测兜底 ⇒ 必须补纯函数级测试，否则改完只能靠人眼。

### 纠正一处上游误判（重要）

上游任务描述称「`errtext_endpoints_test.go:278-290` 与 `errtext_guard_test.go:94` 有针对**旧文案**的断言，必须同步」。逐行核实后的准确结论：

- `errtext_endpoints_test.go:269-293` 的 `TestGeoHistogramInvalidGranularityStill400` 请求的是 **`/geo/histogram`**，断言的文案是 geo 侧的 `granularity 仅支持 year|month|day`。**media 侧文案变更不影响它**。
- `errtext_guard_test.go:94` 的登记项 `MustFix=false`，匹配键是 `File|Func|Prev|Pattern`（**源码行形状**），其中 `「granularity 仅支持 year|month」` 只是 `Reason` 里的**说明文字**，不参与匹配。改 media 文案同样**不影响**它。
- 真正需要同步的是 `errtext_guard_test.go:94` 那条**理由文字本身已经过期**（它描述 geo 端，却写着 media 侧的旧文案 `year|month`）——这是**既有文档缺陷**，顺手修正即可，属可选清理。

**结论：media 侧文案从 `year|month` 改为 `year|month|day`，`go test ./internal/httperr/` 全绿，无需改动任何断言。** 这一条纠正直接降低了改动风险，避免工程师按上游指示去改本来正确的断言（改了反而会把 geo 侧的保护改坏）。

误判根因（团队复盘后确认）：上游用子串 grep 匹配，而 `"granularity 仅支持 year|month"` 恰是 geo 端 `"year|month|day"` 的**子串**，属假阳性。

### 纠正一处本 ADR 初稿的语义误读（重要）

本 ADR 初稿曾把「仅切换分组标题粒度」解读为「档位 = 最细可见粒度，年/月/日三级标题**始终全部渲染**，只是最细到日」。经团队裁决**该解读错误**，已修正：

- 用户当时看到的选项原文为「年视图只显示『2024』这类年标题；月视图显示『2024年6月』；日视图显示『2024年6月14日』」，PM 已编码为验收标准 **A1/A2/A3**，其中 A1(P0) 明确要求 year 档**不得出现任何月或日标题**。
- 初稿解读会导出「年档显示的标题比日档更多」这一自相矛盾结果，据此得出的「三档高度表相同」结论一并作废。
- **正确语义**：档位即**唯一可见的标题粒度**。year 档不产出 month/day 标题，month 档不产出 day 标题，day 档只产出 day 标题。

连带影响：标题高度改为**按档位差异化**（年 > 月 > 日），详见设计文档 §2.1。

## 风险记录：年档下的「无标题细分大块流」（本期不改，显式留痕）

**风险**：年档下一年只产出**一个**标题。若某年有数千张照片，该年内部将出现**长达数千张、无任何标题细分**的连续流。

- 这是用户锁定决策 1（年档只显示年标题）的**直接后果**，属决策内生风险，不是实现缺陷。
- **本期不改**：修它需要引入档位内的二级细分（如年档仍显示月标题），而那已被 A1(P0) 明确禁止。
- **旁证**：Google Photos 于 2026-07 将网格日期分隔线默认关闭后用户强烈反弹（PM 提供），说明日期标题是用户依赖的定位锚点，取消或稀疏化标题会引发同类投诉。
- **留痕目的**：避免日后被当 bug 报障、或被工程师“好心”加回月标题而违反 A1。若用户后续反馈年档难定位，正确的应对是**改产品决策**（例如年档下把粒度自动降级为月），而不是在实现里偷偷加标题。


## 影响面外（明确不做）

- 不做 Logo 落位（用户决策 3，属设计/前端工种）。
- 不改 `/media` 取数与分页契约，不引入 `Date` 筛选。
- 不为 day 粒度新增索引或迁移（`idx_media_taken ON media(taken_at DESC)` 已足够，见设计文档索引评估）。
- 不重构 `TimelineGrid.vue` 的既有超标部分为「顺手治理」——但**本次不得使其变长**（棘轮，见下）。

## 棘轮约束（硬门禁，非风格建议）

`scripts/frontend_org_baseline.json` 已登记 `components/timeline/TimelineGrid.vue: 326`，实测当前 **355 行**，`scripts/frontend_org_guard.py` 的 O1 规则对已登记文件**禁止变长**。

**因此：本次改动必须把三档维度逻辑放进新文件，`TimelineGrid.vue` 行数不得净增。** 新增的维度切换 UI、分组参数化、锚点定位算法一律落到新建的 composable / 子组件中。
