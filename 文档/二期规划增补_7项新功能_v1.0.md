## 二、功能 4：主页功能栏（A 档，最先做）

### 需求补全与优化

你的原话：主页位于时间轴之上，作为默认首页，显示**收藏拼贴、最新入库拼贴、人物拼贴、地点拼贴、相册拼贴**四格拼贴链接，点开跳目标页。

**我补充的细节**（这些是原需求没说但必须定的）：

| # | 待定项 | 我的建议 | 理由 |
| --- | --- | --- | --- |
| 1 | 拼贴是「缩略图九宫格」还是「单图 + 文字」？ | **九宫格（3×3）**，不足 9 张用占位填充 | 缩略图网格信息密度高，且与现有卡片风格一致 |
| 2 | 每格显示几张？ | **9 张**（3×3），点击进入目标页 | 视觉整齐 |
| 3 | 「最新入库」按什么排？ | `created_at DESC`（入库时间），**不是** `taken_at`（拍摄时间） | 用户心智是「最近加进来的」 |
| 4 | 目标页带筛选条件吗？ | **带**。如「收藏拼贴」→ `/timeline?favorite=1` | 点进去看到的必须就是格子里那些内容 |
| 5 | 数据怎么来？ | **每格 1 个轻量 API**（返回 9 个 id + 缩略图），不拉全量 | 避免首页 5 次查询拉爆带宽 |
| 6 | 空状态怎么办？ | 显示「还没有收藏，去看看」+ 跳转按钮 | 不显示空白格 |
| 7 | 拼贴支持自定义排序吗？ | **本期不支持**（固定顺序：收藏/最新/人物/地点/相册） | 5 格固定顺序用户能形成肌肉记忆 |

### 技术方案

**改动很小**：

```
frontend/src/views/HomeView.vue        ← 新增（约 200 行）
frontend/src/router/index.js           ← '/' 从 redirect 改为 HomeView
frontend/src/api/home.js               ← 5 个轻量端点调用（或复用现有 search API）
```

⚠️ **路由改动的影响**：`/` 原本 `redirect: '/timeline'`，改后**所有未匹配的路径都落到主页**。
需确认 `BootGate`（启动等待页）与分享页 `/share/:token` 不受影响——它们是更具体的路径，Vue Router 优先匹配，无风险。

**后端**：**不需要新端点**。5 个拼贴数据可由现有 API 组合：
- 收藏拼贴 → `GET /media?favorite=1&limit=9`
- 最新入库 → `GET /media?limit=9&sort=-created_at`（需确认现有是否支持 sort，不支持则加）
- 人物/地点/相册拼贴 → 各自 API 取前 9

**工期** 3 工作日 · **token** 约 12 万

## 四、功能 5：动态电子相册（B 档，必须拆期）

### 4.1 需求补全与范围收敛

你的原话：以相册为单位手工制作动态电子相册；模板生成或手工逐页编辑；背景相纸、相框、单页多照片拼贴、艺术字体、字幕、贴画装饰、背景音乐；**导出 base64 内嵌的单一 HTML**；也可导出 **PDF 纯静态**；模板素材可上传/管理/官方渠道更新。

**这个功能很大。我建议拆成三期**，理由是它同时包含「编辑器」「模板引擎」「两种渲染器」三块，每块都能独立成产品。

| 期 | 内容 | 工期 |
| --- | --- | --- |
| **5a** | **静态相框排版 + 单一 HTML 导出**（不含动画/音乐） | 8 d |
| **5b** | **动态效果 + 背景音乐 + 翻页动画** | 6 d |
| **5c** | **模板系统 + 素材管理**（上传/官方包） | 6 d |
| **5d** | **PDF 导出** | 4 d |
| **合计** | | **24 工作日** |

### 4.2 关键技术选型

#### 导出「单一 HTML + base64 内嵌」—— 可做，但有代价

**做法**：图片转 base64 内嵌进 HTML → 单文件、离线可看、可邮件发送。

⚠️ **代价必须提前告知**：
| 项 | 现实 |
| --- | --- |
| **体积** | base64 比原图**大 33%**。20 张 4K 图 = 约 **200 MB 的 HTML**（现代浏览器能开，但**移动端可能崩**） |
| **缓解** | ① 提供「图片质量」与「最长边」选项（默认长边 1920，约 1/6 体积）② 明确提示体积 ③ 大相册提示改用「文件夹导出」 |

**结论**：**技术上完全可行**（这是 1990 年代就有的技术），但必须在 UI 上**诚实告知体积**。

#### 编辑器实现：纯前端，不引入富文本库

**建议方案**：**自研页面编辑器**（Canvas 排版 + DOM 导出），**不引入** Fabric.js / Konva 等。

理由：
- 需求是「固定版式排版」，不是自由绘制
- 富文本库体积大（Fabric ~300KB），且导出 HTML 兼容性差
- 自研能精确控制导出的 HTML 结构（保证单一文件可离线）

⚠️ 若要「自由旋转/缩放任意元素」，才值得上 Konva。本期走「模板参数化 + 有限自由」路线。

#### PDF 导出：服务端生成

**建议**：服务端用 `chromium --headless --print-to-pdf`（复用项目已有的 headless CDP 能力），
前端把排版数据（JSON）POST 到后端。

⚠️ 成本：Chromium 约 300MB 运行内存 + 每份 PDF 约 3-8 秒。**必须在 worker 里跑，不能阻塞 API**。

### 4.3 素材与模板的「官方渠道更新」

**你的需求**：「所有模板、素材可以上传、管理也可以通过官方渠道更新下载」。

**建议**：
- **本期（5c）**：模板/素材**本地管理**（上传、编辑、启用/停用）
- **官方渠道更新**：做成「模板包 URL」配置项 —— 管理员填一个 URL，服务端去拉取模板包
  ⚠️ **必须 SSRF 防护**（项目已有 `internal/agentllm/netguard.go`，可直接复用）

### 4.4 验收标准（节选）

| # | 判据 |
| --- | --- |
| 1 | 20 张图的相册导出 HTML **≤ 30 MB**（长边 1920 + quality 0.82） |
| 2 | 导出的 HTML **断网后能正常打开并翻页** |
| 3 | 单页多图拼贴在 Chrome/Edge/Safari/mobile Safari 排版一致 |
| 4 | PDF 导出页数与相册页数一致，A4 横版 |
| 5 | 第三方素材上传有预览与「应用后不影响既有相册」保证 |

## 五、功能 6：AI 生成电子相册（B 档，依赖 5）

### 5.1 需求补全

你的原话：AI 根据主体和提示词，利用**系统现有素材**自动分析相册里合适的照片生成电子相册。

### 5.2 关键澄清：现有 AI 能力的差距

**侦察发现**：
- ✅ 有 `embed`（**Chinese-CLIP ViT-B/16**）→ **能做「按语义选片」**（这是选片的核心）
- ⚠️ `agentllm` **无多模态/vision 调用** → 现在的 LLM 只能传文本，**看不到图片**

**所以要做的两件事**：
1. **选片**：用已有的 CLIP embedding 检索（**复用现成能力**）
2. **编排与文案**：需要 LLM 读「选出的照片的元数据 + 描述」来生成**相册结构（页面编排建议）+ 文案**，
   而非「看图」。**这一条不需要 vision** ✅

💡 **这是个重要的降成本发现**：如果只让 AI「基于照片的标签/时间/地点/embedding 相似度编排」，
**现有能力就够，不需要多模态**。只有「AI 看图判断构图/主体」才需要 vision。

### 5.3 建议的实现路径

```
用户输入：「做个云南 7 日游的相册，突出风景」
    ↓
① 主题解析（LLM，纯文本）→ 关键词: [云南, 风景, 山, 日出...]
    ↓
② 选片（复用 Chinese-CLIP embedding 做语义检索 + 标签/地点/时间加权）
    → 取 20-40 张候选
    ↓
③ 编排（LLM，给它候选片的**元数据 + 标签 + 时间地点**，让它排页面顺序与标题）
    ↓
④ 生成（套用模板 → 交给功能 5 的渲染器）
```

⚠️ **质量控制**：AI 只出**建议**（页面顺序、标题、选片清单），用户可逐项改。
**不做全自动**——全自动的效果大概率不如用户自己排。

### 5.4 工期

| 项 | 工期 |
| --- | --- |
| 选片（CLIP 检索 + 多信号加权） | 3 d |
| 编排（LLM prompt + 结构化输出 + 解析容错） | 3 d |
| 前端交互（AI 建议面板，可逐项接受/拒绝） | 2 d |
| e2e | 1 d |
| **合计** | **9 工作日** |

⚠️ **前置依赖**：必须先有功能 5a（否则没有渲染器可交给 AI）。

## 六、功能 3：网盘挂载（C 档，建议推迟 + 给替代路径）

### 6.1 为什么建议推迟（诚实评估）

你要对接 **9 家**：百度网盘、阿里云盘、123网盘、115网盘、Google Drive、OneDrive、Dropbox、Apple iCloud+/iDrive。

**这不是「加 9 个适配器」的活。真实成本**：

| 维度 | 现实 |
| --- | --- |
| **协议碎片化** | 各家完全不同：官方 SDK（部分）、OAuth2、WebDAV、第三方开源（如 `aliyundrive` 系列、`115` 私有协议） |
| **授权门槛** | 百度/阿里/Google/Microsoft **都要申请开发者资质**（企业认证、个人也行但审核要时间） |
| **限流配额** | 各家 QPS/流量配额不同，且**常无文档**（需实测逆推） |
| **增量同步** | 大部分只能「全量列举」（无 change token / webhook），**10 万张照片每次全量列表很慢且吃配额** |
| **稳定性** | 第三方逆向库随时可能失效（如 aliyundrive 多次改 API） |
| **合规风险** | 逆向协议可能违反服务条款 |

**保守估算**：即使每家 3 天接入 + 联调，**9 家 = 27+ 工作日**，且其中至少 4 家（115、123、百度、阿里）**没有可靠的官方 API 或 SDK**，需逆向 → 法律与稳定性风险。

### 6.2 建议的推进路径（三步走）

| 阶段 | 内容 | 工期 | 说明 |
| --- | --- | --- | --- |
| **第一步（推荐先做）** | **通用 WebDAV 挂载** | 3 d | **一次性覆盖多家**：WebDAV 是通用协议，坚果云/腾讯微云/百度网盘（部分）/OneDrive/Google Drive **都提供 WebDAV**。4 家用一个适配器搞定 |
| **第二步** | **官方 API 挂载 2 家** | 6 d | 选**有正规官方 API** 的：Google Drive、OneDrive（微软 Graph）。文档全、授权正规 |
| **第三步（观察）** | 国内网盘 API | 视情况 | 百度/阿里/123/115 **等官方开放或社区方案成熟**。可在社区方案成熟后再评估 |

### 6.3 与现有能力的衔接

**好消息**：项目已有
- `watch`（rsync + debounce）→ 外部目录的变更监听底座
- `dirscope`（目录作用域）→ 外部库的可见性
- `storage`（凭据加密）→ 存 OAuth token / WebDAV 密码

⚠️ **红线提醒**：网盘挂载的媒体进库后，**`media.path` 是相对 `MediaRoot` 的相对路径**。
挂载点变化会导致全部媒体失效。**必须设计「挂载点 ID」而不是硬编码路径** —— 这是 Immich 踩过的坑
（外部库移动文件后元数据全丢）。

**工期** 第一步 3 d + 第二步 6 d = **9 工作日**（覆盖 6 家）· **约 35 万 token**

## 七、功能 7：广告 + 赞助（C 档，需先想清商业模式）

### 7.1 需求补全

你的原话：预研对接商业互联网广告（免费网站常见的那种）；设计赞助功能，赞助后输入注册码关闭所有广告。

**我必须先给一个诚实的判断**：这个功能**技术上简单，商业上需要慎重**。

| 维度 | 现实 |
| --- | --- |
| **技术上** | 🟢 简单。广告位组件（`<script>` 引入或 iframe）+ 一个「免广告」开关 |
| **广告 SDK 选型** | 常见：百度联盟、Google AdSense、7×24、BitBoard（个人开发者友好）。**国内自托管用百度联盟需要备案域名** |
| **隐私与体验** | ⚠️ 引入广告会拉第三方脚本，与项目**已启用的 CSP** 冲突（需为广告域开白名单）；且会拖慢加载 |
| **⚠️ 许可冲突** | 项目 AGPL/MIT？——广告 SDK 本身多为闭源，商业使用条款需逐个核实 |
| **变现现实** | 自托管相册用户群小、广告点击率低、**收益可能远低于维护成本** |

### 7.2 建议的顺序（赞助优先，广告后置）

**我强烈建议先做赞助，不做广告。** 理由：

1. **赞助更符合开源自托管项目的价值观**（PhotoPrism/Immich 都走这条路）
2. 广告会让项目从「干净的自托管工具」变成「塞满广告的网站」——**这是产品价值观的倒退**
3. 广告收益极低，赞助 + 「感谢名单」的心理收益可能更高

### 7.3 建议的实现（A 档变体，成本低）

| 项 | 内容 | 工期 |
| --- | --- | --- |
| 赞助入口 | 设置项 + 关于页的「赞助」按钮（**不做弹窗骚扰**） | 0.5 d |
| 注册码校验 | 输入注册码 → 服务端校验 → 写 `users.sponsor_until` / `is_sponsored` | 1 d |
| 权益控制 | 未赞助用户**不隐藏功能**，只加一个「赞助支持」徽章 | 0.5 d |
| 「感谢名单」页 | 赞助者名单（可选，公开致谢） | 0.5 d |
| **合计** | | **2.5 工作日** |

⚠️ **不做「付费解锁功能」** —— 那会与「开源」定位冲突，且 PhotoPrism 的 Plus 模式已经证明了
「把社区功能收费」会引发反弹。

**广告部分建议暂缓**。若将来要做，先解决：① 广告域名的 CSP 白名单 ② 与 AGPL 的兼容性确认
③ 广告 SDK 的商业条款 ④ 是否影响 GDPR/隐私声明。
